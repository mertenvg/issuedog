# issuedog specification

Status: draft 3, 2026-10-11

`issuedog` turns rough GitHub issues into reviewed pull requests. It asks the questions needed to write a spec, breaks the spec into ordered tasks, implements each task with headless Claude Code inside a Docker sandbox, verifies the result with real test runs and an independent reviewer, and opens a PR against a protected `main`. A human merges.

## 1. Goals

- Keep work moving on a repo while the owner is away, one task at a time.
- Make the owner's part fast: every question, decision and human task is self-contained and answerable from the GitHub mobile app.
- Treat automated testing and change verification as the first priority of every change.
- Use GitHub as the only control channel and the single source of truth. The daemon keeps no database.

## 2. Non-goals (for now)

- Running on GitHub-hosted runners or consuming GitHub Actions minutes.
- Parallel tasks within one repo.
- Merging PRs into `main`. Merging into `main` is always a human action. The App merges only into a story's branch: a verified task's PR, and `main` itself (7.5).
- Answering on the owner's behalf. A question waits for an answer indefinitely.

## 3. Architecture

```
Mac host (kept awake while issuedog runs)
├── container: issuedog-rumi-black   (one per repo)
│   ├── issuedog daemon (Go, uid issuedog)   holds the GitHub App key, owns /work/<repo>.git
│   ├── claude -p (uid agent)                one process per stage run
│   ├── verify commands (uid agent)          no GitHub credentials
│   ├── /work/runs/<run-id>                  agent-owned clone for one run
│   └── /run/issuedog/<run-id>               context files, read-only to agent
└── container: issuedog-dmcn
```

- One container per repo, so a failure in one repo leaves the others running.
- The daemon acts on GitHub as a GitHub App (section 15) through a Go client: `go-github` v92 with an App installation-token transport, which has the sub-issue and issue dependency calls, plus raw REST calls for what the client leaves out, such as the issue types of timeline events and removing an issue type, and GraphQL for edit histories and deleted-comment events (6.4). There is no `gh` dependency. This gives native ETags for polling (section 8.1), typed responses, and tests against `httptest` fakes.
- The daemon starts a fresh `claude -p` process for every stage run, including every retry. Sessions are never resumed, so each run starts from the issue and the code, and the verifier never shares context with the implementer.
- The base image follows the existing sandbox setup: `~/.claude/CLAUDE.md` bind-mounted read-only, `--dangerously-skip-permissions` as the non-root `agent` uid, feature branch per task.
- Nothing in the container runs as root. The image starts the daemon as `issuedog`. The daemon binary is the only file with capabilities: `cap_setuid` and `cap_setgid` to start stage runs as `agent`, and `cap_net_admin` to apply the agent firewall at startup. It is `root:issuedog 0750`, so `agent` can't run it, and processes started as `agent` get no capabilities. Every `docker run` of the image needs `--cap-add NET_ADMIN`, without which the kernel refuses to start the binary, and must not use `--security-opt no-new-privileges`, which ignores file capabilities.
- The host must not sleep while issuedog runs (for example `caffeinate -s`, or the equivalent Docker Desktop setting).

### 3.1 Who writes to GitHub

Only the daemon writes to GitHub. Agents return structured output and the daemon validates and applies it.

- The GitHub App private key lives in `/state/app-key.pem`, on the state volume, readable only by the `issuedog` uid. It is imported once with `issuedog key import` (section 15), so it is never bind-mounted from the host or built into an image. The daemon mints short-lived installation tokens and uses them for its own API calls. Nothing running as `agent` ever receives a GitHub credential. That includes GitHub connectors and GitHub MCP servers, which are never configured for an agent.
- Claude and every repo command (tests, lint, build) run as the `agent` uid. A different uid cannot read the key file or the daemon's memory.
- Claude's own credential (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`) is necessarily in the agent's environment. Outbound traffic from the `agent` uid is limited to `network.allow` (section 13), enforced inside the container with an owner-matched firewall rule, so a prompt-injected agent cannot send it, or the code, elsewhere.
- Agents read issue context from files the daemon writes to `/run/issuedog/<run-id>/`, outside the clone, so the daemon controls which comments an agent sees (section 6) and nothing it writes appears in the diff.

This keeps prompt-injected text from reaching GitHub directly and makes every write retry-safe.

### 3.2 Git handling

The daemon never runs git, or any other repo command, as `issuedog` inside a directory the agent can write. Hooks and config in an agent-writable repo (`pre-push`, `core.sshCommand`, `core.fsmonitor` and so on) would otherwise run with the daemon's privileges.

- The daemon owns a bare clone, `/work/<repo>.git`. It is the only repo the daemon pushes from, and the only place it reads trusted files from (section 3.4).
- For each run the daemon creates `/work/runs/<run-id>` by cloning the bare repo as `agent`. Not built yet: the clone holds only the commits the daemon names for the run, with their history, and has no remote (3.4). Today's clone keeps `origin` and every branch. Implementer runs start from the task branch head, or on the first attempt from the task's base: its story branch's tip for a task in a story, or `main` for a task with no parent (7.5). A conflict bug's first attempt starts from the `main` commit it names instead (3.4, 7.5). Either way the daemon names the SHA, under the rule in 3.4.
- After an implementer run, the daemon runs `git bundle create` as `agent` for `base..HEAD`, then fetches the bundle as `issuedog` into `refs/issuedog/runs/<run-id>` in the bare repo. A bundle is plain data, so nothing from the agent's repo config or hooks executes.
- All diff inspection (section 10.1, rules 2 to 7) happens in the bare repo. The daemon's own git config defines no diff or filter drivers, so `.gitattributes` in the branch cannot trigger commands.
- Verify commands and the LLM verifier run in fresh `agent`-owned checkouts of the exact head SHA, never in the implementer's clone. Untracked files the implementer left behind (for example `.claude/settings.local.json`) never reach them.
- **Branches.** Section 7.5 has the design. Not built yet: the daemon opens and merges no PRs until phase 3 (section 17).
  - A story, or an epic planned into tasks, has one story branch, `issuedog/<story>-<slug>`, cut from `main` when its first task is picked. An epic planned into stories has none.
  - Task branches are named `issuedog/<issue>-<slug>`. A task in a story branches from its story branch's tip, and its PR targets that branch. A task with no parent branches from `main`, and its PR targets `main`.
  - A task is blocked until its dependencies merge, into the story branch for a task in a story, so stacked branches are never needed.
  - Every `issuedog/*` branch, story or task, is under the `issuedog branches` ruleset (section 15): only a repository admin or the App can create, force-push or delete one. Anyone with write access can still push commits to one that exists, so its history only moves forward. A write collaborator who isn't an admin can push to an existing `issuedog/*` branch but can't create, delete or force-push one, task branches included, and names branches of their own outside `issuedog/`.

### 3.3 Claude invocation

```
claude -p "$(cat /run/issuedog/<run-id>/prompt.md)" \
  --output-format json \
  --json-schema "$(cat schemas/<stage>.json)" \
  --append-system-prompt-file /run/issuedog/<run-id>/system.md \
  --dangerously-skip-permissions \
  --no-session-persistence \
  --max-turns <stages.max_turns.<stage>> \
  [--max-budget-usd <stages.max_budget_usd.<stage>>] \
  [--model <model>] \
  [--effort <level>] \
  [--fallback-model <model>,<model>,...]
```

- The daemon validates the stage's output from the `structured_output` field of the JSON result. The run fails (fail closed) if `subtype` is anything other than `success`, including `error_max_structured_output_retries`, or if `structured_output` is missing or fails the daemon's own validation.
- The daemon writes the full JSON result to `/state/runs/<run-id>.json` before acting on it, for restart recovery (section 8.2).
- Each stage has a timeout from config. On timeout the daemon kills the whole process group, and the run counts as failed.
- `--max-budget-usd` is a client-side estimate and is optional.
- **Model and effort.** The daemon resolves a run's model, effort and fallback models when the run starts, and passes each flag only when it has a value, so an unset one leaves the CLI's default.
  - It starts from the stage's `stages.model`, `stages.effort` and `stages.fallback_model` (section 13).
  - An issue's `model:*` and `effort:*` labels override them for every run on the issue except the verifier's, such as the interviewer and planner on an epic or story and the implementer on a task. `verifier-model:*` and `verifier-effort:*` apply only to verifier runs. A model label names an allowed model by its label suffix (section 13). Labels match ignoring case.
  - Each implementer attempt after the first in a round (8.3) raises the effort one level, up to `stages.max_effort`. A raise never lowers: an effort above the cap, from a stage default or a label, is used as it is. An unset effort stays unset.
  - `--fallback-model` is the stage's list, in order and comma-joined, without the run's own model.
  - Every run checks all four kinds of label, not only the two it uses. Two labels of one kind, or one that names no allowed model or effort level, start no run on the issue at all, and the issue gets one state error, `kind=labels` (5.3).
  - The lease records the resolved settings (8.2), so a label changed during a run affects only the next run, and a restart applies a result with the settings it ran with.
  - The JSON result's `modelUsage` names each model that ran, by full name, such as `claude-haiku-5-5` for `--model haiku`. The run marker records them (section 5).
- **Credential.** The agent gets exactly one Claude credential: `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, whichever is set in the daemon's environment. If both are set, the daemon refuses to start.
- **Usage limits.** `-p` mode does not report the reset time in a machine-readable form. The daemon matches the result text of a failed run (a non-`success` subtype or `is_error`) against `usage_limit.pattern`, so model text that mentions a limit in a successful run doesn't count. If the text includes a reset time it waits until then. Otherwise it backs off, starting at 15 minutes and doubling to a 2-hour cap. While it waits, steps 1 and 2 of the loop (section 8.1) keep running, so commands such as `/hold` still apply. Usage-limit waits do not count toward the retry cap.

### 3.4 Trusted inputs come from `main`

The daemon reads these from `main` in its bare clone, never from a task branch or a story branch (7.5):

- `CODEOWNERS`
- `.issuedog/config.yaml`, including `verify.commands`
- `.issuedog/prompts/*.md`; a missing file falls back to the default that ships with issuedog
- JSON schemas, which ship with issuedog and are not overridable

The triage agent, interviewer and planner run in a fresh checkout of `main`.

The task verifier runs in a fresh checkout of the head SHA, but only after rule 2 of section 10.1 has passed. Every agent-config path (section 6.3) in that checkout therefore matches its version on `main` at the run's baseline, a `main` commit that rule 2 takes from git (10.1). For a task in a story, that's the story's baseline, the merge base of `main` and the story branch's tip the task is named against, not anything in the task's own history (10.1, 7.5). The story verifier runs in a fresh checkout of its story branch's tip (10.3), only once that tip's checks pass, rule 2 included (7.5), so the same holds for it.

**Named commits.** Not built yet: the PR flow, phase 3's (section 17). An implementer or verifier only ever runs in a checkout of commits the daemon named. Every commit the daemon names has each protected path (section 6.3) equal to its version at the run's baseline, one `main` commit (rule 2 of section 10.1), except the story tip a conflict bug merges (below). An implementer never fetches or merges a branch head itself. The rules that follow from it hold for every task, with a parent or none, on any attempt and whatever triggered the run:

- **What the daemon names.** It gives each run its starting SHA. When the run must merge its target, as a conflict bug does (7.5) or a task whose target moved, it also names the exact target SHA to merge. The clone holds nothing else to fetch (3.2).
- **A conflict bug's run.** It starts from the `main` commit the bug names, its baseline, and names the story tip to merge into it (7.5). That tip, and on a later run after the story branch moved, the newer tip it names to merge once that tip passes rule 2, are the only named commits whose protected paths may differ from the baseline's. Each passed rule 2 against the story's baseline, an older `main` commit, so it changed no protected path since then, and merging it changes none in the checkout: they stay at the bug's baseline. That assumes git's rename detection doesn't carry the story's edits into a path the named `main` commit renamed into a protected one. If it does, the head fails rule 2, and like any such head it's never named (below): each retry starts from the bug's base again, until the last attempt sends the bug to `needs-human` (8.3). So at the start of the run the checkout never holds the story's older agent config, even when the `main` commit the bug names changed a protected path. Started from the tip instead, the run would hold that config, or under this rule never start, and the story would wait for good.
- **Only tips that passed rule 2.** The daemon names a head or a target tip only once it has passed rule 2. When the target has moved to a tip that hasn't passed rule 2 yet, or failed it, the run doesn't start, or is stopped with its result dropped (8.2), and the task waits where it is until a tip passes.
- **Rule 7** is judged against the named target SHA, not against wherever the branch has moved since.
- **A head that fails rule 2.** A head a person pushed to a task branch that fails rule 2 sends the task to `needs-human` with a hand-off (9.3, 7.2), never back to `pr-open`. Any head that fails rule 2 when a run would start, as after `/done`, or the App's own head once a merge of `main` into its story has changed a protected path, is never named: the daemon names the task's base instead, as on a first attempt, and the old head is dropped. For a conflict bug, the base is the `main` commit it names, not the story tip (7.5). The App then pushes the new run's result over it, a reset its bypass of the `issuedog branches` ruleset allows (section 15). So when a merge of `main` the App makes into a story changes agent config, or any other protected path, an open task in the story that needs another run restarts from the story's tip, and its earlier work is dropped. That's the owner's decision: the daemon doesn't build the merge of the new tip into the old head itself.
- **A story's waits.** A task in a story also starts no implementer run, and makes no move into `in-progress`, while its story branch's tip has no passing check, or a failure on the branch is open (7.5). That holds for a pick from `ready`, a retry after findings, and a review or a moved target branch at `pr-open` alike. A failure's own bug is excused from both, and its own open failure never blocks it. Once the branch moves past the tip it was filed for, it waits only for a tip that passes rule 2, then targets it even if other rules fail there (7.5).

### 3.5 Daemon settings

The daemon's own settings come from its environment, not from the repo:

- `ISSUEDOG_REPO`: the repo, as `owner/name`.
- `ISSUEDOG_APP_ID` and `ISSUEDOG_INSTALLATION_ID`: the GitHub App and its installation on that owner (section 15).
- The Claude credential (section 3.3).

The App's slug is read from `GET /app` at startup, so it can't be misconfigured. The App's comments are those by the bot `<slug>[bot]` (5.1).

Startup checks the Claude credential, the settings and the App key, then reads the slug, mints a token, syncs the bare clone, loads config and trust from `main`, and creates missing labels (section 15). It also checks the stages registered in code: none may run at `intake` while triage is set, since a triage run's lease records `intake` (8.2), so that stage's results would all be dropped. Only then does it apply the agent firewall and start the loop. A missing or malformed setting, or a failed step, stops the daemon with exit code 1 and the reason logged. A SIGINT or SIGTERM stops it with exit code 0, logging that it stopped on a signal, whether the signal comes in the loop or during startup once the App key is checked. A signal before that, during the credential, settings or key check, gets the default handling: it kills the process, so the exit code isn't 0. After the key check, up to and including creating the labels, a step that fails once a signal has come in stops startup as a signal, not as a failed step, so the exit code is still 0. That holds whether or not the signal caused the failure: it covers setting up the GitHub client from the key, before the slug is read, which no signal interrupts, and a failure that only coincides with the signal.

Not built yet, with the PR flow (section 17): startup also checks the `issuedog branches` ruleset (section 15). It reads the active rules for a branch name under `issuedog/` with `GET /repos/{owner}/{repo}/rules/branches/{branch}`, which lists org rulesets too, and stops the daemon, as a failed step does, unless they include `creation`, `deletion` and `non_fast_forward`. Story branches rely on all three (7.5). The App can't read a ruleset's bypass list with Metadata read, so the check can't confirm it (section 16).

`network.allow` and `usage_limit.pattern` (section 13) are read once at startup, so a change to either takes effect on restart. The rest of the config, and trust, are reloaded on every loop iteration (8.1).

## 4. Work item types

| Type | Meaning | Created by |
|---|---|---|
| `epic` | A rough idea or large feature | Owner |
| `story` | One user-visible outcome with acceptance criteria | Planner (epic plan), or owner |
| `task` | One PR, one scope; a human task has no PR (section 9.3) | Planner (epic or story plan), owner for a small change, or the daemon, as a human task, for a story branch that fails rule 2 (7.5, not built yet) |
| `bug` | Something broken | Owner, story verifier, or a failure on a story branch (7.5, not built yet) |

- Repos owned by an organization use GitHub issue types. The org's defaults are Task, Bug and Feature, so an org owner must create `Epic` and `Story` first. Repos owned by a personal account have no issue types and use `type:epic`, `type:story`, `type:task`, `type:bug` labels instead. Config selects which.
- For now, issuedog chooses a type only by label (`types: labels`). On a `types: issue-types` repo the App sets an issue type only to revert an untrusted change (5.1), or on a child it creates from a plan, `Story` or `Task` (5.2), and the interviewer can't set one: on an untyped issue there, one of its questions asks the owner to set the type on the issue.
- Hierarchy uses native sub-issues: epic → story → task, or epic → task. Sub-issues must share the parent's owner. GitHub allows 100 sub-issues per parent.
- An epic with a single user-facing outcome is planned directly into tasks and acts as its own story, including story verification (section 7.3).
- **Untyped issues.** The owner may file an issue with no type. At `clarifying` the interviewer picks one of the four types and sets it with a question round, a spec, or for a bug or task the `typed` outcome (9.1). The App adds the `type:<type>` label and removes any other `type:*` label. Every comment that sets a type starts with the type and a one-line reason (9.1). If it can't tell yet, it asks questions first and sets the type once the issue is clear. A spec on an untyped issue must set it to epic or story, so an issue with no type doesn't leave `clarifying`.
- **Changing the type.** The interviewer may set or change only a type it set itself: on an untyped issue, or on one each of whose `type:*` labels stands, on the timeline, as the App's add. It runs only at `clarifying`, so that's the only stage it types at. Every other type change is the owner's. The owner can change it at any time, and the daemon follows the owner's type from then on. If the issue's current stage doesn't apply to the new type (section 7.2), the daemon leaves it where it is and reports a state error (5.3).
- **A child is never typed `story`.** The interviewer runs on a story with a parent only at the `clarifying` after a hold from a stage of its plan, where it never writes a spec or sets a type (9.1), and the table has no spec move for one (7.2). So typing an issue with a parent as `story` is invalid interviewer output and a failed attempt (8.3). `issue.md` names the parent, and the interviewer's preamble states this rule (section 12).
- A story filed by the owner has no parent epic. It goes through clarifying, spec review and planning like an epic, then story verification (section 7.3).
- A `bug`, or a `task` filed by the owner, goes through clarifying and then becomes a single task. It skips spec review and planning. Until build phase 3 (section 17), such an issue, whether filed with its type or typed by the interviewer, waits at `clarifying` with no interviewer runs (7.2). A bug filed against earlier work starts its body with `Follow-up to #N` and includes the acceptance criterion "the original behavior of #N is unaffected."

## 5. State

GitHub is the single source of truth. The daemon keeps only an in-memory cache, rebuilt from GitHub on startup and corrected on every poll.

| Concern | Where it lives |
|---|---|
| Stage | `stage:*` label, valid only as described in 5.1: exactly one of the 7.1 stages per open issue in the pipeline, and on a closed one whose close was judged, one closed stage, `stage:completed` or `stage:discarded`, which is valid only on a closed issue (6.4, 7.1) |
| Type | Issue type, or `type:*` label |
| Hierarchy | Native sub-issues |
| Dependencies | Native blocked-by / blocking within one owner, `depends-on` marker across owners (section 14) |
| Priority | `priority:p0` to `priority:p3` (default `p2`) |
| Scope | `scope:<name>` from the repo's allowed list |
| Model and effort | At most one each of `model:<suffix>`, `effort:<level>`, `verifier-model:<suffix>` and `verifier-effort:<level>` (3.3, section 13) |
| Transition history | Bot comments carrying a `transition` marker, e.g. `<!-- issuedog:transition from=clarifying to=spec-review rev=3 body=9f2a61c0 run=8f2c effort=high model=opus ran=claude-opus-5-5 seen=2214587 -->` |
| Attempt count | Hidden marker on the latest bot verifier comment for a task. For other stage runs, the daemon's memory and the lease (8.2, 8.3), so a restart resets every count but the latest run's. The lease also keeps what the attempt cap's error says of why that run failed (5.3) |
| State errors | Bot comments carrying an `error` marker with a stable key, and the bot's `ack` replies to them (5.3) |
| Label reverts | Bot comments carrying a `revert` marker keyed by the reverted timeline event, a label's, an issue type's, or a close's or reopen's (6.4), so a replay doesn't comment twice (5.1, 5.2). A label or issue type that no event explains has no event to key by, so its key is its name and the newest event: `<label>@<id>` for a label, `issue-type:<type>@<id>` for an issue type (5.1) |
| Discussion holds | The hold's transition marker and the bot's notices, each keyed by its trigger, and the bot's `ended` records (6.4) |
| Processed commands | The bot's 👍 on an applied command comment or 👎 on a rejected one, plus `cmd=<comment id>` in the transition marker or a `reply` marker (9.2). A reaction command (section 9.2) is recorded as `cmd=r<reaction id>`, in a transition marker, or for a 👍 on a human task whose check failed, in a `reply` marker (9.3) |
| Spec and plan revisions | One revision comment per revision, carrying a `revision` marker with `rev` and the hash. A spec's hashes the body. A plan's is `kind=plan`, on the plan comment's last line, and hashes the comment above it. A transition posted with a revision, or approving one, carries both too, except that one posting a plan revision carries only `rev` (section 7.4) |
| Triage decisions | Bot comments carrying a `triage` marker: a flag waiting on a code owner, or an issue left to people (6.2) |
| Dirty content | A visible note carrying a `dirty` marker at the top of the comment or body (5.1) |
| Origin of bot-created issues | Hidden `origin` marker in the issue body (section 6.2), or reposted in an App comment once the body's markers aren't read (6.4), with `human=1` on a human task's, and its **Done when** check, if it has one (9.3) |
| Created children | The bot's `created` record on the parent, naming the children of its approved plan revision, or for a revision, the children it leaves (5.2) |
| Story branches | Each story's `issuedog/<story>-` branch, found by that prefix, and its history, which only moves forward under the `issuedog branches` ruleset (section 15). The App's `issuedog/verify` check runs, each naming the branch, mark the tips it checked and their results (7.5, 10.4). There's no record of the branch on the story. Not built yet |
| Digest | The bot's issue carrying a `digest` marker, and its `digest-new` comments, which record the items already announced (9.4) |

Every marker is an HTML comment, `<!-- issuedog:<kind> key=value ... -->`, with its fields in a fixed order. The order is a fixed list in code, such as `from`, `to`, `round`, `run`, `event`, `cmd`. Any field not on the list, such as `effort`, `model`, `questions`, `ran`, `recommend` or `seen`, follows them, sorted by name. The kinds so far:

- `transition`: `from`, `to`, and the key that makes it idempotent (5.2). The key is `cmd=<comment id>`, or `cmd=r<reaction id>`, for a command; `run=<run id>` for a stage run's result; `event=<timeline event id>`; or `event=p<comment id>` for a created child's first move, naming the parent's comment that holds its move to `planned` (5.2). The moves an approved revision makes on a child, a changed child's move and a dropped child's close, are keyed the same way, by the parent's comment that holds the revision's move to `planned` (6.4). The first move of a human task filed for a story branch's failure is keyed `event=t<SHA>`, naming the failing tip, and so is a conflict bug's close once a tip makes it moot, naming that tip (7.5); neither is built yet. An event key carries `by=<login>` for a stage label a trusted user changed by hand (5.1), and no `by` for a move into the pipeline by a label (6.2). Some transitions carry more:
  - A move to `held` carries `at`, the stage the issue was at, and `reason`: `owner` for `/hold`, a hold set by hand or a trusted reopen, or `discussion` or `dropped` (6.4). A discussion hold also carries `origin`, and is keyed `event=<its trigger's key>` (6.4). A trusted reopen's move is `closed → held`, keyed `event=<the reopened event's ID>`, such as `<!-- issuedog:transition from=closed to=held at=spec-review reason=owner event=21877741 seen=2214587 -->`.
  - A hold set by hand on an issue that is already held writes a `held → held` marker with `reason=owner`, `by` and `event`, which keeps the first hold's `at` and `origin` (5.1). So does the owner hold that 6.4 records again when an edit or a deletion hid a hold's marker, keyed `event=<the trigger's key>`, with no `by` and no `cmd`.
  - A held child that its parent's newly approved revision changed gets a `held → held` marker with no `reason`, keyed `event=p<comment id>` as above, carrying `at` and `origin`, both the stage the change would send it to, and the hold's `seen` (6.4), such as `<!-- issuedog:transition from=held to=held at=ready origin=ready event=p6245648446 seen=2214587 -->`. Having no `reason` is what tells it from a hold: it isn't a hold of its own, so it adds nothing that a `/resume` must end. It sets the hold's `at` and `origin`, which `/resume` and the interviewer's `unchanged` then take the issue to. When no hold before it is read, as when the first hold's comment is dirty, it sets the hold's `seen` too, and `/resume` on the issue ends the hold. A held child's first move is such a marker too, with its first stage as `at` and `origin` (5.2).
  - A move out of `held` to `clarifying` after a discussion carries `at` and `origin` (6.4). When the last trigger's resolution makes it, it is keyed `event=h<the ID of the comment holding the move that began the hold>`, and carries `resolved=<Unix seconds>`, the time of the latest act that resolved a trigger, whichever trigger went last. When no act resolved any, as 6.4's With no act says, it has no `resolved`.
  - Every transition marker written at the `clarifying` after a discussion hold carries `origin` (6.4), but for a move out of it to a stage other than `held` that the interviewer doesn't make: an override (5.1), or a parent's revision's move of its child (6.4), carries none. An interviewer run's move there may carry `cmd=<comment id>` beside its `run`, naming the `/revise` it handled (6.4).
  - The interviewer's `plan` move (9.1), `clarifying → planning`, carries `replan=1`. After a hold from `planning`, that's what tells it from `unchanged`'s move, which is the same move, `run` and `origin` included. A `plan` move written before `replan` was added counts as `plan` only when its `origin` isn't `planning`, so the planner gets the interviewer's notes only after a `plan` move (section 12).
  - A move that posts or approves a revision carries `rev` and `body`, the revision's hash (7.4). The exception is a move that posts a plan revision: it carries `rev` but not `body`, since it sits inside the text the plan's hash covers, so the hash is only in the plan revision marker.
  - A plan's approval, `plan-review → planned`, carries the plan revision's `rev`, its hash as `body`, the approving `cmd` and `seen`, as a spec's approval does, with no field of its own (7.4).
  - The move to `spec-review` or `plan-review` that a dirty spec revision or plan comment hid, recorded again (5.1), is keyed `event=spec-dirty-<the dirty comment's ID>` or `event=plan-dirty-<the dirty comment's ID>` and carries `seen`, as in `<!-- issuedog:transition from=planning to=plan-review event=plan-dirty-6245648446 seen=6245640901 -->`.
  - A move to `closed`, the App's own close (7.2), carries `reason`, the state reason it closes the issue with: `completed` for a human task (9.3), as in `<!-- issuedog:transition from=needs-human to=closed reason=completed cmd=r444435463 seen=2214587 -->`, and for an epic planned into stories once every child is closed (7.3), keyed `event=p<comment id>` by its own comment that holds the move to `planned` approving its plan, as in `<!-- issuedog:transition from=planned to=closed reason=completed event=p6245640901 -->`, and `not_planned` for a child an approved revision drops, or an issue below it (6.4), as in `<!-- issuedog:transition from=ready to=closed reason=not_planned event=p6245648446 -->`.
  - `seen=<comment id>` is the newest comment read before the move. It bounds the next round's input (9.2). On a stage run's move it is the newest comment on the issue when the run started. On a move by `/revise`, a revision request or `/approve`, it is that comment. On an approval by 👍 it is the newest comment the daemon had read. On a move into, within or out of `held`, it is the bound from before the hold, so comments posted while held are input in the stage the issue lands in (6.4). On a move recorded again because a dirty comment hid it (5.1), it is the bound of the latest move the clean markers show, as the hidden move's own `seen` can't be read.
  - A stage run's move carries `model` and `effort`, the settings the run started with, each only when set, and `ran`, the full names of the models that ran, comma-separated, from the result's `modelUsage` (3.3). A value a marker can't hold, such as one with a space, is left out and logged.
  - An interviewer question round's move, `clarifying → clarifying`, carries `round=<n>` and `questions=<count>` (9.1), for example `<!-- issuedog:transition from=clarifying to=clarifying round=2 run=8f2c effort=high model=opus questions=3 ran=claude-opus-5-5 seen=2214587 -->`. The interviewer's `typed` move (9.1) is the same move and carries neither. A planner question round's move, `planning → planning`, carries both too, numbered with the interviewer's rounds (9.1).
  - A move into the pipeline is keyed by how the issue got in (6.2): `event=` for `stage:intake` or `approved`, `run=` for triage, `cmd=` for `/track` and `cmd=r` for a 👍 on a flag. A child the daemon created enters by its first move instead, keyed `event=p<comment id>` (7.2).
- `revision rev=<n> body=<hash>`: in each spec revision comment (7.4). Posted without a transition, it also carries `seen`.
- `revision kind=plan rev=<n> body=<hash>`: the last line of each plan comment, which is its plan revision (7.4, 11.4). Its hash covers everything above it.
- `plan-data v=1 data=<data>`: in each plan comment, between the move's transition marker and the plan revision marker. It keeps the validated plan, task bodies and checks included, which the comment's text never shows (11.4). In a revision, a kept item's entry is its approved one in full, from the approved revision's data, with the dependencies it keeps (11.3). `data` is the plan's JSON, compressed with raw DEFLATE and encoded as unpadded base64url. A reader refuses any other `v`, a second marker in one comment, and data that doesn't decode to exactly the plan's fields.
- `reply reason=<rejected|edited> cmd=<comment id>`: on the App's reply to a rejected command, or to an edit made after the App used the comment (9.2). It marks the comment as processed. A command the App 👎'd gets no edited reply.
  - `reply reason=rejected cmd=r<reaction id>`: on the App's reply to a trusted 👍 on a human task whose check failed (9.3). It marks the 👍 as processed, so it's checked once.
- `error kind=<kind> key=<key>`: a state error (5.3). The ack reply to it carries `error kind=<kind> key=<key> ack=r<reaction id>`, and covers only that kind and key. An ack from before acks named a kind has no `kind`, and covers its key for every kind.
- `revert key=<event id>`: an untrusted label change the daemon reverted (5.1), or an untrusted close or reopen, keyed by its `closed` or `reopened` event (6.4). For an unexplained label it removed, the key is `<label>@<event id>`: the label in lower case, URL-escaped, and the ID of its latest event, or 0. One comment may carry several.
- `notice key=<trigger key>`: on the App's notice of a discussion trigger that isn't a comment (6.4). The hold's own comment carries its first trigger's notice too.
- `ended reason=<discussion|owner>`: the App's record that a hold ended while the issue stayed held (6.4).
  - `ended reason=discussion resolved=<Unix seconds>`: every discussion trigger on the issue is resolved, at that time, but an owner hold stays, or the hold began at `intake`. It may also carry `held=<comment id>,…`, the `/hold`s on ancestors that keep the issue held, with `heldon=<issue number>,…`, the issue each counted as posted on, in the same order, and `gone=<issue number>-<Unix seconds>,…`, comments deleted on ancestors during the hold that may have been `/hold`s. A record that only names such holds, when the last trigger went with no act to resolve it, has no `resolved`.
  - `ended reason=discussion resolved=<Unix seconds> cmd=<comment id>`: a `/resume` on the issue, at that time, accepted every trigger made before it, while a later one keeps the issue held. It carries `after=1` when that `/resume` would itself have sent the issue to `clarifying`.
  - `ended reason=owner key=<hold> cmd=<comment id>`: that `/resume` ended the owner hold named by `key`, while the issue stays held for another reason. The key is `c<comment id>` for a `/hold`, `e<event>` for a hold keyed by an event, such as one set by hand or a trusted reopen, or `g<issue number>-<Unix seconds>` for a deleted comment that may have been a `/hold`. One comment may carry several.
- `triage verdict=<ask|leave>`: a triage decision on an issue with no stage label (6.2), with one key. The key is `run=<run id>` for a triage run's result, `cmd=<comment id>` for `/ignore`, or `cmd=r<reaction id>` for a 👍 on a flag. A flag, `verdict=ask`, also carries `recommend=<handle|leave>`, its recommendation, for example `<!-- issuedog:triage verdict=ask run=8f2c recommend=handle -->`. The issue's decision is the latest triage marker in its comments. One in dirty content doesn't count.
- `dirty by=<login>`: the note on dirty content (5.1).
- `rewrite run=<run id>`: the first line of every whole body the App writes, such as a spec (11.1), or a changed child's body, whose `run` names the planner run that wrote the revision (6.4). It also carries `replaced=<login>` when the body it replaced was dirty. It marks the App's full rewrite, which cleans the body (5.1).
- `origin`: in the body of an issue the daemon created (5.2), or reposted in an App comment once the body's markers aren't read (6.4).
  - **The issue's origin.** The daemon reads `plan=#<n>`, `rev` and `item` into the issue's state from a whole `origin` marker: one with a plan number and a `rev` above 0, and an item. Other fields don't stop it from being read. It places a waiting plan in its parent plan's order (9.4), matches a child to its plan item (5.2), and makes the issue one filed from a plan, for its class, such as a task from the planner rather than one the owner filed (7.2), and for the digest's title rule (9.4).
    - **Where it's read.** From the first whole marker in the body, while the body's markers are read: like any body marker, only from the App, in a body that isn't dirty and that nobody but the App edited last (5.1). Otherwise, from the newest clean App comment that carries a whole one, whoever wrote or edited the body (#195's assumption 3). That covers the App's repost of a lost marker (6.4), and an issue a person filed whose App comment carries its `origin`, as an adopted story's does. The body's marker wins while it's read. A marker in a dirty App comment, or in anyone else's comment or body, counts for nothing.
    - **After a revision.** A changed child's rewrite gives its marker the revision's `rev`, and a kept child keeps the `rev` it was filed at (6.4). An adopted child, one a person filed, has its rewritten marker in its move's comment as well, since its body's markers aren't read, and so does a child a clean App comment carries an older `origin` for, such as a repost (6.4).
  - **The body's last line.** The daemon writes the marker as the last line of each child's body, `origin plan=#<n> rev=<r> item=<id>` (5.2, 11.2).
  - **Human tasks.** A human task's marker also carries `human=1`. It's how the daemon knows a human task: a task with an `origin` marker is a human task (7.2) exactly when the marker has `human=1`.
  - **The check.** A human task whose **Done when** has a check (9.3, 11.3) records it on the same marker (#250's Q1a): `check=<kind>`, by the kind's name, and `value`, the label, the issue type, the file's path, the required check's name or the owner, and for a `file` check with text, `contains`. `value` and `contains` are percent-encoded as a `digest-new` marker's keys are (9.4), so a space, `<`, `>` or `%` reads back exactly, such as `<!-- issuedog:origin plan=#12 rev=1 item=T4 check=file contains=go%201.25 human=1 value=go.mod -->`. A plain-text **Done when** adds none of these. The check is read with the rest of the marker, so only from a marker the daemon reads (5.1). A marker with none of `check`, `value` and `contains` has no check. Fields that don't make a whole check read as a check that couldn't be read, which fails (9.3), not as no check: a whole one has a known kind, a `value` that decodes and isn't empty, and `contains` only on a `file` check. The App never writes any other.
  - **Story branch failures.** Not built yet: an issue filed for a failure on a story branch (7.5) carries `origin story=#<n> tip=<SHA>`, naming the story and the failing tip, with `human=1` on the human task filed for rule 2. On that human task, `story` and `tip` are its own **Done when** check (9.3), not plain text. Before filing, the daemon looks for an issue whose `origin` names the same story and tip, open or closed, and reuses it, as for a plan's children (5.2). So each failing tip is filed once.
- `created rev=<n> children=<n>,<n>`: the App's record on a parent that every child of its approved plan revision `rev` is created, linked, given its first move and its blocked-by links (5.2). It names the children by issue number, in plan order, and its comment lists each one, such as `- S1 #247: title`. Only a clean one of the approved revision counts, and only when every child it names reads back as a number above 0.
  - **A revision's record** is written once every change the revision makes to the children is made, and names every child it leaves: each kept, changed and new item's, but no dropped one's (5.2, 6.4). One that leaves none has `children=none`, which reads back as no children, and stands like any other.
- `depends-on url=<issue url>`: a dependency across owners (section 14).
- `digest`: the digest's identity marker, with no fields, on the last line of its body (9.4).
- `digest-new items=<key>,<key>`: on the App's comment on the digest that announces new items, naming their keys (9.4).
- Planned: the attempt marker on the latest verifier comment of a task (8.3), not built yet.

Assignees, and the priority labels on PRs, are not state either: the daemon derives them (section 9.6) and corrects them on every poll. Nor are the `triage:*` labels, which follow the latest triage marker (6.2). Nor is the digest's body, which the daemon renders from what waits on the owner (9.4).

Apart from the App key (section 3.1), the only local files are the lease (section 8.2) and the run results in `/state/runs/`. Both are scratch: losing the container loses nothing except the current run and the count of failed non-task runs toward the attempt cap (8.3).

### 5.1 Reading rules

- **Markers.** The daemon only reads markers in comments and issue bodies written by the issuedog App (3.5). A marker anywhere else is ignored.
  - **Embedded text.** Whenever the App writes a comment or body, it escapes `<!--` as `&lt;!--` in all text it didn't write itself, such as agent output, quoted comments, issue titles and file contents. So the only unescaped markers are the daemon's own.
  - **Dirty content.** A comment or body is dirty once someone edits it whose edit isn't sanctioned. An edit by its author or the App is sanctioned, and so is one by a trusted user (6.1), except on a comment the App wrote: such a comment carries state markers, so only the App may edit it. Once the App has rewritten an issue body whole (below), the App is the body's author, so the issue author's own later edit is sanctioned only if they are trusted. The daemon never reads markers in dirty content, and it never counts as a command, an answer or an approval, however it is edited later. The one way back is the App's full rewrite of an issue body, below.
    - **Trust as it stands.** Trust is checked afresh on every pass, so an editor who loses trust makes their earlier edits dirty again. A visit to an issue checks each editor's trust once, and never for an editor whose edits all come before the App's last full rewrite of the body. Once the App has noted that (below), the note keeps the content dirty even if they become trusted again.
    - **Body markers.** Markers in an issue body are read only while the App made the body's last edit, or nobody edited it. A trusted user's edit leaves the body clean, but it isn't the App's text.
    - **The App's full rewrite.** Only the edits after the App last wrote the whole body count, so a full rewrite cleans a dirty body. Every whole body the App writes, such as a spec (11.1), starts with `<!-- issuedog:rewrite run=<run id> -->` on its first line, with `replaced=<login>` when the body it replaced was dirty. A full rewrite is an entry in the body's `userContentEdits` whose editor is the App and whose text starts with that line. Each entry gives its editor, its time and its `diff`, which is the whole text after the edit, not a diff (section 16). Nobody else can make such an entry: GitHub names the App as the editor only of the App's own edits, nobody can change an entry's text, and the App escapes every `<!--` it didn't write, so only the App puts that line first. Someone with write access can delete an entry's text. A deleted rewrite isn't found, so the edits before it count again. Comments are never rewritten whole, so this applies only to bodies.
    - The daemon finds such edits in the GraphQL `userContentEdits` history. It reads the history only for content whose last edit was sanctioned, since someone else may have edited it before, and not for a body whose last edit is the App's full rewrite, since the body is that edit's text. A history that doesn't reach the last edit counts as dirty.
    - GitHub keeps only the original post and the 99 newest edits (section 16). So the App puts a visible note at the top of dirty content, carrying `<!-- issuedog:dirty by=<login> -->`, and keeps the rest of the text, escaped. The note keeps the content dirty after the history drops the edit. A note that is removed, or names someone else, is put back.
    - **The history's limit after a rewrite.** Nothing keeps the App's full rewrite in the history, though. After about 99 edits by the issue author following it, the history no longer shows the rewrite, so the author's edits count as theirs again, and are sanctioned: once their edits have also taken out the App's note, the body counts as clean. Little follows from it: an untrusted author's edit still gets no revision, the hash still keeps approval blocked (7.4), and the interviewer still reads the body as changed after admission (6.2).
  - **Edits and deletions by untrusted users.** When an untrusted write collaborator edits trusted content, or deletes a comment, section 6.4 says what happens.
  - **Deletions.** A deleted comment's markers are gone with it. The daemon reads deletions from the `CommentDeletedEvent`s on the timeline, which name who deleted a comment, whose it was and when, but not which comment it was (section 16). GitHub records no event when an author deletes their own comment, so such a deletion is seen only as the comment gone from the snapshot, which is read again as the deletion moves the issue's `updated_at` (section 16). A deleted App comment may hide a revision (7.4). When an untrusted write collaborator's edit or deletion of App content hides the markers that set the issue's stage, 6.4 holds the issue at the stage its label shows.
  - **The digest.** Its body and comments are exceptions to the rules above (9.4). The daemon never takes a snapshot of the digest, so it never reads the body for state, only to find the digest and its pin note (9.4).
    - **Its identity marker.** `<!-- issuedog:digest -->` is read even in an edited or dirty body. Only the App can author the issue, the marker holds no state, and the next pass writes the body again anyway.
    - **No `rewrite` marker.** The digest's body is a whole body the App writes, but it doesn't start with a `rewrite` marker. It has no run to name, and its first line is the pin note when there is one (9.4).
    - Its `digest-new` comments count only while they have never been edited, by anyone (9.4). That is stricter than the dirty rule.
- **Labels.** A `stage:*`, `priority:*`, `scope:*`, `type:*` or `approved` label, or a `model:*`, `effort:*`, `verifier-model:*` or `verifier-effort:*` label (3.3), counts only if the issue timeline shows that its most recent `labeled` event came from the App or a trusted user (section 6.1). On a `types: issue-types` repo the same applies to the issue type: it counts only as the most recent issue-type event (`issue_type_added`, `issue_type_changed` or `issue_type_removed`) from the App or a trusted user left it.
  - When an untrusted actor adds or removes one of these labels, the daemon posts a short comment carrying a `revert` marker, then reverts the change.
  - **Issue types.** On a `types: issue-types` repo, an untrusted change of the issue type is reverted the same way, keyed by its issue-type event. The type goes back to the one the newest standing issue-type event left, or is removed if none stands. The standing event is chosen as for a `type:*` label: the newest from the App or a trusted user, but not the App's revert, which only restores the type before it.
    - The timeline gives each issue-type event the type it set and the one it replaced. GitHub's REST description gives a removal's event only `prev_issue_type`. If it ever gives an `issue_type` too, neither its name nor its ID counts as the type the removal left, as a removal leaves no type (#246, section 16). The App sets the type with REST's update of an issue, `type` set to the type's name, or `null` to remove it.
    - **Types by ID.** Two types are the same if their IDs match, where both the issue and the event give one, and else if their names match, ignoring case. An org can rename a type, and the timeline keeps the name its events were written with, but the type keeps its ID. So a renamed type doesn't count as a change.
    - **A renamed type's revert** (#245). GitHub refuses a type by a name the org renamed away, with a 422, so a revert that restores a type names it as the org does now, found by its ID in `GET /orgs/{org}/issue-types` (section 15). Both the comment and the update use that name, and the comment escapes and defuses it, as the org's text. It's a code span fenced by one more backtick than the longest run in the name, padded with a space when the name starts or ends with a backtick or a space, so a backtick in the name stays inside it (#409). A type whose event gives no ID keeps the timeline's name, and a removal needs no name.
      - **The cost.** The org's types are read only for a revert that restores a type, and then once a pass, for every such revert in it. So a pass with none reads nothing, and the next pass reads them again, so it sees a later rename. Stage work's applies read them for themselves, as a run can outlast a rename.
      - **A failed read** writes nothing, so no comment names a type the App can't set, and the untrusted type stays. The issue fails its pass, and the next pass tries again, with one more read. A failed read is kept for the rest of the pass, so it isn't retried there.
      - **A refused read** (#409), a 403, as without Issue Types read (section 15), or a 404, as for an org the App can't see, says nothing of the org's types: a 404 isn't an empty list. So the revert names the type as the timeline does, as before #245, and logs each refused read as a warning. A revert with no rename involved goes through. One whose type the org renamed gets GitHub's 422, and fails as before.
      - **A deleted type.** A type the org no longer lists, as once it deleted it, can't be set back, and neither keeping the untrusted type nor removing it is a revert the App can explain. So nothing is reverted: the untrusted type stays on the issue, and is left out for the type that stands, as an unexplained type is (see Late events), so the pass goes on as if the issue had the type that stands, and starts no type error for the untrusted one. The daemon reports it once as a `kind=typegone` state error, keyed by the revert's key, so the owner hears of it (5.3). It stays so until a trusted user changes the type, which then stands and ends the error. While the error is open, step 1 visits the issue on every pass, which reads the org's types once, and writes nothing.
    - GitHub drops a type change from anyone without push access, with no error. So the daemon checks the type GitHub answers with, and a revert that didn't take is the pass's error, like any failed revert: that issue's visit fails, while the other issues carry on. The next pass tries again, and doesn't post the comment twice.
    - Everything after the label rules in that pass reads the type set back. So an untrusted change starts and ends no type error (5.3), and puts nothing in the digest, unless a deleted type blocks its revert, whose `typegone` error the digest lists (see A deleted type).
    - **Late events.** GitHub writes issue-type events a few seconds late too. A type on the issue that is the one that stands needs nothing, even before the App's own event shows. Any other type that no issue-type event explains yet, anyone's, is unexplained, and is treated as an unexplained label is, timed from when the daemon first finds it, or since the type or the issue-type events last changed:
      - For up to 30 seconds, it holds the issue back.
      - After that, it's left out: the daemon carries on as if the issue had the type that stands, and reads the issue again when the type falls due, or sooner if the issue changes. So a trusted change starts no type error while it waits.
      - Once its event lands, it's judged like any change: a trusted change stands, with its type error if it doesn't fit, and an untrusted one is reverted, keyed by its event.
      - If none lands within 5 minutes, it's reverted the same way, keyed by `issue-type:<type>@<newest issue-type event id, or 0>`, `<type>` being the type's lowercase name, URL-escaped, and empty for a removal. The comment names the type as GitHub shows it, or says the issue had no type.
    - A `types: labels` repo doesn't guard issue types. So a switch to `types: labels` forgets each type that waits, held back or left out (#246): an issue held with its type left out is read once more, for its own type, and isn't read again for it, as nothing there would explain or revert it. The memory of waiting types is in-process, so on a restart none waits.
  - **Unexplained labels.** A pipeline label on the issue that no standing `labeled` event explains is unexplained. A repo label rename makes one, since it adds no event to the issues that carry the label. GitHub also writes label events a second or two late, so the daemon holds such an issue back, acting on nothing of it, for up to 30 seconds from when it first finds one. After that it carries on with the unexplained labels left out of everything it reads and acts on, and reads the issue again when one falls due for removal. A label falls due once it has been unexplained for 5 minutes, or, once the issue has had unexplained labels for 5 minutes, once the label has been there for 30 seconds. A change to the label's events starts its time again. The daemon then posts a comment carrying a `revert` marker and removes the label.
    - A stage label that names the latest transition marker's stage is never unexplained.
    - When the daemon sets a label that's on the issue but unexplained, it removes the label and adds it again, so its own event explains it.
    - A rename can't name who made it, so a trusted rename of a pipeline label is removed too. The owner adds the new name back by hand.
  - When a trusted user changes a stage label by hand, the daemon treats it as an owner override and records a transition marker with `by=<login>` and `event=<timeline event id>`. It does this even if the change is not in the transition table. Setting `stage:held` by hand is an owner hold: its marker also carries `at=<previous stage>` and `reason=owner`. A change to the stage the issue is already at writes no marker, except on a held issue: there, removing `stage:held` and adding it back by hand is a hold of its own, since holds stack (6.4). Its `held → held` marker keeps the first hold's `at` and `origin`.
- **Disagreement.** If the stage label and the latest transition marker disagree and 5.1 does not explain the difference, the daemon reports a state error (5.3), then puts the label back to match the marker.
  - **A dirty spec revision or plan comment** (#315, #447). The interviewer's spec revision comment holds its move to `spec-review` (7.4), and a plan comment its own move to `plan-review` (11.4), so once it's dirty, that move no longer counts, and the label, `stage:spec-review` or `stage:plan-review`, which the App set with it, disagrees with the markers left, which show `clarifying` or `planning`. That's no state error, and the stage doesn't run again: before the label rules act, the daemon records the move again, in an App comment of its own (section 5). At `plan-review` it says there's no clean plan revision to approve, and that `/revise` or any other comment gets a new plan. At `spec-review` it says it's no revision, and the daemon posts the next spec revision after it, as it does after any dirty one (7.4). It does so only on a disagreement that's no override and not the App's own write cut short, while the one stage label is `stage:spec-review` or `stage:plan-review`, the markers left show `clarifying` or `planning`, but not the `clarifying` after a discussion hold, whose moves carry `origin` (6.4), and an App comment after the latest move they show is dirty: the newest such comment keys the record. Its `seen` is the bound of that latest move, so a comment no run read is still a revision request, whether posted during the run or after the dirty comment, but a comment the App 👍'd as an answer before the dirty comment was posted isn't (7.4). The dirty comment's text is never read: the move recorded is the one the label shows, which the label rules have just judged the App's (as 6.4's hidden markers rely on). So it stands in for no other stage's move. An untrusted write collaborator's edit holds the issue instead, as 6.4 says, and an owner's override wins, as ever. A deleted revision comment leaves nothing dirty to point at, so the disagreement stands for it, unless another App comment after the latest move the markers show is dirty, which then keys the record. A record that is made dirty in turn is recorded again. Finding the dirty comment costs no request beyond the visit's own, and the record is one comment; an unchanged pass after it writes nothing, and costs no rate limit.
- **Unfinished writes.** If no stage label has changed since the latest transition marker, other than changes toward it, the disagreement is the App's own write cut short (5.2). The daemon finishes it by setting the labels to match the marker, or, on an open issue whose latest marker is a move to `closed`, by closing the issue with the marker's `reason` (7.2). That isn't a state error.

### 5.2 Idempotency

Every transition goes through one table in code (section 7). Each write is checked first, so a crashed run can be replayed safely:

- **Transitions.** A transition writes in this order: the comment with its marker, the new stage label, removal of any other stage label, then the 👍 for a command comment. A marker with the same key (`cmd`, `run` or `event`) means the transition is written, so a replay only finishes the labels and the 👍. A crash between the marker and the labels leaves an unfinished write, which the next poll finishes (5.1).
- **Commands.** For a command comment, the daemon writes the transition marker with `cmd=<comment id>`, then adds its 👍 reaction. GitHub has no ✅ reaction. On replay, a marker carrying that `cmd` means the command is applied, and only the labels and the 👍 may be missing. `/priority`, `/model` and `/effort` write no marker, so the 👍 is the record. A rejected command gets the App's 👎 first, then the reply (9.2). For a reaction command, the marker carries `cmd=r<reaction id>`. A reaction can't be reacted to, so the transition comment is the acknowledgment, or for a 👍 on a state-error comment, the ack reply (5.3), or for a 👍 on a human task whose check failed, the `reply` (9.3).
- **Created issues.** Every issue the daemon creates has an `origin` marker with a stable item ID, such as `plan=#12 rev=3 item=T4`. Before creating an issue, the daemon looks for one with the same plan and item, whatever its `rev`, and reuses any match. A revised plan keeps the item ID of every child it keeps, changes or drops, gives new items IDs no child or approved item has, and marks each item kept, changed, new or dropped (11.3). The same applies to sub-issue links and dependency links: the daemon reads the current links before adding any. The digest is the one created issue with no `origin` marker. It carries the `digest` marker instead, and the daemon looks for it in the poll before creating one (9.4).
- **Finding a child, without search.** GitHub's search lags behind writes (8.1), so a crash just after a create, then a quick restart, could miss the new issue and file it twice. So the daemon never searches for a plan's children. It reads two consistent lists:
  - the parent's sub-issues, which hold every linked child, open or closed;
  - the repo's issues listed since the parent's first move to `planned` that approved a plan revision, any of them, the REST list the poll uses, which also holds a child filed but not yet linked when a pass stopped, even once the owner has sent the parent back and approved the revision again, and a child someone unlinked by hand, so a revision's planner and its creation find the same children (#362).

  A child is an issue whose `origin` names the parent's plan, matched to its item whatever its `rev`. For an issue the App authored, it's read from the body as listed, unless someone edited that body. The lists name no editor, so the edit history of each body the App filed that gives an `origin` as listed is read, all in one query, and only when there's such a body: every sub-issue's, and each other listed issue's whose `origin` names the parent's plan. An edited body's `origin` is the one 6.4 reads: from the newest version the App wrote that has a whole marker, back to the original post, never one anyone else wrote. So a body someone edited still matches while it keeps the App's marker: reusing an edited child is safer than filing a duplicate. A whole marker someone pasted in, naming another item, counts for nothing, though: matched by it, the issue would leave its own item to be filed again, and the other never filed (#501). With no such version, as when someone deleted their text, the issue is no item's child. A history read here is kept for that edit, so the child's own step 1 doesn't read it again (5.1, 6.4). A sub-issue whose listed body gives no `origin` is read once more, as a snapshot, for the `origin` section 5 reads, so one the App reposted in a comment (6.4) matches too. One the App filed that has no `origin` there, and whose body's markers aren't read, matches by the marker its repost would carry, read from the body's edit history as 6.4 reads it, so from a version the App wrote and never anyone else's: in the pass after an edit removed the marker, the parent's visit can come before the child's step 1 posts the repost, as step 1 visits issues in number order (8.1) (#347). Only then is the history read, or one read for that edit already used: the dirty check's (5.1), or this one's. It's kept, past the App's dirty note on that edit, so the child's step 1 reposts from it, and a closed child, which gets no repost, costs one read, not one each time the parent's children are found. So does a sub-issue a person filed, whose body never gives one, when a clean App comment carries its `origin`, as an adopted story's does (#372): it's its item's child like any other, kept, changed or dropped by a revision (6.4). A marker in a dirty App comment, or in a person's comment or body, counts for nothing (section 5). Each such sub-issue costs that read, and that history read when it's due, which, like the query for edited bodies above, are made only until the parent's record stands (below), and while a revision is planned and checked. An issue that isn't linked yet isn't read so: it was filed in the pass that stopped, and its body is still the App's. So an issue a person filed is a child only once it's a sub-issue of the parent. A sub-issue in another repo, and a pull request, are skipped. If two issues name one item, the linked one wins, or else the lower number, and the other is logged.
- **Creating the children.** For a parent's approved plan revision (7.4), each item's child is written in creation order: plan order, with human tasks last, each after every human task that depends on it (9.3). For each child, each write checked first:
  1. its issue, if none is found, created with its title, body, type and all its labels at once, its stage label included (11.6);
  2. its link under the parent, unless it's a sub-issue of it already;
  3. its first move (7.2), unless it has a clean transition marker of the App's already, other than a hold's and a move back from one to `intake` that isn't an override (5.1): a hold moves every open descendant (7.2), so a child linked but not yet moved when a pass stopped may have been held since. A child still held gets a `held → held` marker with no `reason` instead, keyed as its first move is, which makes its first stage the hold's `at` and `origin` (section 5), so `/resume` takes it there.

  Then, in plan order, each child gets a blocked-by link to the child of each item its "Depends on" names, through the issue dependencies API. Its blocked-by links are read first, and only the missing ones are added. Links someone else added stay. Last comes the `created` record on the parent (section 5), once every write before it is made.
- **A found child keeps its labels.** It's read fresh, and the label rules (5.1) run on it first, so a stage a trusted user set by hand meanwhile is recorded as an override, and the child gets no first move, even when that stage is `intake`, set on a held child. A child found closed gets none either.
- **After the writes.** Each child the daemon writes to skips its stage work that pass, and its step 1 too, unless the digest may list items for it that aren't cached (9.4), and is read again on the next. A failed read or write fails the parent's visit, and the next pass starts again from the reads. A failure no pass gets past instead posts a `children` state error on the parent, once (5.3): plan data that won't read back, as from a plan comment with a second `plan-data` marker of the App's, one of another version, or data that doesn't decode; an item that can't be written as an issue; a revision's kept or changed child that isn't found (below); a revision's plan comment that names no `run`, which its changed children's rewrite would name; or a child GitHub refuses to file, or to link, with a 422, as for an issue type the org doesn't have, or a child that has another parent. Its comment says what failed and that the daemon won't try again until the parent moves. Until the parent's next move, such as `/hold` then `/resume`, a visit reads and writes nothing for creation, and then it starts again from the reads. A plan comment that's gone, dirty or edited since is no such failure: the move into `planned` then approves no revision, so creation writes nothing, and logs that only at debug, as for a plan comment with no `plan-data` marker of the App's. Once a clean record of the approved revision stands, a visit to the parent reads and writes nothing for creation. A record someone else edited is dirty and counts for nothing (5.1): the next visit finds every child, adds nothing twice, and posts a new record.
- **Applying a revision.** When the approved plan revision is a revision (11.3), the same visit applies it to the children, which it finds as above (6.4). Every write is checked first, in this order:
  1. each new item's child, written as above, steps 1 to 3. A kept, changed or dropped item gets no issue, link or first move. So a child that a pass filed under an earlier revision but stopped before linking, which the listing still holds (above), stays unlinked, and a kept one gets no first move, so it doesn't enter the pipeline (6.2): that takes a crash, then a later revision approved before the earlier one's record stands;
  2. each changed item's child, in creation order: its title and whole body rewritten from the revision, unless its `origin` names the revision's `rev` already; then its labels; then its move, keyed `event=p<comment id>` by the parent's comment that holds the revision's move to `planned`. A changed child found closed gets none of these;
  3. in plan order, each new item's child gets the blocked-by links its "Depends on" names, a dependency on a kept or changed item included, as above;
  4. each changed child's blocked-by links to its siblings follow the revision: the missing ones are added, and those to a sibling it no longer depends on are removed. A sibling is the child of any item of the plan, a dropped one's included. Links to any other issue stay, and so do a kept child's links;
  5. each dropped item's child, and every open issue below it, deepest first, is closed as not planned, keyed the same way, and then loses its dependency links (6.4);
  6. last, the revision's `created` record (section 5), listing every child but a dropped item's, in plan order, a kept one by the number it was found under, or `children=none` when none is left.
- **Links a revision removes.** It removes links only from a changed child, as step 4 says, and from an issue it closed itself, its close's marker read back to tell, so a replay after the close still removes them. An issue closed before, by anyone, gets no write, and keeps its links. Each listing is read just before its removals, so a replay removes nothing twice.
- **A child that isn't found.** A child someone unlinked by hand is still listed (above), so a child that isn't found is gone, as when it was deleted or moved to another repo after the revision was checked, and no later pass finds it either. For a kept or changed item, that's a failure no pass gets past (above): the visit stops before any write, and the state error names the item (#362). A dropped item whose child isn't found has nothing to close, so it gets no write. The record leaves it out, and its comment names the item, as one the revision left as it was. The record still stands, so no later pass looks for it again.

### 5.3 State errors

A state error is something the daemon reports to the owner instead of acting on: a transition missing from the table (7.2) other than a rejected command, a stage label that disagreed with its marker (5.1), a type that can't be at the issue's stage (4), a stage run that failed `loop.max_attempts` times in a row (8.3), model and effort labels that give a run no settings (3.3), a question of how an issue was closed that failed on `loop.max_attempts` passes (6.4), a revert of the issue type that would set back a type the org has deleted (5.1), the children of an approved plan that a failure no pass gets past keeps from being created (5.2), an issue the digest's title rule can't judge, as its edit history failed to read on `loop.max_attempts` passes (9.4), or, not built yet, two branches with one issue's prefix, or none for a story whose branch was deleted once a task or bug in it had been `in-progress` (7.5).

- The daemon posts one comment per error, carrying `<!-- issuedog:error kind=<transition|disagreement|type|attempts|labels|closer|typegone|children|digesthistory|branches> key=<key> -->`. The key is the ID of what triggered it: the comment, reaction or timeline event (such as a `labeled` or issue-type event). For a stage run, the key names the stage and its round of input (8.3), so the stage doesn't run again until the issue moves or gets new input. A run's missing transition also keys on the issue's type and parent. For model and effort labels, the key is the timeline event of the newest change to any of the four kinds that stands (5.1): the App's or a trusted user's, but not an untrusted change or the App's revert of one. So the same bad labels set again after a fix are reported again, and an untrusted change posts nothing. For a type, the key is the type change that stands (see Types). For a closer question, the key is the `closed` event's ID. For children, the key is the ID of the parent's comment holding its latest move, the one into `planned`, so each stay there reports it once. For a deleted type, the key is the key of the revert it blocks (5.1): the untrusted change's issue-type event, or `issue-type:<type>@<id>` for a type no event explains, so a new change is a new occurrence. For the digest's title rule, the key is the hash of the issue's body as listed, as a revision records one (7.4), so an edit of the body is a new occurrence. For branches, the key is the names of the issue's branches with its prefix, sorted, each percent-encoded as a `digest-new` marker's keys are (9.4), then joined by commas, or `none` when it has none, so the same branches are reported once, and a different set is a new occurrence. The same set again, once the daemon has seen the set change since its newest comment for that set, is a new occurrence too, so a 👍 on that comment doesn't cover it: its key is the names as above, then `:`, which no branch name can hold, and that comment's ID. Otherwise the key is that newest comment's, so a set that comes back after a change the daemon didn't see, between two passes or before a restart, reuses it. Before posting, the daemon looks for a comment with that key and kind and reuses it, so the same cause is posted once across polls and restarts, and a new occurrence gets a new key.
- For a stage run's attempt cap, the comment also says why the last attempt failed, for every stage (8.3).
  - **What it quotes.** Only a cause the daemon wrote itself, told by its type, not its text (#320): a check's broken rules, each with its detail, such as `rule scope: T3's scope "web" isn't on the list` (11.3); a result's own failure, such as claude's subtype, `run failed with subtype "error_max_turns"`, whether claude exited 0 or not, but only a subtype claude ends a failed run with: `error_max_turns`, `error_max_budget_usd`, `error_during_execution` or `error_max_structured_output_retries`; a timeout, named from `stages.timeouts`, such as `run timed out after 10m0s`; and the daemon's other failures (#441): no valid result after a restart (8.2), an issue its stage no longer runs on, read again, a move that doesn't fit, and output that doesn't decode. The quote is fenced and escaped, since it may quote the agent's output, and cut to 1,000 characters.
  - **What it doesn't.** Any other cause, such as the runner's error, which may name a local path under `/work` or `/state`, an apply's failure, which may quote GitHub's error text, a result that fails the stage's schema, whose error names the daemon's working directory, or claude's own text: its result's text, or a type or subtype it isn't known to write. The comment then says only that the last attempt failed and that the daemon's log says why. The daemon logs the full cause once, as the attempt fails, so the last failure to apply a result isn't the pass's error too.
  - **Every state error.** The closer, digest-history and children errors, the others that name a failure, follow the same rule. Their causes are GitHub's, or for children the planner's too, so none quotes one (see below, and 5.2).
  - **After a restart.** The lease keeps what the comment quotes, or that the cause is in the log (8.2), so the comment still names it after a restart. It keeps that under a key new with #320, so a lease written before, which held the whole cause, is read as naming none.
- For a disagreement, the comment is posted before the label is put back, so a crash between the two can't lose the report.
- For model and effort labels, the daemon reads the issue again first. It posts nothing if the issue closed, changed stage, has no stage work pending, or has other model and effort labels than it had in step 1 (8.1), since the change may fix them.
- A trusted 👍 on the comment acknowledges the error. The daemon records it by replying with `<!-- issuedog:error kind=<kind> key=<key> ack=r<reaction id> -->`, never posts that kind and key again, and the error stops counting toward assignment (9.6) and leaves the digest (9.4). Removing the 👍 later changes nothing.
  - **Which 👍.** The earliest 👍 by a trusted user (6.1), not a bot, on any clean comment carrying the error. A race may have posted it twice, and a 👍 on either copy counts. The reply reads "Acknowledged, by `<login>`'s 👍.", with the login defused (section 9).
  - **The reply is the record.** A replay finds it, so it is posted once. A 👍 on a comment that carries several open errors gets one reply for each.
  - **Kind.** An ack covers only the kind and key it names. An ack with no `kind`, from before acks named one, covers its key for every kind. Comment IDs and timeline event IDs come from separate sequences, so without the kind an ack of one error could silence a later, different error with the same number.
  - **Only open errors.** A 👍 on an error that has ended, acknowledged or with its cause gone, is ignored: its reactions aren't read. An error whose only copy is in an issue body can't be acknowledged, but the App never posts one there.
  - A 👍 doesn't change the issue's `updated_at`, so step 1 visits an issue with an open error on every pass (8.1).
- Otherwise the error ends when its cause is gone. A type mismatch ends when the type is no longer the cause, or a newer type change stands (see Types). A missing transition, a disagreement or a children error ends at the issue's next valid transition, including a trusted user's manual stage change (5.1). A stage run's error ends when the issue moves or gets new input. A labels error ends at the next change to the labels that stands; if they still give no settings, that is a new occurrence. A branches error ends when the issue's set of branches with its prefix changes; if the new set is still two or more, or none for a story whose branch was deleted once a task or bug in it had been `in-progress` (7.5), that is a new occurrence. A closer error ends once GitHub answers its question, or its close is no longer the one to judge. A typegone error ends once no revert with its key is blocked any more, as when a trusted user changes the type.
  - **Open.** An error is open until it is acknowledged or its cause is gone. One on a closed issue is never open, though the digest lists a closed issue's `closer` error (see Closer questions). For each kind, the cause is gone:
    - `transition`, `disagreement` and `children`: at a transition marker in a later comment than the error's. A run's missing transition also ends when its key changes: the issue moves, gets new input, or changes type or parent.
    - `attempts`: when its key changes, as the issue moves or gets new input.
    - `labels`: when the change to the model and effort labels that stands changes.
    - `type`: when the type is no longer the cause, or a newer type change stands. If the type is still the cause, it's a new occurrence with a new key.
    - `branches`: when its key changes, as the issue's set of branches with its prefix changes. So going from three branches to two ends one error and posts another. The issue's runs wait while it has two or more, or none for a story whose branch was deleted once a task or bug in it had been `in-progress` (7.5), acknowledged or not.
    - `closer`: when GitHub answers the question of how its close was made (6.4), or when step 1 no longer asks it, as the close is no longer the one to judge: it's before the issue's floor (6.4, Which acts count), as after a move out of `held`, or a marker records it, or the issue has no floor. The daemon knows an answer only while it runs, so after a restart the error stays open until the next answer, which it asks for on every pass, or until step 1 no longer asks.
    - `typegone`: when the label rules no longer find a revert with its key that a deleted type blocks (5.1), as once a trusted user changes the type, which then stands, or the untrusted type goes. An untrusted change to another type is a new occurrence, with its own key, reverted if it can be, or reported again if not.
    - `digesthistory`: once the title rule judges the issue (9.4). Step 1 visits only an issue it has judged, so the error is never open there.
    - any other kind: never, so only an ack ends it.
- **Deleted types.** A `kind=typegone` error (#409) says the issue's type wasn't reverted, as the org no longer has the type that stands, and that the daemon acts on that type until a trusted user changes the type. The types' names and the login are code spans, as the org's and the user's text (5.1). Why a state error and not a digest item of its own: it's something the daemon reports instead of acting on, the revert, it has a stable key, and its cause is read on every pass, so it ends when its cause is gone, as a `type` error does, while an ack lets the owner silence it. As a state error, it's also posted on the issue, counts toward assignment and is listed and announced in the digest (9.4, 9.6). It doesn't hold back the issue's stage work, which acts on the type that stands.
- **The digest's title rule.** A `kind=digesthistory` error (#305) says that the daemon can't tell whether the issue is the digest, as reading its edit history failed on `loop.max_attempts` passes of a start in a row (9.4), so it keeps the issue out of the pipeline and creates no digest, which may leave the repo with none until a read works or the owner acts. It doesn't quote the last read's error, which GitHub wrote (#320): it says the daemon's log has it, where each failed read is logged in full. Before posting, the daemon looks for it in the comments the poll lists, which on a start are all of them, so a restart doesn't post it again. A post that finds the issue gone, deleted (404 or 410) or transferred, lets the issue go, so a digest can be created. A held issue has no snapshot, so the post is how a transfer is found: GitHub answers a POST about a transferred issue with a 301, which Go follows with a GET in the new repo, so a post answered from anywhere but this repo's path posted nothing, and the issue was transferred, as for the digest's own writes. No step 1 visits the issue while it's held, so a 👍 on the error isn't read, nobody is assigned for it (9.6), and a digest, if there is one, doesn't list it.
- **Closer questions.** A `kind=closer` error reports a question of how a close was made, GraphQL's `ClosedEvent.closer`, that failed with an error under `node` other than `FORBIDDEN` or `NOT_FOUND` on `loop.max_attempts` passes, with no answer between (6.4).
  - **The comment.** It names the close's actor. It doesn't quote the question's last error, which GitHub wrote (#320): it says the daemon's log has it, where the daemon logs it in full as it posts the comment. On a closed issue, it also says that a 👍 on it isn't read, and that reopening the issue and closing it again settles it, as a trusted user's close stands with no question.
  - **On an open issue,** for step 1's close trigger, it's an open error like any other: a trusted 👍 acknowledges it, it counts toward assignment and the digest lists it. After a restart it stands at once, from its comment.
  - **On a closed issue,** whose close stays unjudged, no step 1 visits the issue, so a 👍 on it isn't read and nobody is assigned for it (9.6). The digest still lists it, from the daemon's memory, until GitHub answers, a newer close is the one to judge, or the issue is reopened. While it stands, and the listing still shows the `closed_at` and the stage labels the issue had, a pass asks only the question, and reads nothing of the issue, its timeline included. A restart doesn't drop it from the digest: the first time the question fails so in a run, the daemon reads the issue once, and if the issue carries the error, it stands at once and isn't posted again. If not, the issue is read again only when the question has failed on `loop.max_attempts` passes, to post the error.
- **Types.** A type that can't be at the issue's stage is a `kind=type` error (section 4).
  - **What fits.** `intake`, `clarifying` and `held` fit every type the pipeline knows, untyped included. Any other stage, closed included, fits a class when a 7.2 row for that class has it as its from or to. The "any open" rows don't count. A type the pipeline doesn't know, such as `type:feature`, fits only `intake`.
  - **The cause.** The type is the cause when the pipeline doesn't know it, at any stage: even at `intake`, which it fits, since the table never moves it on. A known type is the cause only when no issue of that type fits the stage, whatever its parent, origin or past. So an owner's story at `spec-review` that gains a parent is no type error. A move the table lacks there is a `kind=transition` error, as before.
  - **The key.** The type change that stands: the newest `labeled` or `unlabeled` event of a `type:*` label that stands (5.1), or on a `types: issue-types` repo, the newest issue-type event that stands (5.1). On a `types: labels` repo, an issue that also has a GitHub issue type takes its type from the issue type, but its key from the labels. With no type change standing, nothing keys a type error.
  - **When.** Step 1 checks the type right after the label rules and the dirty notes (8.1), on an open issue with a transition marker, or at intake with none, once a type error has been reported on the issue (see Holding back). A type that is the cause, with a key, gets one error per key, and the issue stays where it is. The interviewer sets only types the pipeline knows, and only at `clarifying`, which fits every such type, so it never causes one.
  - **Unknown types and missing moves.** A move the table lacks because the type is the cause, such as an unknown type's move out of intake (6.2), reports the type error, not `kind=transition`. With no type change standing, it's a `kind=transition` error, keyed by its trigger.
  - **Holding back.** While a type error has been reported on the issue, acknowledged or not, and the type is still the cause, no stage runs on the issue, triage included (8.3). That holds for any type error reported on it, not only the one for the type change that stands. A move the type blocks is logged, not posted as a second error. So a 👍 acknowledges a type error but doesn't let the stage run again. A change to a type that can be at the stage, or a trusted user's manual move to a stage the type can be at, ends the hold.
    - A newer type change that is still the cause is a new occurrence, which step 1 reports before any stage runs, at intake too. So at intake, a change from one unknown type to another gives triage no run: triage waits until the type is one the pipeline knows.
    - A trusted 👍 on a revision, given while a type error holds the approval back, still counts once the type is fixed. The issue then moves on that 👍, as long as the revision is still the latest and the body still matches its hash (7.4).
- A command that doesn't apply at the issue's stage isn't a state error. The rejection reply (9.2) is enough, and nobody is assigned for it.

## 6. Trust model

### 6.1 Trusted people

A GitHub user is trusted when either holds:

1. They are an owner of the CODEOWNERS file itself, under the CODEOWNERS rules as read from `main` (section 3.4). These are the people who already control trust.
   - GitHub reads the first file it finds, in this order: `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`. The daemon uses the same order.
   - Team entries (`@org/team`) are resolved through the API. Email entries are ignored and logged.
   - GitHub ignores code owners without write access, and so does the daemon.
2. No CODEOWNERS file exists on `main`, and the user's `role_name` is `write`, `maintain` or `admin` (`GET /repos/{owner}/{repo}/collaborators/{user}/permission`).

The issuedog App, and any other bot account, is never trusted.

### 6.2 What the daemon acts on

The App creates an issue in the pipeline when its `origin` marker points to an approved plan revision, to a story-verifier run, or to a failure on a story branch (7.5, not built yet). Issues the App creates in another repo (section 14) carry no such marker, so they need `approved`.

A child created from a plan enters the pipeline by its first move, `intake →` its first stage, or, for a child held before it, a `held → held` marker with no `reason` that makes its first stage the hold's `at` and `origin` (5.2), in an App comment on the child keyed `event=p<comment id>`, the ID of the parent's comment that holds its move to `planned` (7.2, 5.2). An issue's stage comes from its transition markers, so without that move a new child would read as at `intake` whatever its label. With it, the label rules, the replay checks and the stages' "on entry" rules read the child as they read any issue.

Every other issue enters by one move, `intake → clarifying`, on the "issue is trusted" row (7.2). The ways in, with the key the move's marker carries (section 5):

- It has `stage:intake`, set by a trusted user or the App, and a trusted author. The key is `event=<the labeled event of stage:intake that stands>`.
- A trusted user added `approved` (checked on the timeline), and the issue is at `stage:intake` or has no stage label. The key is `event=<that labeled event>`.
- A triage run admits it (below). The key is `run=<run id>`.
- A trusted user posts `/track` at intake (`cmd=<comment id>`), or reacts 👍 to a flag that recommends handling it (`cmd=r<reaction id>`).

If the event already keys a transition, as when an override brought the issue back to intake, the move is keyed `event=<the ID of the comment holding that transition>` instead. Every move into the pipeline says in its comment why the issue is in. For a bug or a task, and a story with a parent, it also says that the issue waits at `clarifying` (7.2).

An untrusted author's issue enters only by `approved`, `/track` or a trusted 👍 on a flag. Each of these is the approval. A trusted user's `stage:intake` alone doesn't let it in.

An issue the table can't move, such as an approved issue of a type the pipeline doesn't know, stays at intake and gets one state error (5.3):

- When a type change stands, the type is the cause, so it is a `kind=type` error, keyed by that change. Triage doesn't run on the issue while a type error has been reported on it and the type is still the cause, even once a trusted 👍 acknowledges it. A change to another unknown type is a new `kind=type` error, which step 1 reports, and triage still doesn't run (5.3).
- Otherwise, as for a GitHub issue type on a `types: labels` repo, it is a `kind=transition` error, keyed by the admitting event, comment or reaction. Triage doesn't run on the issue while that error stands.

Only these move it on: a trusted 👍 on a `kind=transition` error, which lets triage run again, a stage label, `approved` or `/track`, or a fix to its type while `approved`, or a trusted author's `stage:intake`, still stands.

**Triage.** An open issue with no stage label (none left out, 5.1), no transition marker, no triage marker that counts, no `approved` label, no standing admission error, and no type error reported on it while the type is still the cause (5.3), is classified once by a short triage run. That covers the issues already open when the daemon first runs on a repo, and each new one. Closed issues and pull requests aren't triaged, and an issue with a stage label is adopted by the label rules (5.1) instead. Nor is the digest, which is never in the pipeline (9.4).

- **When.** Triage runs only in a pass where no other stage ran, on the newest such issue first, one per pass (8.1). Like every stage run, it runs under the usage gate and the attempt cap (8.3). It uses the interviewer's `stages` settings (section 13).
- **Output.** `verdict` (`handle` or `leave`), `sure` (true or false), `reason` and `summary`, each one line. The daemon decides:
  - A sure `handle` on a trusted author's issue admits it, keyed `run=<run id>`.
  - A sure `leave` records "left": a short comment with the reason, saying that a code owner can `/track` it, carrying `<!-- issuedog:triage verdict=leave run=<run id> -->`. The issue isn't classified again.
  - Anything else posts a flag, with the verdict as the recommendation. That covers every verdict that isn't sure, and any `handle` on an untrusted author's issue, which triage never admits.
  - Its check (8.2) fails the output unless each text it could render, the admission, the flag and the "left" comment, fits GitHub's 65,536-character limit with 1,024 to spare.
- **A flag** is one App comment in the 9.1 style, carrying `<!-- issuedog:triage verdict=ask run=<run id> recommend=<verdict> -->`:

  ```
  ### Should issuedog handle #N?

  **1. <summary>** Blocks: #N
     a. Handle it (recommended): <reason>
     b. Leave it

  React 👍 to take the recommendation, or post `/track` or `/ignore`.

  cc @<notify>
  ```

  With a `leave` recommendation, "Leave it" is option a.
- **During the run.** If a trusted user adds `approved`, or a code owner's answer records a triage marker, the result writes nothing, and the run isn't counted. A triage marker in dirty content doesn't count, so that issue is classified again.

**Answering a flag.** Each answer must come from a trusted user, in a clean comment or a 👍:

- The earliest trusted 👍 on the latest flag takes its recommendation, keyed `cmd=r<reaction id>`. A `handle` admits the issue, an untrusted author's too. A `leave` records "left" with `<!-- issuedog:triage verdict=leave cmd=r<reaction id> -->`, unless the issue is in the pipeline or has `approved`. With `approved`, no "left" comment is written, and the move into the pipeline answers the flag.
- A 👍 on an older flag, an untrusted 👍 and the App's 👍 are ignored. So are 👍s on a flag a later move answered, as when an override brought the issue back to intake, or after a hold and `/resume`. Only `/track` or `approved` admit such an issue.
- `/track` admits the issue at intake, keyed `cmd=<comment id>`, whether it is flagged, left or never triaged.
- `/ignore` records "left", keyed `cmd=<comment id>`. It's rejected on an issue in the pipeline, meaning one with a stage label, a left-out one included, or a transition marker, and on one already left. On an issue with `approved` it's rejected too, since `approved` brings the issue into the pipeline instead.

**The `triage:*` labels.** `triage:ask` and `triage:left` show the two waiting states in GitHub's filters. They follow the latest triage marker: `triage:ask` for a flag, `triage:left` for "left", and neither once the issue is in the pipeline. The App sets and removes them, and on its next visit undoes anyone else's change, with no comment. The daemon never reads them as state, so the label rules (5.1) don't guard them.

**Admission time.** An issue's admission time is the earliest of:

- the earliest `labeled` event of `approved` by a trusted user, or of a stage label past intake, other than `held`, by a trusted user or the App;
- the time of the clean, trusted `/track` comment, or the trusted 👍 on a clean flag, that a clean App move out of intake names in its `cmd`.

Dirtying or deleting the move or the command falls back to the label's time. With no admission found, every edit counts as after it. Times are to the second, so a change in the admission's second counts as after it.

**Edits after admission.** An approval approves what the approver read, not what the author writes later. On an untrusted author's issue, a title or body the author changed after the admission is untrusted input for the interviewer and the planner: it goes in `untrusted.md` under a heading that says so, and `issue.md` says it's there instead of showing it.

- The body counts as changed after admission when its last edit is at or after the admission, by anyone but the App. GitHub dates only the last edit, so any later edit counts.
- The title counts as changed after admission when its latest rename is at or after the admission and by someone untrusted. A trusted user's later rename makes the title theirs.

**The planner's other trusted text** (#312). The admission check covers only an untrusted author's issue, so for the planner:

- **A rename by someone untrusted.** An issue or a parent that the App or a trusted author filed, and that someone untrusted renamed since, such as a write collaborator, shows its title as of its last trusted change: the newest rename by the App or a trusted user, or with none, the title it was filed with. The rename holds the issue (6.4), but a `/resume` doesn't make the title trusted. A later rename by the App or a trusted user does. The new title goes in `untrusted.md`. The interviewer shows the issue's own title so too, as its run after the hold's `/resume` would otherwise trust the rename.
- **A parent never admitted.** A parent by an untrusted author that never entered the pipeline, as when the owner put a story under it, has neither its title nor its body shown: both go in `untrusted.md`, as triage gets an untrusted author's whole title and body.
- **Sub-issues.** The titles of the sub-issues `children.md` and `parent.md` list are data, not instructions, as the preamble says: anyone who can write can rename an issue, and the owner can link an untrusted author's issue. Their stages are read from their markers, never their labels, and their types from the `type:` labels that stand, never an untrusted one, as is the parent's (section 12).

**Untrusted input.** Only comments and reactions by trusted users count as answers, approvals or commands. A comment a trusted user approved (6.4) counts as their input, never as a command. Agents receive other text only in a separate `untrusted.md` context file (section 12). Each piece is fenced under a heading that says it is untrusted data, not instructions. That file holds:

- comments by untrusted users and other bots;
- dirty comments by anyone, and a dirty body (5.1);
- for the interviewer and the planner, an untrusted author's title or body changed after admission, and a title someone untrusted renamed, and for the planner, its parent's too, and a parent's whole title and body when it was never admitted;
- for triage, an untrusted author's whole title and body.

The interviewer and the planner get `untrusted.md` only on epics and stories. On an untyped issue, a bug or a task, that text is in no file. Triage is the exception: a triage run gets `untrusted.md` on any issue, so it can classify an untrusted author's issue. Its result can only flag such an issue or leave it, never admit it.

A command counts once. If its comment is edited after the daemon applied it (its 👍), the edit is ignored and the bot replies asking for a new comment, except as 9.2 says for answers: an applied command that wrote no marker, such as `/priority`, edited into plain text at `clarifying` or `planning`, in the current round, becomes an answer, with no reply. A rejected command (its 👎) gets no new reply when edited. If it is edited before the daemon processes it, the daemon reads the latest text. Section 9.2 has the details, including edited answers.

### 6.3 Protecting the trust inputs

- CODEOWNERS lists itself (`/.github/CODEOWNERS @owner`).
- A ruleset requires code-owner review on `main` (section 15).
- Protected paths are:
  - CODEOWNERS in any of its three locations
  - `.github/**`
  - `.issuedog/**`
  - the agent-config paths: `.claude/**`, `**/CLAUDE.md`, `**/CLAUDE.local.md` and `.mcp.json`
  - anything in `verify.protected_paths`

  Any diff that touches one fails deterministic verification (section 10.1) and needs a human-authored change instead. The owner merges those through the admin bypass in section 15.

### 6.4 Discussion holds

Write collaborators who aren't trusted users (6.1) can take part in an issue, but they can't move it. Any of these on an issue in the pipeline (6.2) puts that issue, and only that issue, on hold:

- a new comment by such a user
- their edit to a comment or body written by the App or a trusted user, seen in its GraphQL `userContentEdits`, or to their own comment at or after a trusted 👍 approved it. Once the App has rewritten a body whole, the body is the App's (5.1), so the issue author's own edit after that is one too
- their deletion of a comment written by the App, a trusted user or someone GitHub doesn't name, seen as a `CommentDeletedEvent` on the issue timeline. Deleting their own comment, or another untrusted user's, changes nothing anyone trusted wrote, so it holds nothing. GitHub records no event for deleting one's own comment anyway (section 16)
- their renaming of the issue
- their close of the issue (see Closes and reopens)

Each of these is a trigger. Comments from people without write access hold nothing. They reach agents only as untrusted input (6.2).

**Who holds an issue.** A write collaborator who isn't trusted has the `role_name` `write`, `maintain` or `admin` (6.1), and isn't trusted under CODEOWNERS. Without a CODEOWNERS file every such user is trusted, so nothing holds. One permission request answers both whether a user is trusted and whether they're such a writer, and a visit asks about each login once.
- The daemon asks only about who made an open act that no marker records (see Keys and records), and never about a bot, the App included, someone GitHub doesn't name, or someone every `authorAssociation` the snapshot gives them, on the issue or its comments, says has no access to the repo: `CONTRIBUTOR`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN` or `NONE`. So a stranger's comment costs no request.
- A question of trust alone, such as who wrote the content an edit changed, who wrote a deleted comment, or who gave a 👍, asks only whether the user is trusted, which needs no request for a login CODEOWNERS doesn't name.
- A login GitHub answers with no permission record, a 404, such as a removed collaborator or a deleted account, is remembered in memory as no writer, so an unchanged pass doesn't ask again. The memory ends an hour later, when the issues it was asked for are read again; at once when a snapshot shows the login as the owner, a member or a collaborator, as a re-added writer's comment does; or on a restart. So a re-added writer's act other than a comment holds nothing for up to an hour. While an open act of theirs stays on an issue that is visited, that costs three requests an hour that no ETag saves: the snapshot's GraphQL query, its parent's GET and the permission 404.

**Which acts count.** An act counts only after the issue's floor: its first transition marker, so old comments don't hold issues on the day this ships, or its latest move out of `held` or `ended reason=discussion` record with a `resolved` time, whichever is latest, as each of those resolves every trigger before it.
- A comment counts when it's above the comment holding the floor's marker, and any other act when it's at or after that marker's time. Times are to the second, so an act in the marker's second counts.
- A marker that records an act made before it bounds the triggers from that act's time instead, where that time is known, and comments are then compared by when they were posted, so an act between the two still counts. For a stage label set by hand, the time is the label's event, not the App's record of it, and that includes a first marker that records a label set by hand. For a move out of `held` or an `ended` record, it is its `resolved` time, or the time of the `/resume` on the issue that its `cmd` names.
- An issue with no marker left, but with a stage label past `intake`, has had its markers hidden by an edit or a deletion (see While held), so every act counts, failing closed.

**Keys and records.** Each trigger is keyed by what it was, in the style of `cmd=r<reaction id>`: `c<comment id>` for a comment; `e<content id>-<Unix seconds>` for an edit, with the comment's ID, or 0 for the issue body, and the edit's time, so each edit is a trigger of its own; `d<node id>` for a deletion, the `CommentDeletedEvent`'s; and the timeline event's ID for a rename or a close.
- A trigger is recorded once a clean App marker carries its key: the hold's transition marker, `event=<key>` with `reason=discussion`, or a notice's `notice key=<key>` (section 5). A second pass then writes nothing for it, and no key gets a second notice.
- A recorded trigger stays a trigger, known from its record, whatever its content shows later. A later edit of the content, by its writer, another writer or a bot, its deletion, or its maker's loss of access doesn't undo it: it was judged when the record was written.
- A comment trigger on an issue that is already held has no record at all. It's known by being open.

**Closes and reopens.** Closes and reopens are separate. Only a trusted user, the App or a merged pull request may close an issue in the pipeline, and only a trusted user may reopen one. The newest `closed` or `reopened` event on the timeline decides:
- An accepted close stands, and the App sets the closed stage it names in place of the issue's other stage labels, with no comment and no marker: `stage:completed` for a close as completed or by a merged pull request, and `stage:discarded` for a close as not planned or as a duplicate. A trusted user's choice of the other closed stage by hand stands too. Section 8.1 says when a closed issue is judged.
- Any other close is reverted at once: the daemon reopens the issue and leaves its stage label alone, so a parent never closes on an untrusted close (7.3). The close holds the issue only if the closer is a write collaborator: then it's a trigger, and step 1 holds the reopened issue for it, with its notice. Anyone else's close gets a short comment carrying a `revert` marker keyed by its event, then the reopen.
- An untrusted reopen of an issue with a closed stage is reverted too, and holds nothing: a `revert` comment keyed by its event, then a close with the state reason of the close it undid, as GraphQL's `ClosedEvent.stateReason` gives it, or else the closed stage's. If that question fails, nothing is written, and the next pass asks again, so one passing failure doesn't change the reason. Once it has failed on two passes, with no answer between, the close uses the closed stage's reason, and the failure is logged, so the close waits on it for one pass at most. The daemon counts the failures in memory, so a restart starts again from none. The label stays.
- A trusted reopen moves the issue to `held`, `closed → held`, at the stage the latest transition marker shows, which an accepted close left as it was, and the closed stage goes. When that marker is the App's own move to `closed` (7.2), the hold is at the stage the move came from, `needs-human` for a human task. When it came from the `clarifying` after a discussion hold, as a dropped child's close may (see Leaving the hold), the hold carries the `origin` of the move before the close, which the close itself carries none of (section 5). It's an owner hold with no `cmd` (section 5), which `/resume` on the issue ends. On an issue that was held when it closed, the first hold's `at` and `origin` stay.
- A merge is told by GraphQL's `ClosedEvent.closer`, asked by the `closed` event's node ID: a merged pull request whose base is this repo's default branch, or a commit in this repo. A closer in another repo is no merge. The REST `closed` event of a merge names the merger as its actor, and gives no `state_reason` or `commit_id` (section 16). The closer is asked only for a close nobody trusted made, and for the close an untrusted reopen undid, for its `stateReason` (above), once per event while the daemon runs. A closer GitHub won't show the App, such as a project's workflow on a personal account or a commit in a private repo, is no merge, so the close counts as its actor's, and is reverted unless they're trusted. Only a `FORBIDDEN` or `NOT_FOUND` error under `node` says so. Any other failure of that query, an error of another type or of none under `node` included, is logged as the pass's error, but fails only that issue for the pass, its close's judging (8.1) or its step 1, while other issues carry on, and the next pass asks again. For the close a reopen undid, it delays the close again by one pass at most (above).
  - **A question that keeps failing.** An error of another type or of none under `node` is about that close, and may last, as for a type GitHub uses that isn't confirmed yet (section 16). Once the question has failed so on `loop.max_attempts` passes, with no answer between, the issue gets one state error, `kind=closer` (5.3), pointing to the daemon's log for the error, and that failure is no longer the pass's error. A closed issue's close stays unjudged, with its stage label as it is, and an open issue's close is no trigger, until GitHub answers. The question is still asked once a pass, and an answer judges the close and ends the error. Each pass then writes nothing. On an open issue, it costs what step 1's visit cost before the error, the question included. On a closed issue, it costs the question alone, with no timeline read, until the listing shows another `closed_at` or other stage labels (5.3).
  - Any other failure, a failed request, an error on the repository, or one GraphQL lists with no path, as when it fails as a whole, says nothing of that close, as in an outage. It is the pass's error on every pass, with no state error.
  - The daemon counts the failed passes in memory, once a pass however often the question is asked, so a restart starts again from none.
- **Merges into a story branch.** A merged pull request whose base is any other branch, such as a task's PR into its story branch (7.5), is no merge here. Such a merge closes nothing: GitHub's closing keywords act only on a merge into the default branch, and such a PR names its task without one (11.5). So the App closes the task itself, by its move to `closed` (7.2), after its own merge or a trusted merger's (7.5). That close is the App's, so it's accepted without asking for a closer. A story's PR targets `main`, so the merge that closes the story is told as above. Section 16 has the live check.
- `stage:completed` and `stage:discarded` are valid only on a closed issue. On an open issue, a trusted user's is a disagreement (5.3), and the label is put back.

The digest isn't in the pipeline and is never held by its own close or reopen: 9.4 says how they are handled.

**While held.**
- The daemon sets `stage:held` with a transition marker carrying `reason=discussion` and two stages: `at`, where the issue was, and `origin`, where it was before the first discussion hold. Every marker written in the `clarifying` that follows a hold, including question rounds and any later hold of either kind, carries `origin` forward, but for the moves out of it that section 5 names, so back-and-forth discussion never loses it. `/resume` restores `at`. "Nothing changed" returns to `origin`. The hold is keyed by the oldest open trigger that no transition marker carries as its `event`, even one a notice records, and carries `seen`, the round's bound from before the hold (section 5).
- **Notices.** For anything other than a comment it also posts a notice naming it, since there is nothing else to react to. The hold's own comment carries its trigger's notice marker, when that trigger isn't a comment, and each later trigger that isn't a comment gets an App comment of its own carrying `notice key=<its key>`. The hold's comment and each notice end in the `cc` line (section 9), so the digest doesn't mention them again (9.4). No notice is posted for a trigger once an App comment posted at or after it was made dirty, or an App comment, or one GitHub names no author of, was deleted at or after it: that may have been its notice, so it never gets a second one (see Resolving).
- **Hidden markers.** An untrusted write collaborator's edit or deletion of the App's content, or of a comment GitHub names no author of, may hide the markers that set the issue's stage (5.1), and the label rules would then put the label back to the stage the markers left show. Instead, before the label rules act, the daemon holds the issue for that trigger, at the stage its one stage label shows, which the App set with its last move, and posts no disagreement. On an issue that was held, the hold is at the stage the markers left show, and it also records the hidden hold again as an owner hold with no `cmd` (section 5): whose hold it was isn't known, so only `/resume` on the issue itself ends it. Nothing is held so when an override stands, since the owner's change wins, or when the App's own write was cut short (5.1).
- Holds stack. Any hold on an issue that is already held, whether by `/hold`, by hand (5.1) or for discussion, keeps the stage recorded by the first hold. Only the parent's revision, or a held child's first move (5.2), changes that stage, by a marker that isn't a hold (see Leaving the hold). The issue leaves `held` only when every hold on it has ended. A discussion hold ends when resolved, or by `/resume` on the issue itself. An owner hold ends by a `/resume` posted after its `/hold`, on the issue itself, on the issue where its `/hold` was posted, or on any issue between the two, and by no other `/resume` (the owner's choice (b) on #188). Loop step 1 (8.1) visits issues in number order, so a `/hold` or `/resume` waits, neither applied nor rejected, while a `/hold` or `/resume` posted before it on an open ancestor in this repo isn't processed yet (9.2). One on the digest, which no pass visits (9.4), is never processed, so nothing waits for it. The daemon reads both issues again on the next pass, so the ancestor's is handled then if it wasn't in this one, and the waiting one once the ancestor's is (#243). So a `/hold` on an ancestor, then a `/resume` on a descendant numbered below it, in one poll, leave the descendant and the issues below it released, as if handled in the order posted. A command on an ancestor posted after one on a descendant doesn't wait for it, and may be handled first: a `/resume` doesn't end a `/hold` on its path posted after it, even when that `/hold` was handled first (#205), and never ends a `/hold` posted below it, so for two such commands in one poll that comes out as the order posted would. Three or more in one poll can still come out otherwise (section 16). A `/hold` on an issue that is already held writes no marker there, but still holds it until that rule ends it, whatever held the issue when the `/hold` was posted: a parent's `/resume` never ends a `/hold` posted on its child, so only `/resume` on the child ends the child's own `/hold`. A `/hold` counts by the App's record that it applied it, so a write collaborator's edit of its comment doesn't end it. A `/hold` whose comment is deleted counts as posted on the issue that an `ended` record's `heldon=` names for it (see Leaving the hold), or else on the farthest issue with its marker. A `/hold` that neither a marker nor such a record names is known only by its comment, so it ends when a trusted user deletes that comment, its author included: a trusted user's deletion holds nothing, and GitHub records no event when an author deletes their own comment (section 16). A hold a `/resume` ended stays ended, whatever happens to its comment after: when the issue stays held for another reason, the App records the end with `ended reason=owner` (section 5). A comment that an untrusted write collaborator deletes on an ancestor during the hold, written by a trusted user or by someone GitHub doesn't name, may have been a `/hold` that wrote no marker, so it counts as one posted on that ancestor, which only a `/resume` posted after the deletion ends. That holds on the issue itself too: its own `/resume` ends such a hold only when the deletion came before the `/resume`, and when handling that `/resume` the daemon reads the comments deleted on the issue's ancestors at or after it, from the ancestors it reads for the `/resume` anyway, as it reads them for the issues below (#244). A `/resume` whose issue stays held only by such a deletion still applies: it ends the holds before it and records that there, as when a later `/hold` keeps the issue held. A hold set by hand ends by `/resume` on the issue itself. Every hold on the issue also ends at once when a trusted user sets another stage label by hand, which 5.1 records as an override. Removing `stage:held` alone is a disagreement (5.3) and is put back. If a discussion trigger was resolved by a trusted response during the hold, the final `/resume` sends the issue to `clarifying` as below, whatever else held it.
- Content edited by an untrusted write collaborator is dirty (5.1), so it never counts as a command or an answer, even after the edit is accepted. In loop step 1 (8.1) the daemon looks for triggers before it processes commands.
- Before applying any run result, the daemon checks the issue for triggers since the last poll before the run was picked up. If it finds one, it holds the issue and drops the result.
- Comments and pushes made while the issue is held are handled once it leaves `held`, in the stage it lands in. A PR review made while held is handled when the task, or for a story's PR the story, next reaches `pr-open`, through the usual `pr-open` rows (7.2, 7.5).
- Any run for the issue is stopped and its result dropped. Nothing is pushed, no PR is opened or updated, and the issue makes no other transition until the hold ends. Other issues, including its parent and children, carry on.
- A held issue is visited on every pass, since a 👍 that resolves a trigger doesn't change its `updated_at` (8.1).
- The digest lists the issue while a discussion trigger on it is open, with each open trigger, a link to it and how to resolve it, and assignment (9.6) assigns `notify` to it for as long (9.4). A hold that only owner holds make is the owner's own, so it gives no item.

**Resolving.** Every trigger needs a trusted user's response:
- A 👍 on an untrusted comment approves it. From then on it counts as that user's input (6.2). The earliest trusted 👍 counts, while the comment is there and clean. A 👍 approves only the text it post-dates: as owner input, an edited comment counts only with a trusted 👍 after its last edit, and a 👍 in the same second as the edit counts as before it. Any edit un-approves it as owner input, a code owner's own included, though a discussion trigger it resolved stays resolved. So a code owner who edits a comment they approved removes their 👍 and gives it again to approve the new text (the owner's choice A on #210). The rule doesn't ask who made the edit. The author's own edit after a trusted 👍 is a trigger of its own (above).
- A trusted comment counters every untrusted comment posted before it, and is itself owner input. Any clean trusted comment counters, a command too, other than `/hold` or `/resume`, which counter nothing. Commands in it apply as usual, except that any that would move the issue wait (see Commands that wait).
- A 👍 on a notice accepts the change. Each notice accepts only the trigger it names, so a 👍 on the notice of a newer edit of some content doesn't accept an older one's. Some triggers are accepted only by `/resume` on the issue, not by a 👍 on a notice:
  - one that edited or deleted what may have been the App's content, a comment GitHub names no author of included, which may have hidden another trigger's record or a hold's. So is an edit known from its record alone of the body, or of a comment that is gone or the App's;
  - a deletion on the held issue made during any hold, at or after the move that began it, which may have hidden a code owner's `/hold` that wrote no marker (see Holds stack). A deletion that started the hold came before it, so a 👍 on its notice accepts it, unless it hit the App's content;
  - one with no clean notice (see Notices).
- Accepting a write collaborator's edit of their own approved comment, by a 👍 on its notice or by `/resume`, ends its hold but doesn't approve the edit. A new trusted 👍 after the edit does.
- Markers in edited or deleted content are never read again (5.1). When that content was the body of an issue the App filed, the daemon reposts its `origin` marker in a new App comment, so the issue keeps its class and its place in its plan (section 5), and matching a plan's children still finds it (5.2):
  - **When.** In step 1, right after the dirty notes and before the type check (8.1), whether the issue is held or not, once the App wrote the issue, no `origin` is read for it, in the body or a clean App comment (section 5), and the body's markers aren't read: it's dirty, or someone other than the App edited it last, trusted or not (5.1). So the owner's own edit of a plan task's body reposts it too, with no hold. An untrusted write collaborator's edit still holds the issue, as above.
  - **From where.** The body's edit history, read once, or one read for that edit already, by the dirty check (5.1) or in finding its parent's children (5.2), and kept past the App's dirty note on it: the newest version the App wrote that has a whole marker, back to the original post, which the App wrote when it created the issue. GitHub keeps only the original post and the 99 newest edits (section 16), so a version gone from the history, or one whose text was deleted, is passed over, and so is the App's own dirty note, which escapes the text it keeps.
  - **What.** The whole marker, every field as it was written: `human=1`, and a check's fields, still percent-encoded. The comment says the description was edited, so the marker is copied there to keep tracking the issue in its plan, and has no `cc` line, since there's nothing for anyone to do.
  - **Once.** The comment is the record: section 5 reads the `origin` from it in the same pass, so a replay posts nothing more. If anyone edits it, it's dirty, and it's reposted once more. With no marker in any version, nothing is posted, and a warning is logged once: until the body changes, a pass reads no history for it.
- `/resume` on the issue accepts every open trigger made before it (see Leaving the hold). Only a `/resume` the App applied counts: a rejected one resolves nothing.
- A resolution is read from GitHub on each pass until the App records it. Until then, removing the 👍, deleting the counter comment or the comment a 👍 approved, making either dirty, or the trusted user's loss of trust opens the trigger again. The App's record, a move out of `held` or an `ended reason=discussion` record, sets the floor (see Which acts count), so nothing later undoes it. Records in edited or deleted App content aren't read (5.1), so editing or deleting a record is a trigger of its own, which only `/resume` accepts.

**Commands that wait.** `/approve`, `/revise`, `/done`, `/track`, `/ignore`, a 👍 on a revision comment and a 👍 on a human task (9.3) would move the issue. While it is held, or at the `clarifying` after a hold, they wait: they're neither applied nor rejected, even when posted before the hold, since step 1 looks for triggers first. A command in a comment is checked at the first stage the issue reaches where it doesn't wait: it applies if it fits that stage and the revision it names still matches its hash (7.4), and otherwise gets a rejection reply (9.2), as `/approve` does after an override to `planning`, with no wait for a later stage it fits. A 👍 is read only at the stage it fits, so it applies when the issue next reaches that stage, under that stage's checks. `/resume` applies at once, and so do `/hold`, which moves only an issue that isn't held, and the commands that set a label, except that a `/hold` or `/resume` waits for one posted before it on an ancestor (see Holds stack).
- At the `clarifying` after a hold from `spec-review` or `plan-review`, as its `origin` names it, which a later hold at that `clarifying` keeps, the interviewer handles the oldest `/revise` that waited as its revision notes. Its transition marker records it with `cmd=` beside `run=` (5.2), and the App 👍s it, so it isn't applied again. That holds for every outcome: after `unchanged`, the `/revise` is used up, and the revision that stood before the hold still stands (9.1). After a hold from `plan-review`, the `/revise` was meant for the plan: after the interviewer's `plan`, the planner gets it as revision notes (section 12), and after a spec, it's used up, answered in the spec's message, so it doesn't send the new spec back from `spec-review`. Another `/revise` waits for the next run, or applies once the issue is at the review stage again.
- The same holds at `plan-review`: an `/approve`, a `/revise` or a 👍 on the plan revision, given while the issue is held from `plan-review`, waits, and goes through its normal checks once the issue is back at `plan-review`, by `/resume` or the interviewer's `unchanged`, but for the `/revise` the interviewer handled (above). So an `/approve` approves only if its plan revision is still the latest and still matches its hash, with nothing else keeping it from approval, and is rejected with the reason otherwise (7.4). A trusted 👍 given during the hold on the latest plan revision approves it then.

**Leaving the hold.**
- Once every trigger is resolved and no owner hold is left, the issue goes `held → clarifying`, and its transition marker carries the stage before the hold: `at`, `origin`, `resolved`, unless no act resolved a trigger, and `seen`, keyed as section 5 says. Its comment names who resolved the discussion, says what comes next, and ends in the `cc` line. The interviewer reads the discussion, with approved and countering comments as owner input, and picks the next stage. An approved comment is owner input only as the text its 👍 post-dates (see Resolving), and other untrusted text stays in `untrusted.md`. Comments it handled there don't count again as revision requests (7.4). A class the interviewer doesn't run on yet waits there instead, until a code owner sets its stage by hand (7.2). The outcomes:
  - Nothing in the discussion changes the issue: `origin`, the interviewer's `unchanged` (9.1). A task whose run was dropped goes to `ready`.
  - The spec changes: the interviewer rewrites it, and the issue goes to `spec-review` for a new 👍 (7.4).
  - The spec stands, but the plan changes: the interviewer's `plan` (9.1), after a hold from `planning`, `plan-review` or `planned`, on an epic or a story, a story with a parent included (#195's Q1a). The issue goes to `planning`, with the interviewer's message and the discussion as the planner's notes (section 12), then to `plan-review` for a new 👍, even when `plan.review` is false (7.2). A story with a parent can't get a spec: its body is its item of its parent's plan, which only its parent's revision changes. For an epic or story that was already `planned`, the plan is a revision (11.3), and once approved it updates the children rather than starting over. The children are the issues matched to its plan items by their `origin` (5.2). Other sub-issues are shown to the planner, but never marked, and are closed only when they sit below a dropped child. Section 5.2 gives the writes and their order:
    - **Kept** items keep their issues and stages, with no write but one: a link to a dropped issue goes when that issue closes (see Dropped). They keep every other dependency link.
    - **Changed** items keep their issues. Each is rewritten whole from the revision: its title, and its body, as a new child of its kind would be written (11.6), with the `rewrite` marker on its first line, naming the planner run that wrote the revision, and its `origin` carrying the revision's `rev`. The full rewrite cleans a dirty body (5.1). Its type label, on a `types: labels` repo, and its scope, priority, model and effort labels become the revision's, replacing any set since, such as by `/priority`, and a kind the item leaves unset is left with none. A changed task goes to `ready`, or `needs-human` for a human task, and a changed story to `planning`, where its next plan is a revision of its own children. Each move comes from wherever the child is, on the `any open →` rows (7.2), and its comment names the revision and links the plan comment. Where a clean App comment carries the child's `origin` from before, as the App's repost after an edit of its body does (above), the move's comment carries the rewritten marker too, and says why: it's then the newest clean App comment with one (section 5), so a later edit of the body by anyone but the App falls back to it, not to the earlier `rev`. A run result for it still waiting to be applied is dropped (8.2). Its blocked-by links to its siblings follow the revision, and links to issues outside the plan stay.
    - **A changed item adopted from a person** (5.2, #372) is rewritten the same way: its body becomes the App's whole, from the revision, with none of the person's text, which stays in the body's edit history. The daemon still reads no marker from a body a person filed (5.1), so its move's comment also carries the rewritten `origin` marker, with the revision's `rev`, and says why. That comment is then the newest clean App comment with one (section 5). A replay that finds the App's clean rewrite already, its `origin` naming the revision's `rev`, doesn't rewrite it again.
    - **A changed item that is held** stays held: the stage it would go to becomes its hold's `at` and `origin`, by a `held → held` marker with no `reason`, which isn't a hold of its own (section 5). So `/resume` takes it there, and so does the end of a discussion, through the interviewer's `unchanged`.
    - A closed child can't be marked changed (11.3), and one that closes after the approval gets no write.
    - **New** items become new children (5.2), and may depend on kept and changed items.
    - **Dropped** items, and every open issue below them, are closed as not planned, deepest first, through the App's move to `closed` (7.2). Its comment names the revision, the dropped item, and for an issue below it, the dropped child it's below, and links the plan comment. Closing a held one ends its hold. A close the table refuses, such as for an issue of a type the pipeline doesn't know, is a state error (5.3), and that issue stays open with its links. A sub-issue in another repo is skipped, with everything below it. Once closed, each loses every dependency link, to it and from it, so no kept child is left blocked. The one link left is one that blocks an issue in another repo, which is that repo's to remove: it's logged. An issue that was closed before gets no write, and keeps its links. A story closed this way skips story verification (7.3). The one exception is an issue with an open PR: it is held with `reason=dropped`, any run for it is stopped, and it is listed for the owner (9.4, 9.6). `/resume` doesn't end this hold. Once its PR merges or closes, or the owner closes the issue, it closes as well, and so do its now-empty ancestors in the dropped subtree. Not built until phase 3, which adds PRs (#234): until then a dropped task closes like any other. Stage runs come after step 1 (8.1), so a drop never lands while a run is under way, and a result of its run still waiting to be applied, after a failed apply or a restart, is dropped, with nothing written, as on any closed issue (8.2).
    - **The record.** The revision's `created` record on the parent comes last, once every change is made, and names the children it leaves, or `none` (section 5). A dropped item's child that isn't found gets no write, and the record names its item and still stands, while a kept or changed one's stops the revision with a state error (5.2).
  - A task's body changes: the interviewer rewrites it in its own template (11.2, or 9.3 for a human task), and the task goes to `ready`, or back to `needs-human` for a human task. Not built until phase 3.
  - More answers are needed: a question round, staying at `clarifying`.
- **An owner hold that stays.** While an owner hold stays, the issue stays held, and the App records that the discussion ended: an App comment carrying `ended reason=discussion resolved=<time>` (section 5), naming who resolved it, posted when a write collaborator's trigger was resolved during the hold since the latest such record. The last `/resume` then sends the issue to `clarifying`. A `/hold` on an ancestor that holds the issue with no marker on it (see Holds stack) is looked for only once the issue could otherwise leave: the daemon reads the ancestors then, and the record names each such `/hold` in `held=`, with the issue it counted as posted on in `heldon=`, and each deleted comment that may have been one in `gone=`, so no later pass reads them again. Its comment names each such `/hold` by its comment and that issue, or by its comment alone where that issue isn't known, and says "`/resume` there, or here, ends that". The App reads the record by its marker alone, so a record whose comment words this differently, as before the issue was named, counts the same.
- **From `intake`.** An issue held from `intake` isn't in the pipeline yet, so the end of its discussion never sends it to `clarifying`, which would bring it in without the approval 6.2 asks for (the owner's Q1a on #188). It stays held with an `ended reason=discussion` record, and `/resume` takes it back to `intake`. So the rules here that send an issue to `clarifying` don't apply to it.
- **With no act.** When the last trigger goes with no act to resolve it, such as a comment its author deleted that no marker records, the issue still goes to `clarifying`, and its comment says the discussion is resolved. But where a `/hold` on an ancestor keeps it held, the record that names that `/hold` has no `resolved`, so it says no discussion ended, and the ancestor's `/resume` sends the issue back to `at`.
- Each of these writes a fresh transition marker, so an edited or deleted marker can't roll state back.
- A trusted `/resume` on the issue itself ends the discussion hold at once. It accepts every open trigger made before it, including triggers whose notice was deleted, and restores `at`, except that a task whose run was dropped goes to `ready`. When a trusted response resolved a trigger before the `/resume`, it goes to `clarifying` instead, so the interviewer reads what was approved or countered: once the App has recorded the end of a discussion during the hold, or else when a write collaborator's trigger was resolved during the hold before the `/resume`, whatever else held the issue. A trigger made at or after the `/resume`, as one between it and the App's pass, keeps the issue held: the `/resume` ends the holds before it and records that with `ended reason=discussion … cmd=` (section 5), and the issue leaves once the later trigger is resolved too. A `/resume` on an ancestor doesn't end a discussion hold. An issue whose owner hold it ended, held for discussion only, goes to `clarifying` once the discussion is resolved, with no other `/resume`, as the App recorded the end of that owner hold (see Holds stack).
- A restart changes nothing, because the hold marker and its triggers are all on GitHub, and the lease of a held issue is dropped (8.2).

## 7. Pipeline

### 7.1 Stages

| Label | Agent | Output |
|---|---|---|
| `stage:intake` | none | Owner's rough idea |
| `stage:clarifying` | interviewer | Numbered questions (section 9.1) |
| `stage:spec-review` | interviewer | Spec written into the issue body (section 11.1) |
| `stage:planning` | planner | Proposed stories or tasks in one comment |
| `stage:plan-review` | none | Waiting for owner approval of the plan |
| `stage:planned` | story verifier when children close | Parent of created sub-issues |
| `stage:ready` | none | Task waiting for the scheduler |
| `stage:in-progress` | implementer | Commits in the run clone |
| `stage:verifying` | verifier | Pass, or findings |
| `stage:pr-open` | none | PR waiting to merge: a PR to `main` waits for human review, and a task's PR into its story branch for the App's merge (7.5) |
| `stage:needs-human` | none | Task only the owner can do (section 9.3) |
| `stage:held` | none | Paused by the owner, or held for discussion (6.4) |
| `stage:completed` | none | Closed as completed, or by a merged PR. Only on a closed issue (6.4) |
| `stage:discarded` | none | Closed as not planned, or as a duplicate. Only on a closed issue (6.4) |

The last two are the closed stages. They're valid only on a closed issue, so they aren't stages an open issue moves through, and no transition marker names them. A closed issue gets one once its close is judged (6.4), and "closed" in the lifecycles and in 7.2 means a closed issue with either.

The lifecycle of each type:

- **Epic.** intake → clarifying → spec-review → planning → plan-review → planned → closed. An epic planned into tasks acts as its own story (section 4), so it ends as a story does, story branch included (7.5).
- **Story.** Created from an approved epic plan, with its acceptance criteria in its body (11.6), and moved intake → planning by its first move (7.2). Then planning → plan-review (or straight to planned, see `plan.review`) → planned → closed. Not built yet: once the daemon opens PRs, a story with changes on its branch goes planned → pr-open → closed, closed by its PR's squash-merge into `main` (7.3, 7.5).
- **Story filed by the owner.** intake → clarifying → spec-review → planning, then as a story.
- **Task.** A task from the planner is created and moved intake → ready by its first move, or intake → needs-human for a human task (7.2, 11.3). Then ready → in-progress → verifying → pr-open → closed, with loops back through clarifying, in-progress or needs-human. A task in a story closes when the App merges its PR into the story branch, and a task with no parent when its PR merges into `main` (7.5). A human task from the planner goes needs-human → closed.
- **Bug, or task filed by the owner.** intake → clarifying → ready, then as a task. Until build phase 3 it waits at clarifying (7.2).

From `ready` on, a `bug` follows the rows for `task`.

**The App's move to `closed`.** The App closes an issue through the table only by a move to `closed`: the `needs-human → closed` row, for a human task (9.3), as completed, the `planned → closed` row, for an epic planned into stories once every child is closed (7.3), as completed, and the `any open → closed` row, for a child its parent's newly approved revision drops and each open issue below it (6.4), as not planned. Not built yet: a task in a story is to close through the same move, as completed, by the `pr-open → closed` row once the App, or a trusted merger, has merged its PR into the story branch (7.5), since GitHub's `Closes #N` acts only on a merge into the default branch. So is a conflict bug the story branch's tip has made moot, as not planned, by the `any open → closed` row (7.5).

- Its transition marker carries `reason`, the state reason, `completed` or `not_planned` (section 5).
- It writes the marker, then the 👍 for a command comment, then the close with that state reason, unless the issue is closed already. The 👍 goes before the close, since step 1 doesn't visit a closed issue to finish it.
- It sets no stage label. The close is the App's, so it's accepted (6.4), and the close judge (8.1) sets `stage:completed` or `stage:discarded` from the state reason on a later pass.
- A crash after the marker leaves an unfinished write, which the label rules finish by closing the issue (5.1).
- A trusted reopen holds the issue at the stage the move came from (6.4).

**A story's PR.** Not built yet, and not in the table yet: these rows join it, and the table in code, with the PR flow (section 17). Until then no story reaches `pr-open`. Each applies to a story, or an epic planned into tasks (7.3, 7.5):

- `planned → pr-open`: every child closed, the story branch has a commit `main` lacks, its tip's checks pass and story verification passes there. The App opens or updates the story's PR to `main`, which carries the tip's `issuedog/verify` check (7.5).
- `pr-open → pr-open`: the story branch has a new tip, from a merge of `main` or a push the App didn't make, and section 10.1 passes on it. The App posts the check on the new tip.
- `pr-open → planned`: a failure on the story branch (7.5) filed a `bug` under the story, or for rule 2 a human task. The App posts the check as `failure`, and the story waits for its children again.
- `pr-open → planning`: a trusted reviewer submits a review with comments on the story's PR, as for a task (above). The review is the next planner run's notes, and its plan is a revision of the story's children (11.3, 6.4), whose new tasks are worked on the story branch.
- The story's close is the "any open → closed" row: its PR's squash-merge into `main` closes it, by its `Closes #N` (11.5).

**Skipping plan review.** With `plan.review` false, a story's plan skips review unless the move that put the issue at `planning` carries `origin`. Looking through the planner's own rounds and the holds the issue went back from, that's only the interviewer's move out of the `clarifying` after a discussion hold (6.4). A discussion hold at `planning` that `/resume` ends with no trusted response goes straight back to `planning`, with no `origin`, so that plan still skips review. This affects only a first plan: every revised plan, of an issue `planned` before (11.3), waits for review, however the issue got back to `planning`, as a revision can close issues (#195's Q2a).

Until build phase 3, the interviewer runs only on an epic, a story with no parent and an untyped issue (9.1). A bug or a task, whether filed so or typed so by the interviewer, waits at `clarifying` with no more runs until the implementer stage adds the 11.2 rewrite. So does a story with a parent. Every move into the pipeline says so (6.2). Each of these also waits at the `clarifying` after a discussion hold, until a code owner sets its stage by hand, and the move there says so (6.4). The exception is a story with a parent back from a hold from `planning`, `plan-review` or `planned`: the interviewer runs on it there, with only `questions`, `unchanged` and `plan` (9.1, #195's Q1a).

Any transition missing from this table is an error, except a trusted user's manual label change (5.1) or a rejected command (9.2). The daemon logs the error, leaves the issue unchanged and reports a state error (5.3).

`/hold` applies `stage:held` to every open descendant of the issue, then to the issue, each with its own transition marker, then 👍s the command. An issue that is already held gets no new marker (6.4). `/resume` ends that owner hold on each one, restoring the stage named in its marker unless another hold remains (6.4). A `/resume` that would take no issue out of `held` is rejected, naming the issues where `/resume` would end the holds left, unless it ends an owner hold on an issue that stays held for discussion only, or only by a `/hold` on an ancestor posted after the `/resume` but handled first, or a comment deleted after the `/resume` that may have been one, which it records there (6.4). When the rejection names the issue it's posted on, as held for discussion or as where holds left were made, it calls it "this issue" and says "here" for it, and names the others with "there".

### 7.3 Story and epic completion

- When every child of a story, or of an epic planned directly into tasks, is closed, the daemon runs story verification on the story branch (section 10.3, 7.5), unless the story itself was dropped from its parent's plan (6.4). The verifier sees each child's close reason, so tasks closed as not planned are not mistaken for delivered work.
  - It runs only on a tip whose checks pass (7.5). A story with no story branch, as when its only tasks were human tasks, is verified on `main`.
  - Failures create `bug` sub-issues under the story, worked on the story branch.
  - On a pass, a story branch with a commit `main` lacks gets the story's PR: the App opens it to `main`, or updates it, and the story moves to `pr-open` (7.2). The owner reviews it and squash-merges it, and the merge closes the story. Review comments become tasks on the story branch (7.5).
  - A pass with nothing to merge closes the story, as story verification does today.
  - Not built yet: story branches and the App's task merges are phase 3's, and story verification and the story's PR phase 4's (section 17). Until phase 3 all of it runs by hand, and from phase 3 to phase 4 story verification and the story's PR still do, on the branch the daemon keeps.
- An epic planned into stories closes when every child is closed. It has no story branch of its own: each of its stories has one.
  - Its children are read as a finished story's are (9.4): every child its `created` record (5.2) names is closed, its close judged and accepted, with no close of one still to judge, and no open issue is left below it. An untrusted close doesn't close the epic: while it waits to be judged, as when its event is late or how it was made can't be read, the epic waits too, and once it's reverted the child is open again (6.4). A close that's never judged keeps the epic open: for good when its issue is transferred or its timeline is gone before that, and for a closed child with no stage label, which isn't judged unless this daemon held it open with one (section 16), whoever closed it, till a closed stage is added to it while a daemon runs. The exception is a close-judging gap section 16 lists that a start can't see: a child a start finds closed with one closed stage counts as closed, though someone untrusted set that stage, or closed it, while no daemon ran. A child its approved revision dropped (6.4) isn't named, so it counts for nothing. A record of none, after a revision that drops every child, leaves nothing to wait for, so the epic closes on the next pass.
  - A child's close changes nothing on the epic, so this is judged on each pass from what the poll listed, with no request. An epic to be read again, as when its step 1 failed, waits for its next good visit, which may hold it (6.4). Once it holds, the epic is read again, the label rules run on it (5.1), and the daemon closes it through the App's move to `closed` (7.2), as completed, with one comment naming those children. The close judge then sets `stage:completed`.
  - The move is keyed `event=p<comment id>`, by the epic's comment that holds the move to `planned` approving its plan (section 5), so it's made once for each approved plan. After a trusted reopen holds the epic (6.4) and `/resume` brings it back to `planned`, it stays open until the owner closes it or approves a revision.

### 7.4 Approvals bind to a revision

- **Revision numbers.** Each time the daemon writes a spec or plan, it increments `rev` and posts a revision comment naming the revision. For a spec, the comment carries `<!-- issuedog:revision rev=<n> body=<hash> -->`. For a plan, the plan comment is the revision comment (11.4), and its last line is `<!-- issuedog:revision kind=plan rev=<n> body=<hash> -->` (#247's Q1a).
  - **Two kinds.** A `revision` marker with no `kind` is a spec revision, and one with `kind=plan` is a plan revision. Each kind numbers its revisions on its own, from 1, and is read on its own: every rule for specs reads only spec revisions, and a plan revision is never the latest spec revision, nor a spec revision a plan revision. So a 👍 on a plan comment approves no spec, and at `spec-review`, `/approve`, revision requests, reposting a stale revision, the digest's approval item (9.4) and the interviewer's line that a revision still stands (9.1) ignore plan revisions. At `plan-review` the same rules read only plan revisions, so a 👍 on a spec revision there approves nothing.
  - The hash is the first 8 hex digits of the SHA-256 of the body, with CRLF and CR line endings normalised to LF. Nothing else is normalised, so markers and a dirty note (5.1) are part of it.
  - **A plan's hash.** For a plan revision, the "body" is the plan comment's text above its last line: the plan, the move's transition marker and the `plan-data` marker (section 5), with line endings normalised the same way. The last line must be the plan revision marker alone. A plan revision matches while its comment still has that hash, so an approval binds to the plan's data as well as its text.
  - A spec revision posted with a transition goes in the transition's comment, and the transition marker carries `rev` and `body` too. A plan revision's transition marker carries `rev` only, since it's inside the hashed text. A revision is posted even when the hash is unchanged, since an answered question is a new revision and 👍s on the earlier one mustn't approve it. A revision posted without a transition, such as after a body edit, is skipped when the latest revision already has the body's hash. Plan revisions are posted only with the planner's move.
  - The latest revision of a kind is the last revision comment of that kind that counts. A dirty revision comment (5.1) is no revision. A dirty App comment after the latest revision may hide a newer one, and so may an App comment deleted after it was posted (a `CommentDeletedEvent`, section 16). The App never deletes a comment, so such a deletion is always someone else's, unlike an author's deletion of their own, which records no event (section 16). So nothing approves until the daemon posts a clean revision after it.
- **Approving.** A trusted 👍 on the latest revision comment of the stage's kind, or a trusted `/approve` posted after it, approves that revision: at `spec-review` the latest spec revision, while the body still matches its hash, and at `plan-review` the latest plan revision, while its comment still matches its hash. Either way, only while nothing hides the revision and the body isn't dirty. A spec's approval moves the issue to `planning`, and a plan's to `planned`. The approval's transition marker carries `rev`, `body`, the revision's hash, the approving `cmd` and `seen` (section 5). With several trusted 👍s, the earliest is recorded.
  - 👍s on earlier revision comments, and 👍s from untrusted users, other bots or the App, are ignored.
  - Removing a 👍 after the daemon applied the approval changes nothing.
  - A rejected `/approve` gets the App's 👎 and a reply with the reason (9.2), such as a hash that no longer matches, or that it was posted before the latest revision.
  - **Rejecting a spec's `/approve`.** When the body is dirty, or the latest spec revision is missing, hidden or no longer matches the body's hash, the reply says whether a revision follows, and doesn't ask for a new comment, as a second `/approve` would be rejected the same way. A dirty body gets no revision: the reply says so, and that `/revise <notes>` or any other comment gets a new spec, which replaces the edit. Otherwise a revision follows when the body's last editor, or its author if nobody edited it, is the App or trusted (see The body is edited below), and the reply says the App posts it next, and to 👍 it or post `/approve` after it. When that's someone else, such as an untrusted author, the reply names them, says no revision follows, and that editing the description, or `/revise <notes>` or any other comment, gets one.
  - **A plan that nothing approves.** No plan revision approves while the plan comment is dirty, which makes it no revision, while a dirty or deleted App comment after it hides it, or once its comment no longer matches its hash. A spec gets a new revision from the daemon, but a plan comes only from a planner run, so the daemon posts none of its own: `/revise` or any other comment gets a new plan (#248's Q1a). The digest's item says why the plan can't be approved, and how to get a new one (9.4).
  - **Rejecting a plan's `/approve`.** The reply says why, in this order: there's no clean plan revision to approve, which may mean the only plan comment was edited without approval or deleted, not that none was posted; an App comment after the latest plan revision was edited without approval or deleted, so it may hide a newer one; the plan comment was edited after it was posted, so it no longer matches its hash; or the body has an edit that wasn't approved. Each of the first three says that `/revise` or any other comment gets a new plan, and the reply doesn't ask for a new comment, as a second `/approve` would be rejected the same way. An `/approve` posted before the latest plan revision is rejected with no ask either, and the reply says to 👍 that revision or post `/approve` again. A dirty body's reply doesn't ask for one either: nothing at `planning` or `plan-review` rewrites the body (see The body is edited at `plan-review` below), so it says a new plan won't clear the edit, and that setting the stage by hand moves the issue on.
  - **The approved plan.** The plan revision a move to `planned` approved is read back, with its comment and the plan's data (section 5), for creating the children. That's the revision the latest clean App move to `planned` names: by its `body` for an approval, or for a story's plan that skipped review, by the plan revision marker in the move's own comment, since that move is the plan comment. The comment must still be clean and match its hash, or nothing is read back. A later dirty comment doesn't unapprove it. Creating the children reads it (5.2).
- **Revising.** In `spec-review` or `plan-review`, any trusted comment that is not a command (9.2) and isn't dirty, posted after the latest revision comment and after the issue entered the stage, is a revision request with the comment as the notes. "After the revision comment" means after the newest comment the App had read when it posted it, its `seen`, if it has one. A revision request is handled exactly like `/revise`: applied with a 👍, rejected with a reason, and replied to if edited after it was applied (5.2, 9.2).
  - **Sending a plan back.** At `plan-review`, a revision request or `/revise` moves the issue to `planning`, with `cmd` and `seen` set to the comment, and the App 👍s it. The comment is the next planner run's notes, even after a hold at `planning` (section 12). "After the revision comment" is after the `seen` of the move in the plan comment. A request at `spec-review` reads only spec revisions, and one at `plan-review` only plan revisions. A rejected request's reply says it didn't send the plan back, or the spec, by the stage it was posted at. When the stage has moved on since, as when such a reply was lost and is posted again, it says where the request was posted, and that a comment sends the spec back only at `spec-review`, and the plan only at `plan-review`.
  - A comment beats a pending 👍, since comments are handled before reactions.
  - **A comment 👍'd as an answer.** The App's 👍 on an answer at `clarifying` or `planning` acknowledges it, and only a move's `seen` uses it (9.2). So a comment after the `seen` of the run's move to the review stage is a revision request even with that 👍, while no marker names it in `cmd`, unless it was edited after the 👍: then it gets the reply asking for a new comment, as an applied command does (#318). A comment the run read is under the move's `seen`, so it is never one. A run resumed from a lease leaves no such comment, as its result is dropped and the stage runs again with the comment as input (8.2), but a read that lists the comment without the run's move can. Once that move is recorded again because a dirty comment hid it (5.1), the record's `seen` may be below the run's, so a comment the App 👍'd before the dirty comment was posted may be one the run read, and is no revision request; one it 👍'd in that comment's second or later is, as no run read it.
  - A question counts as a revision request: the agent answers it and posts the next revision, even if nothing else changed.
  - A comment posted after the approval was applied goes to the next stage as owner input. The transition's `seen` (section 5) decides which comments come after it, so one posted in the same poll isn't lost.
- **The body is edited.** The hash no longer matches. After an edit by the body's author, if trusted, by another trusted user (6.1), or by the App, the daemon increments `rev` and posts a new revision comment with the new hash, which voids any pending approval. So the owner's edit to the spec of an issue someone else filed gets a new revision. An edit by anyone else makes the body dirty (5.1): it gets no revision, and nothing can approve it. An untrusted author's own edit gets no revision either: before the App's first full rewrite of the body (5.1) the mismatch keeps approval blocked, and after it the edit makes the body dirty, until the history no longer shows the rewrite (5.1). Then the mismatch alone keeps approval blocked, as before the rewrite.
  - **An edited spec revision comment.** It's the App's, so anyone else's edit makes it dirty (5.1), and it's no revision. The issue stays at `spec-review`, with no state error and no interviewer run: the daemon records the move to `spec-review` again in a comment of its own (5.1), and an untrusted write collaborator's edit holds the issue for discussion instead (6.4). The record holds no revision, so the daemon then posts the next revision of the body, as after any dirty revision comment, unless the body is dirty or its last editor isn't trusted (see The body is edited). A 👍 or `/approve` on that approves the spec.
  - **An edited plan comment.** A plan comment is the App's, so anyone else's edit makes it dirty (5.1), and it's no revision. The issue stays at `plan-review`, with no state error and no planner run: the daemon records the move to `plan-review` again in a comment of its own (5.1), and an untrusted write collaborator's edit holds the issue for discussion instead (6.4). With no other clean plan revision, a 👍 approves nothing, `/approve` gets the reply that there's no clean plan revision to approve, and the digest's item says so (9.4). `/revise` or any other comment gets a new plan.
  - **The body is edited at `plan-review`.** A plan's hash is of its own comment, so a trusted edit to the body changes nothing: no revision is posted, and the plan still approves. To get a plan from the edited spec, post `/revise` or any other comment, so whether the plan is stale is the owner's call (#248's Q2a). A dirty body keeps any plan from approval, as for a spec. Nothing at `planning` or `plan-review` rewrites the body, so that lasts until the interviewer rewrites the spec after a discussion hold (6.4), or an override moves the issue on (5.1).
  - **Leaving `spec-review` with a dirty body.** The interviewer's spec is the App's full rewrite of the body (5.1, 11.1), so it cleans the body. The untrusted text is gone from the body, and the interviewer saw it only in `untrusted.md` (6.2). So a `/revise` or a revision request sends the issue back to `clarifying`, and the next spec gets a normal revision, which a trusted 👍 or `/approve` approves. The spec's move names whose edit it replaced. Until then nothing approves the dirty body. An override also leaves: a trusted user sets the next stage label by hand (5.1).
- **PR approval.** This relies on GitHub. The ruleset dismisses stale approvals when new commits are pushed, and `issuedog/verify` is posted for an exact head SHA.

### 7.5 Story branches

Each story gets one branch. The pipeline merges each verified task into it, and the owner reviews the story's PR, which squash-merges into `main`. So tasks never wait for the owner's merge, and sibling tasks never stack. Not built yet: the daemon opens and merges no PRs until phase 3, and story verification is phase 4's (section 17). Until then the dispatcher works this way by hand, from S5 (#195) on.

- **Which branch.**
  - A story, or an epic planned into tasks (section 4), has one story branch, `issuedog/<story>-<slug>`. The App cuts it from `main` when it picks the story's first task, and that task starts once the new tip is checked (8.1).
  - An epic planned into stories has none: each of its stories has its own.
  - A task or a bug whose parent is an open story, or an open epic planned into tasks, is in that story, and works on its branch. That covers the story's planned tasks, bugs from its story verification or from a failure on its branch (below), tasks planned from a review of its PR, and a task or bug the owner files under it.
  - A task or a bug with no parent works as before: a branch from `main` and a PR to `main`, which the owner reviews and merges, its `Closes #N` closing the issue.
  - A branch is found by its `issuedog/<issue>-` prefix, so a retitled issue keeps its branch.
  - **Two branches with one prefix.** Only an admin or the App can create an `issuedog/*` branch (section 15), so a second branch with one issue's prefix can come only from one of them, or from a rename if the ruleset allows one (section 16). The daemon can't tell which is the issue's, so it acts on neither: it posts a `kind=branches` state error on the issue (5.3), merges nothing into either, and starts no run of the issue's, or for a story of any task in it, until one is left. The owner deletes the other.
  - **A deleted story branch.** Only an admin or the App can delete a story branch (section 15), and the App does so only once the story's PR has merged (below). Not built yet: if an admin deletes it once a task or bug in the story has been `in-progress` (section 16), the daemon doesn't cut it again, since a new cut from `main` would drop the story's merged work without a word. It posts a `kind=branches` state error on the story (5.3), and starts no run of any task or bug in the story until a branch with its prefix is back. Any run under way for a task or bug in the story is stopped with its result dropped, as when its named target moves (3.4, 8.2). GitHub closes each open PR of a task or bug into the deleted branch, unmerged, and restoring the branch doesn't reopen it. One at `pr-open` moves to `needs-human`, as for any PR closed without merging (7.2), and the owner reopens the PR once the branch is back, or posts `/done` to start it over. One further back, at `in-progress` or `verifying`, whose run was stopped, waits where it is, and once the branch is back, its next pass through verify opens or updates its PR (7.2's `verifying → pr-open`). The owner restores the branch, or creates one, as an admin can at any time (below). Before any task or bug in it has been `in-progress`, the branch holds no task's work, so the next pick cuts it again from `main` (8.1).
- **History only moves forward.** Story and task branches share `issuedog/<n>-<slug>`, so one ruleset, `issuedog branches`, covers `issuedog/*` (section 15). It blocks creation, force-pushes and deletion for everyone but a repository admin and the App. Anyone with write access can still push commits to such a branch once it exists, or merge into one. A write collaborator who isn't an admin can push to an existing `issuedog/*` branch but can't create, delete or force-push one, task branches included, and names branches of their own outside `issuedog/`.
  - So only the App or an admin can create a story branch (section 15). The App cuts it from `main` as it is then. An admin can create one at any time, as the dispatcher does while the pipeline runs by hand, and is trusted with where it starts, since an admin can change the rulesets anyway. Every later tip descends from the commit the branch was created at, and from every tip before it. Nothing pushed to the branch can start it from an older commit, or take its history back to one. Whether the ruleset also blocks renaming a branch into or out of `issuedog/*` is still to confirm (section 16).
  - That's what lets rule 2 take a story's baseline from git, as the merge base of its tip and `main` (10.1), with no record of the branch on the story. It also lets the App's checks on the branch's tips stand as the record of which tips it checked (below).
  - The App's bypass covers what the design has it do itself: create story and task branches, delete a branch once its PR has merged, and push a new run's result over a task head it dropped (3.4).
- **Task PRs.**
  - A task's PR is one the App opened, from the task's branch in this repo. A PR from a fork, or one the App didn't open, is never a task's PR.
  - A task in a story branches from its story branch's tip, and its PR targets the story branch. It's blocked until its dependencies merge, now into the story branch (8.1).
  - **A checked base.** The PR is verified, and merged, only while the tip it's based on is checked with `success` (see The story branch's checks). A failure's bug is the one exception: it's verified and merged against a tip that passed rule 2, even if other rules fail there, and its own open failure never blocks it (below). Rule 2 compares the head with the story's baseline too, the merge base of `main` and that tip (10.1), so wherever a task's checks or verifier run, every agent-config path is `main`'s version at that commit (3.4), whatever was pushed to the branch.
  - When verify passes (10.1, 10.2), the App posts the check, squash-merges the PR into the story branch and closes the task as completed (7.2). No owner merge is needed. The PR names its task without a closing keyword (11.5), since GitHub's act only on a merge into the default branch, so the App closes it.
  - **The merge's guards.** The App merges with the merge API's `sha` set to the head it verified, so GitHub refuses the merge if the head moved. It merges only while the PR is based on the story branch's tip (10.1 rule 7). If the branch moved, the PR is checked again first, on its merge result with the new tip (7.2), and merged only if that passes. Only a merge onto the tip the task was verified against carries the check over (below).
  - **Carrying the check over.** The squash commit's tree is the verified head's. So when the new tip's parent is the tip the task was verified against, and that tip was checked with `success`, the App posts `issuedog/verify` as `success` on the new tip, naming the branch, and linking the task's verifier comment. Any other new tip gets no such check, and is checked as a push the App didn't make (below): one whose parent is another commit, as when someone pushed between the check and the merge, and one a failure's bug made.
  - **Someone else's merge.** A task's PR merged into the story branch by anyone but the App counts only if the merger, the PR's `merged_by`, is trusted (6.1). Then the App closes the task as completed, as a trusted close stands (6.4). An untrusted merge closes nothing: the task moves to `needs-human` with a hand-off naming who merged it (9.3), and the owner closes the task if the work is right, or posts `/done` to start it over. Either way the merged tip is a push the App didn't make, and is checked again.
  - **Branches after a merge.** Once a task's PR has merged into the story branch, the App deletes the task's branch, and once the story's PR has merged into `main`, the story branch. GitHub's own "Automatically delete head branches" may get there first, if the repo has it on (section 16).
- **The story branch's checks.**
  - **Which check counts.** A tip is checked only by a check the App posted for that commit as this story branch's tip: its check run's `external_id` names the branch. A check from elsewhere, such as one on the same commit as another branch's tip, doesn't count. Story verification, the story's PR and new task branches use only a tip whose check is `success`. Every tip needs one, even a newly cut branch's, which is a `main` commit: the daemon checks it as it checks any tip that has no check (8.1). So that check run sits on the `main` commit the branch was cut from, naming the story branch, and it's `failure` if `main`'s `verify.commands` fail there, a failure on the story branch like any other (below). Nothing else reads it: a check counts only for the branch it names, and the `main` ruleset requires `issuedog/verify` only to merge a PR (10.4).
  - **Why the check is the record.** Only a GitHub App can write a check run, only the App that wrote one can change it, and nobody can delete one (section 16). And the branch's tip can't go back to a commit it held before. So, unlike an App comment, the mark can't be taken away or rolled back, and the daemon reads which tips it checked, and with what result, from GitHub after a restart. It keeps no other record of the branch.
  - On a story branch, section 10.1 runs rules 1, 2, 3 and 7, on the diff against `main`. Rule 2 compares every protected path with its version at the story's baseline, the merge base of the tip and `main` (10.1). Rules 4 to 6 are about one task's diff, so they run on each task's PR, not on the whole story, whose diff may pass `verify.max_diff_lines`.
- **When `main` moves.**
  - The App merges `main` into each open story branch with a real merge commit, never a rebase or a squash, and re-runs section 10.1 on the new tip. The merge makes that `main` commit the story's baseline, as the merge base.
  - It merges only into a tip whose check is `success`. A tip with no check yet is checked first (8.1), and while a failure on the branch is open, no more of `main` is merged in.
  - A task's open PR into that branch then has a moved target branch, and is checked again (7.2).
  - A conflict, or a failing check, is a failure on the story branch (below), the daemon's to handle at the story level.
- **Pushes the App didn't make.** The `issuedog branches` ruleset blocks creation, force-pushes and deletion, not pushes to a branch that exists (section 15). Anyone with write access can push commits to a story branch or merge into one, so an engineer can add a commit directly.
  - Such a commit leaves a tip with no check of the App's naming the branch, which is how the daemon tells it (section 16). It doesn't need to know who made the tip: the App's own merge of `main` leaves one too, and both are checked the same way. The bare clone's sync (8.1) shows the new tip, and the daemon re-runs section 10.1 on it, as after a merge of `main`.
  - A failure is handled like a failed merge of `main`.
  - Story verification, and the story PR's `issuedog/verify`, are posted only for a tip whose checks pass.
- **A failure on the story branch.** The App posts the tip's check as `failure`. While a failure is open, no other task in the story is picked (8.1), and a story at `pr-open` moves back to `planned`, its PR's check posted as `failure` (7.2). What follows depends on the failure:
  - **Rule 2.** A protected path that differs from its version at the story's baseline needs a human-authored change (6.3), which no agent can make. So the App files a human task under the story (9.3), in the hand-off template, its `origin` marker naming the story and the failing tip, with `human=1` (section 5). A tip that fails rule 2 gets only this human task, never a bug, whatever other rules it fails too. Its steps say to revert the change on the story branch with a new commit, and to land it on `main` in a PR of its own if it's wanted. The story's tasks wait until a later tip passes, whatever happens to the human task.
  - **Any other rule.** Only for a tip that passed rule 2, the App files a `bug` sub-issue under the story naming each rule that failed and its output. The output is fenced and escaped, since it may quote an agent's or a test's text, and each rule's is cut to 1,000 characters, as an attempt cap's cause is (5.3). Its branch is cut from the failed tip, and its PR is verified and merged against the story branch's tip as long as that tip passed rule 2, the exception to a checked base. Its own open failure never blocks it.
  - **When the branch moves under a failure's bug.** Once the story branch's tip moves past the tip a failure's bug was filed for, the bug waits until a tip passes rule 2, and its runs then name that tip as the target to merge (3.4), even if other rules fail there, since the bug is their fix. While a failure's bug is open, a later tip that passes rule 2 but fails another rule files no second bug: the App comments that tip's failing rules and their output on the open bug, fenced, escaped and cut the same way, which its next run reads as input.
  - **A conflict.** The App files a `bug` naming the `main` commit that didn't merge and the conflicting files. Its `origin` names the story tip the merge failed on, which had a `success` check, since `main` is merged only into such a tip. Its run starts from that `main` commit, the bug's baseline, so its branch is cut there, and names that tip as the target to merge (3.4). Its implementer merges the tip and resolves the conflicts, so its head is a merge commit whose parents are that commit and the tip, or it fails rule 7. Starting from the `main` commit keeps the run's checkout at the bug's baseline even when that commit changed a protected path: the tip changed none since the story's older baseline, so the merge brings in none of that baseline's agent config (3.4). Its rules other than rules 1 and 2 judge the head's diff against the conflicted merge of the two, as `merge-tree --write-tree` writes it, markers included, so they judge only the resolution, not `main`'s changes. Rule 1 runs on the head. For rule 2, the bug's baseline is the `main` commit it names, which is also the merge base of its head and `main`, so a `main` that changed a protected path doesn't block the resolution. A squash would drop `main` from the branch's history, so once verify passes the App fast-forwards the story branch to exactly the head SHA it verified, without force, a push GitHub records as the PR's merge (section 16). The push fails if the branch moved. Once it lands, that `main` commit is the story's baseline, as the merge base. If the push fails, the bug waits, as when the branch moves under a failure's bug (above), and its next run merges the named new tip.
    - **A conflict merged by hand.** Once the story branch's tip descends from the `main` commit an open conflict bug names, other than through the bug's own PR, as when an engineer merged that commit or a newer `main` into the branch, the bug is moot. Not built yet: when the daemon checks that tip, it first closes the bug as not planned, with a comment naming the tip, its move keyed `event=t<SHA>` by that tip (section 5), and then its PR if it has one, and any run of the bug's is stopped, its result dropped (8.2). Closing a held bug ends its hold, as a dropped child's close does (6.4). The tip is then checked as any push the App didn't make, so a failure there is a new one. Otherwise the bug's runs would fail rule 2 against its named commit until the last attempt, whenever that newer `main` changed a protected path.
  - Each filed issue's `origin` marker names the story and the failing tip, so a replay files it once (section 5). The new tip a bug's merge makes is checked afresh.
- **The story's PR.**
  - When story verification passes on the branch (7.3), the App opens the story's PR from the story branch to `main`, or updates it. Its head is the tip, so it carries the `issuedog/verify` check run the App posted on that tip, already `success`, which the `main` ruleset requires (10.4). Story verification posts no check of its own (see Its required check is the tip's).
  - The owner reviews it and squash-merges it, and its `Closes #N` closes the story (6.4).
  - A trusted review with comments sends the story to `planning`, with the review as the planner's notes (7.2). The story was `planned` before, so its plan is a revision of its children (11.3, 6.4), and the revision's new tasks are worked on the story branch. Revisions are built (#195); the story's PR, and so this move, are not yet.
  - **Its required check is the tip's.** The `issuedog/verify` the `main` ruleset requires on the PR is the check run the App posted on its head as the story branch's tip (10.4): rules 1, 2, 3 and 7 there, or a task's check carried over. It doesn't follow story verification. So after a review sends the story to `planning`, each review task the App merges carries a `success` check to the new tip, and the PR's required check stays green while those tasks land, before story verification runs on them. It doesn't stop the owner merging then. The story's stage shows where it is, and the PR is assigned to the owner only while the story is at `pr-open` (9.6).
  - A new tip while the PR is open, from a merge of `main` or a push the App didn't make, re-runs section 10.1 only. Story verification runs again only after the story's next children close.
  - A story PR closed without merging leaves the story at `pr-open`, and the digest lists it for the owner, who reopens the PR or closes the story (9.4, 9.6). Not built yet, like every PR item.
- **Stories that depend on stories.** A story branch is cut from `main`, so a task isn't picked while its story is blocked (8.1): a story waits for the stories it depends on to merge into `main`.

## 8. Scheduling

### 8.1 Picking work

Each loop iteration:

1. Process new trusted comments, reactions and label changes on open issues: answers, `/approve`, `/revise`, `/done`, `/hold`, `/resume`, `/priority`, `/model`, `/effort`, `/track`, `/ignore`, 👍 on revision comments, triage flags (6.2), hand-off comments, state-error comments, human-task issues, untrusted comments and hold notices (6.4), and other comments in review stages (7.4). Revert untrusted label changes, record overrides and note dirty content first (5.1), then repost a lost `origin` (6.4), then check the type (5.3). Then move admitted issues from intake to clarifying (6.2), and bring the `triage:*` labels in line. Last, on an open issue at `planned`, create the children of its approved plan revision, or for a revision, apply it to them (5.2), after its commands and reactions, so an approval by 👍 or `/approve` and its children land in the same pass. A story's plan that skips review gets its children in the next pass's step 1, as the planner runs in step 3. A held or closed parent gets nothing, and creation carries on once a hold ends back at `planned`. One whose move into `planned` approves no revision with its data, as when the plan comment is dirty or edited since, gets nothing either, and that is logged at debug, while plan data that won't read back is a `children` state error (5.2, 5.3). An issue with `triage:ask` is visited on every pass, since a 👍 on its flag doesn't change the issue's `updated_at`. So is an issue at `spec-review` or `plan-review`, for a 👍 on its spec or plan revision (7.4), and one that had an open state error after its last step 1, for a 👍 on the error (5.3), and a held issue, for a 👍 that resolves a discussion trigger (6.4), and an issue with `stage:needs-human`, for a 👍 on a human task itself (9.3) and for the closes of the issues blocking it (9.4). Their reaction reads, and a human task's read of its blockers, are conditional, so an unchanged pass costs no rate limit.
2. Reconcile PRs: merges, closes, reviews with comments (7.2), new head SHAs, and `main` or a story branch moving under open PRs. Reconcile story branches too: first check each tip that has no check of the App's naming its branch, then merge `main` into each open one whose tip's check is `success` (7.5).
3. Run any pending non-task stage work for the highest-priority issue that has it: clarifying, spec, planning, story verification. If no stage ran, run triage (6.2) on the newest open issue that needs it.
4. Otherwise pick the next task:
   - It is `stage:ready`.
   - It is not blocked, judged by advanced search `is:blocked` plus any open `depends-on` markers. Search results lag behind dependency writes, so the daemon confirms a candidate through the issue dependencies API before picking it.
   - A task in a story (7.5) is picked only when its dependencies have merged into its story branch, which for a sibling task is its close. The pick of the story's first task cuts the branch from `main`, and the task starts once step 2 has checked the new tip (7.5). That check is posted on the `main` commit the branch was cut from, naming the branch, and is `failure` if `main`'s `verify.commands` fail there, which files a bug under the story like any failure on its branch. Nothing else reads it (7.5). It also waits while its story is blocked, while the branch's tip has no passing check, and while a failure on the branch is open. A failure's bug is excused from both: its own open failure never blocks it, and once the branch moves it waits only for a tip that passes rule 2, then targets it even if other rules fail there (7.5). These waits hold for every implementer run in a story, not only a pick (3.4).
   - Ties are ordered by priority, then the parent's priority, then issue number.
5. If nothing is available, sleep `idle_sleep` (default 60s).

- **The digest.** After step 1 on every issue, and before any stage runs (steps 3 and 4), the daemon brings the digest up to date (9.4), since a stage run can take minutes. A stage run's writes show in it on the next pass. A failure to keep the digest is logged and stops nothing. The digest itself is never in the loop's steps: it is never visited, never runs a stage and is never picked.
- **Closed issues.** Before step 1's reads, the daemon judges the closes still to judge (6.4), at most 20 per pass, newest close first, so a fresh close isn't stuck behind a backlog. An issue whose close it reverts is read and visited in the same pass.
  - The poll lists closed issues too. A closed issue's close is still to judge when it has a stage label, or this daemon held it open with one, judged it or closed it again, unless the close is explained: this daemon judged it, and the listing still shows the `closed_at` and the stage labels it left; or the App closed it again itself, and the listing still shows what that close left; or, on a start's first poll, it has exactly one stage label, a closed stage, which only an accepted close leaves, and that counts as this daemon's judging of it. A close found still to judge stays so, even if its stage labels go, until it is judged or explained. So a comment or any other change to a judged closed issue reads nothing, but any change to its stage labels, their removal included, has it judged again, and an accepted close is left with one closed stage, the one it names unless a trusted user chose the other (6.4).
  - Judging reads the timeline once. A close whose event GitHub hasn't written yet, one from `closed_at` on, is looked at again next pass. So is one whose closer question failed, even once a state error stands for it (6.4), but while that error stands, only the question is asked, with no timeline read, until the listing shows another `closed_at` or other stage labels. So a closed issue with one closed stage is never read again, on a pass or a start, until its `closed_at` or its stage labels change while the daemon runs.
  - The first start judges each closed issue from before the closed stages once, most of them at `stage:pr-open`, with one timeline read and at most two label writes each. A crash part way resumes, since each write is checked first and the issues still to judge are found from the listing again.
- **One task at a time.** Only one task is `stage:in-progress` at a time. A task waiting on the owner releases the worker, and the scheduler moves on to the next independent task.
- **Polling cost.** Polling uses conditional requests (ETags) and `since=` filters, so unchanged resources don't count against the rate limit. On a pass where nothing changed, the digest makes no request beyond the poll (9.4). Creating a parent's children, or applying a revision to them, reads its lists only until the revision's `created` record stands: then its visits make no request for them (5.2). An open human task at `needs-human` costs two conditional reads a pass, its reactions and its blockers, each a 304 when unchanged (9.3, 9.4).
- **Issues gone from the repo.** A transferred issue drops out of the repo's listings, and nothing about it changes there, so no `since=` poll lists it again, and a deleted one is the same (section 16). So every 10 minutes, by GitHub's clock, the daemon lists every open issue, and reads again each issue it holds open that the listing leaves out. A read that finds an issue gone drops it only if the read before it found it gone too, as one answer may be wrong, and being left out of the listing counts as that first one, unless the same pass's poll listed the issue, as it lists one that changed and the one at its cursor. So the read drops a transferred or deleted issue at once: Work gets it no more, and it leaves the digest's items (9.4) and assignment (9.6). One that's there after all, such as one closed since the poll, is kept, or left by the next poll. Until the listing, Work still gets such an issue, though a stage run's own read finds it gone (8.2). The listing also brings back a live issue that wrong answers dropped: each open issue it lists that the daemon doesn't hold, other than a pull request or the digest, and last updated before the poll's cursor, is read that pass, and step 1 runs on it as on any issue read (6.2). One updated since is the next poll's. The listing costs one conditional request for each 100 open issues and pull requests, every 10 minutes, each a 304 when nothing on its page changed since the last one. A start's first pass makes none, as its poll lists every issue, and nor does a pass that holds no issue. A failed listing is the pass's error, and the next one waits 10 minutes, as after a good one. Every other pass makes no request for it, and an issue the listing has that the daemon holds is read no more often than before.
- **Reloading.** Each iteration first syncs the bare clone and reloads config and trust from `main` (3.4, 3.5). If that fails, the last good ones stay and the failure is logged. A config that allows a new model gets the model's labels created (section 15), tried again each iteration until that succeeds.

### 8.2 Leases and restart

- **On pickup.** The daemon writes `/state/lease.json` (write to a temp file, then rename) with the issue number, stage, run ID, clone path, start time, and the time of the last poll before pickup (6.4). It also records what the run read: the newest comment on the issue (the run's `seen`, section 5), the last edit time of each input and of the body (`body_edit`), and the run's resolved model, effort and fallback models (3.3), and for an implementer run the named starting SHA and any named target SHA (3.4, not built yet). A triage run's lease records the stage `intake`, which is what the daemon reads for an issue with no stage label. For a task, the `stage:in-progress` label and the transition marker show the lease on GitHub. A non-task run doesn't move its issue, so the lease's stage is the one a reset returns to.
- **Attempts.** The lease names the round of attempts the run belongs to and its number in it (8.3). When a run ends, failed or not counted, the lease is first marked ended with the count of failed attempts in a row it leaves, and for a failed run, what the attempt cap's error says of why it failed (5.3); then the run's files are deleted, and the lease too if that count is 0. A restart that finds an ended lease only takes its count and deletes what's left. The lease holds only the latest run, so every other count, such as another issue's, is held in memory and resets on any restart.
- **Saving the result.** When claude exits, its output is written to `/state/runs/<run-id>.json` through a temp file and a rename, and then `/state/runs` is synced, so the result survives a crash. If any of that fails, the run is a failed attempt (8.3), even when the output is valid. The daemon doesn't apply a result it couldn't save from memory: a crash part way through that apply would leave no saved result for the restart to finish it from (5.2), so the run would count as failed and the stage run again on top of what it wrote. And a save that keeps failing reaches the attempt cap and its state error, instead of running the stage without end.
  - One gap remains, when the ended lease can't be written either (see Attempts): the lease then stays the run's, and the next pass resumes it as a restart would. If only the sync failed, the result was renamed into place, so the next pass applies it, once, though the run was already counted as a failed attempt. Otherwise there's no saved result, and the next pass counts the run as failed again, as the same attempt, not another. A crash before the ended lease is written leaves the same lease, so the restart applies the result if the rename survived, and otherwise counts the run as a failed attempt.
- **On apply.** The daemon reads the issue again and applies the result through its `run=<run id>` key (5.2). It drops the result, writing nothing and counting no attempt, when the issue is closed or gone, even if the run's move is written already. Unless the move is written already, it also drops the result in these cases, and every stage follows the same rules:
  - The issue's stage changed during the run, since the owner's change wins. A triage result is also dropped once the issue has a stage label or a transition marker.
  - The named target moved to a tip the daemon doesn't name (3.4). Not built yet.
  - An input was edited or deleted since the run read it, or the body has a later edit by anyone but the App. The stage runs again on what's there. The App's own edit, such as one a result applied part way made before a restart, doesn't drop it.
  - A clean App transition marker sits in a comment above the run's `seen`, even a move back to the stage the run ran at, such as a changed child's move (6.4), or a hold that ended back there. The stage runs again on what's there now.
  - The issue has new trusted input since the run's `seen`: a comment above it by a trusted user that isn't a command and isn't dirty. The stage runs again with that comment as input. Without this, an answer step 1 👍'd before a delayed apply would be lost. So a comment posted during a run that resumes from a lease, after a crash, a restart or labels held back, is the next run's input, under its move's `seen`, when the resumed apply's read lists it, and no revision request at the review stage the move lands at (7.4, #318). One posted after that read, before the move is written, is above the move's `seen`, so it's a revision request there.
- **Checks.** A stage may check its result past what the schema can say, on the issue read again, before anything is written. The interviewer, the planner and triage do (9.1, 11.3, 6.2). A broken rule is a failed attempt (8.3), with nothing written. A result whose move is written already isn't checked again. A GitHub read that fails during the check says nothing about the result, so it isn't a failed attempt: it is a failure to apply.
- **Failing to apply.** A result that fails to apply keeps its lease, and the next pass tries again. After `loop.max_attempts` failures, the run is a failed attempt (8.3). While the issue has unexplained labels held back (5.1), the result waits with its lease, uncounted, and no other run starts; once they're left out, it applies without them. The read before a run and the attempt cap's check leave them out too.
- **On startup.** The daemon reads the lease.
  - First it checks the issue for discussion triggers since the last poll before the run was picked up (6.4). If the issue is held or closed, it deletes the clone and leaves the issue as it is. A valid saved result is dropped. Without one, the run counts as a failed attempt, unless it hit a usage limit or a marker shows the result was applied. The lease is deleted, unless it holds a count of failed attempts in a row (see Attempts): then it stays, marked ended, with that count.
  - If `/state/runs/<run-id>.json` exists and validates, and for an implementer run the clone also has commits ahead of its base, the daemon applies the transition.
  - Otherwise, unless a marker shows the result was applied before the restart, the run counts as a failed attempt (8.3). The daemon deletes the clone, resets the issue to its pre-run stage and starts the run again.

### 8.3 Retries

- The verify loop allows `max_attempts` (default 3) implementer runs per round. A round starts when a task becomes `ready`, or when a review with comments sends it back (7.2).
- Each retry prompt includes the previous verifier findings verbatim, and each retry runs one effort level higher, up to `stages.max_effort` (3.3).
- After the last failed attempt, the task moves to `stage:needs-human` with the findings attached.
- **Other stage runs.** A failed triage, interviewer, planner or story-verifier run is tried again, up to `loop.max_attempts` (default 3) runs in a row per round. A round starts when the issue moves, or when it gets new input. For triage, only a way into the pipeline (6.2) ends it, since triage's input never starts a new round. After the last failed attempt, the issue gets one state error, `kind=attempts` (5.3), naming why the last attempt failed when the daemon wrote the cause itself, or else pointing to its log, and the stage doesn't run again until the round changes.
  - A run fails when its result isn't a `success` or is an error (3.3), when its output fails validation or the stage's check (8.2), when it times out, when its result can't be saved or it leaves no valid result across a restart (8.2), or when its result fails to apply `loop.max_attempts` times. A GitHub read that fails inside a stage's check is a failure to apply, so it counts only toward that limit.
  - A usage limit (3.3), a failure to start the run, a shutdown and a dropped result (8.2) don't count, nor an apply held back by unexplained labels (5.1).
  - A result asking for a transition the table lacks isn't an attempt either. It gets one state error, `kind=transition`, and the stage doesn't run again until the issue moves, gets new input, or changes type or parent. When the type is the cause, the type error (5.3) stands for it instead, and the stage waits while a type error has been reported on the issue and the type is still the cause, as 5.3 says under Holding back.
  - **The interviewer is an exception to that rule.** Its check (9.1) fails a result that would leave the issue with no move, before anything is written. The main case is typing an issue with a parent as `story` (section 4): the table moves only a story with no parent to `spec-review`, and the interviewer doesn't run on a story with a parent but at the `clarifying` after a hold from a stage of its plan, so a round would get no answers read. Such output is invalid, so it is a failed attempt, not a `kind=transition` state error. After `loop.max_attempts` of them, the owner gets the `kind=attempts` state error. A result on an issue the interviewer no longer runs on, such as one the owner retyped as a task or gave a parent during the run, is a failed attempt too.

## 9. Owner interaction

The owner should never have to go and work out what is being asked.

Bot-created issues do not subscribe the owner to notifications. So every question round, typed comment, spec, plan, human task and triage flag @mentions the users in `notify` (section 13), and so does every new digest item that its own comment doesn't, such as a state error (9.4). Each of these comments, and the digest's announcement, carries a `cc @<login> @<login>` line: at the end, or for a plan, just before how to approve it (11.4).

Agent text can't mention anyone: the daemon puts a zero-width space after each `@`, or HTML entity for one, that isn't followed by a space. Lines inside a code fence the agent kept are left as they are, since GitHub never mentions anyone in code. It also escapes markers (5.1) and HTML tags in agent text.

### 9.1 Questions

Questions go in one comment per round:

```
### Questions for #123 (round 2)

**1. Where should the quote expiry be enforced?** Blocks: #130, #131
   a. Server-side on booking (recommended): one place, covers PWA and MCP
   b. Client-side countdown only
   c. Both

**2. ...**

Reply in one comment, e.g. `1a 2c 3: free text`.
```

The comment then ends with the `cc` line (section 9).

A question's text goes inside the App's bold, so nothing in it may close the bold or open anything that swallows its end: outside a code span, each `*`, `_`, `[`, `]`, `~` and `\` in it is backslash-escaped, and so is each backtick that doesn't open a code span the text closes itself. A bare URL that GFM links, `http://…`, `https://…` or `www.…`, keeps its `_` and `~`, which can't close the bold, so GitHub links it whole. Its other escapes stay, as in a title (9.4), and cut the link short. GFM leaves trailing punctuation out of the link, so a `_` or `~` there is escaped. The text reads as typed, its code spans render, and only its own emphasis and links don't. A triage flag's summary (6.2) is escaped the same way.

Rules:

- Each question stands alone, lists what it blocks, and offers 2 to 4 different options with the recommended option first and marked.
- Free-text answers are always allowed.
- Questions wait for an answer indefinitely. There is no default-on-silence.
- The interviewer and the planner each ask at most `max_questions_per_round` (default 7) per round, most blocking first.
- **The type line.** Every comment that sets a type starts with `Type: <type>, because <reason>`: a question round, a typed comment or a spec's revision comment (11.1). On an issue with no type, the interviewer's first comment starts with it, or with its questions when it can't tell yet (section 4).

**When the interviewer runs.** It runs at `clarifying` on an epic, a story with no parent, or an untyped issue, and at the `clarifying` after a hold from `planning`, `plan-review` or `planned` on a story with a parent too (#195's Q1a), in two cases:

- **On entry.** The latest transition entered `clarifying` by anything other than an interviewer run: a move into the pipeline (6.2), `/revise` or a revision request, an override, or the end of a discussion hold (6.4). The end of a discussion hold is the move out of `held` once its triggers are resolved, or by a `/resume` after a trusted response resolved one, whose marker carries `at`, even when the hold began at `clarifying`. It runs at once, with no input needed.
- **After a round.** The latest transition is an interviewer run's `clarifying → clarifying`, and there is at least one trusted answer since (9.2). Commands, App comments and dirty comments don't count. A hold the issue went back from by any other `/resume`, restoring `at` to `clarifying`, doesn't count as a transition here, so its round still waits for an answer.

Any answer starts the next run, including a partial one. That run sees every answer so far and asks again whatever is still open. Rounds end when it returns a spec. There's no cap on rounds. A bug and a task get no runs, nor does a story with a parent anywhere else (7.2).

**A story with a parent.** Its body is its item of its parent's plan, so the interviewer never rewrites it, and its parent's plan gave it its type. So at the `clarifying` after a hold from a stage of its plan, it may return only `questions`, `unchanged` and `plan`, with no `type`, and its preamble says to leave the type out (section 12). In phase 2 most stories have a parent, and this lets a discussion send a story's own task plan back to `planning`.

**Rounds.**

- A round's transition marker carries `round=<n>` and `questions=<count>` (section 5), so round numbers and question IDs come from markers, not from comment text. Question `<k>` of round `<n>` has the ID `Q<n>.<k>`.
- A round is numbered one more than the highest round on a clean round marker, the interviewer's or the planner's. The two stages share one numbering per issue, so question IDs and the digest's keys never repeat: after interviewer rounds 1 and 2, the planner asks round 3, and an interviewer round after that is round 4. The interviewer's checks and decisions (11.1) count only its own rounds, and its preamble says the planner's questions aren't its own (section 12).
- A round whose comment is dirty (5.1) isn't read, so it counts as 0 questions. If it was the latest round, its marker no longer counts and the next round takes its number: the round is cancelled, and its stage runs again. Under CODEOWNERS trust (6.1), a write collaborator who isn't trusted can edit an App comment, so they can do this.

**The interviewer's outcomes.** Its output is one object whose `outcome` is `questions`, `spec`, `typed` or, after a discussion hold, `unchanged` or `plan`:

- `questions`: a round in the format above, at `clarifying`.
- `spec`: the spec, written into the body and posted as a revision (11.1). The issue moves to `spec-review`.
- `typed`: only for an issue whose type the interviewer may set (section 4), when it finds the issue is a bug or a task. It sets the type, and its comment has the type line, then "Bugs and tasks wait at `clarifying` for now, until issuedog can implement them (build phase 3), so I won't ask anything more here.", then the `cc` line. The move is `clarifying → clarifying`, with no `round` or `questions`. The issue then waits (7.2).
- `unchanged`: only at the `clarifying` after a discussion hold from another stage, when nothing in the discussion changes the issue, with a message at most. The issue goes back to `origin` with no new revision, so a spec revision at `spec-review` that the body still matches stands, and so does a plan revision at `plan-review` that nothing keeps from approval (7.4). Its comment names the revision that still stands, says how to approve it, and ends in the `cc` line (6.4). A `/revise` that waited through the hold is used up all the same (6.4).
- `plan`: only at the `clarifying` after a discussion hold from `planning`, `plan-review` or `planned`, on an epic or a story, when the spec stands but its plan changes: its stories or tasks, their order, or what one of them covers. It has a `message`, always, written as notes for the planner, and nothing else. The issue moves `clarifying → planning`, and the marker carries `replan=1` (section 5) and `origin` (6.4), so the next plan waits for review (7.2). Its comment says the discussion changes the plan but not the spec, then the message, then that the planner posts a new plan for the owner's 👍, and ends in the `cc` line. The planner's next run gets the message, the discussion's owner input and each `/revise` the interviewer's moves after the hold named (6.4, section 12).

**Checks.** The daemon checks the output after its schema, and fails closed: a broken rule is a failed attempt (8.3), logged with the reason, and nothing is written.

- 1 to `max_questions_per_round` questions, each blocking at least one issue, with 2 to 4 options, no two the same. Options are the same when their text is, once case is ignored, leading and trailing space is dropped and each run of spaces is one space.
- One-line question, option, reason and list item text.
- A `type` only where the interviewer may set one (section 4). `typed` sets bug or task. A round or a spec sets epic or story, and a spec on an untyped issue must set one.
- The Decisions rules (11.1). A decision's `by` is a login with a clean, trusted comment on the issue, and its letter names one of its question's options.
- Every text it renders fits GitHub's 65,536-character limit, with 1,024 to spare.
- The move fits the issue once its type is set, and the issue is still one the interviewer runs on (8.3).
- `unchanged` only at the `clarifying` after a discussion hold, and not when `origin` is `clarifying`.
- `plan` only with a message and nothing else, on an epic or a story, at the `clarifying` after a discussion hold from `planning`, `plan-review` or `planned`.
- On a story with a parent, never `spec` or `typed`, and no `type`.

**When the planner runs.** It runs at `planning` on an epic or a story, with or without a parent, in two cases:

- **On entry.** The latest transition entered `planning` by anything other than a planner run, such as the spec's approval, a created story's first move (7.2), a plan sent back (7.4) or an override. It runs at once, with no input needed.
- **After a round.** The latest transition is a planner run's `planning → planning` round, and there is at least one trusted answer since (9.2). As for the interviewer, a hold the issue went back from by `/resume` doesn't count as a transition here, so its round still waits for an answer.

On an issue that was `planned` before, as any clean transition marker to `planned` shows, its plan is a revision of its approved plan (11.3), however the issue came back to `planning`: by the interviewer's `plan`, a changed story's move (6.4) or a stage set by hand. One whose approved plan revision doesn't read back with its data (7.4) gets no run, as a revision couldn't be checked against its children: the daemon logs it once and runs nothing.

**The planner's outcomes.** Its output is one object whose `outcome` is `questions` or `plan`:

- `questions`: a round in the format above, at `planning`. Its move is `planning → planning`, with `round` and `questions`. Its questions use the interviewer's shape, so they block issue numbers, usually the issue being planned.
- `plan`: the plan comment (11.4), which is a plan revision (7.4). The issue moves to `plan-review`, or for a story's first plan with `plan.review` false, to `planned` (7.2). A revision always moves to `plan-review`.

Its checks are 11.3's.

### 9.2 Commands

| Command | Where | Effect |
|---|---|---|
| `1a 2c 3: text` | Issue | Answers the latest question round |
| 👍 on a revision comment | Issue | Approves that revision (7.4) |
| `/approve` | Issue | Approves the current spec or plan revision |
| Any comment that is not a command | Issue in `spec-review` or `plan-review` | Sends the spec or plan back, with the comment as the notes (7.4) |
| `/revise <text>` | Issue | Sends the spec or plan back with the owner's notes |
| 👍 on the issue | Human task, from the planner, or for a story branch's failure (9.3, not built yet), at `needs-human` | Same as `/done` on it: runs its **Done when** check, once for each 👍 (9.3) |
| 👍 on the latest hand-off comment | Blocked task at `needs-human` | Same as `/done` (9.3) |
| 👍 on a state-error comment | Any issue | Acknowledges the error (5.3). The stage doesn't change |
| 👍 on the latest triage flag | Issue at `intake` | Takes the flag's recommendation: admits the issue, or leaves it to people (6.2) |
| `/track` | Issue at `intake` | Admits the issue, flagged, left or never triaged (6.2) |
| `/ignore` | Issue at `intake` that isn't in the pipeline | Leaves the issue to people (6.2) |
| `/done` | `needs-human` issue | Owner finished the human task, which runs its **Done when** check (9.3), or wants a closed PR's task started over. Not built yet: starting a task over is phase 3's, and until then `/done` on a task that isn't a human task is rejected as not handled yet |
| `/hold`, `/resume` | Any issue | Pauses or resumes the issue and its descendants. `/resume` also ends a discussion hold (6.4) |
| 👍 on an untrusted comment or a hold notice | Issue held for discussion | Approves the comment, as the text the 👍 post-dates, or accepts the edit, deletion, rename or close the notice names. Accepting an edit ends its hold but doesn't approve the edited text (6.4) |
| `/priority p1` | Any issue | Sets priority |
| `/model <name>`, `/model verifier <name>` | Any issue | Sets the model of the issue's runs other than the verifier's, or with `verifier`, of its verifier runs (3.3) |
| `/effort <level>`, `/effort verifier <level>` | Any issue | Sets the effort the same way (3.3) |

A comment is a command when its first line is a slash and a word, such as `/priority p1`. A known command followed directly by more text, such as `/approve.`, is that command with a bad argument. An unknown word followed directly by more text, such as `/usr/bin`, is plain text. Only comments by trusted users that aren't dirty (5.1) count, oldest first. A `/hold` or `/resume` also waits for one posted before it on an ancestor (6.4).

- **Applied.** The daemon reacts 👍 to each command comment it has applied, after its marker (5.2). GitHub has no ✅ reaction. A reaction command is acknowledged by the transition comment (5.2).
- **Rejected.** A command that doesn't apply, because it is unknown, has a bad argument, doesn't fit the issue's stage or fails its own check, gets the App's 👎, then a reply with the reason carrying `<!-- issuedog:reply reason=rejected cmd=<comment id> -->`. The 👎 is the record that it was processed: a reply can be edited or deleted, but only the App can remove its own reaction. A command with the App's 👎 but no clean reply gets its reply posted again, worded from the issue as it is then, or saying the reply was lost when there's no reason to give now. A comment edited after the 👎 isn't judged by its new text: the reply says the reply was lost, and that the edit is ignored. A reply asks for a new comment only when a new one could apply; when it couldn't, the reason says what the owner can do instead (7.4). So the edited comment's reply asks for one unless its new text is a command or a revision request that a new comment with that text would see rejected the same way, and then gives that reason instead. A reply already posted counts by its marker, whatever its wording. A rejection isn't a state error (5.3). The reply to an unknown command lists the commands, `/track` and `/ignore` included.
- **Processed.** A comment is processed once a `cmd` or `reply` marker names it, or it has the App's 👍 or 👎. It is never applied again.
- **Edited.** A comment edited after the App used it gets one reply asking for a new comment, carrying `reply reason=edited cmd=...`, and the edit is ignored. That covers a command edited after its 👍, even into plain text except as below, and an answer edited after a later transition's `seen` covered it. A rejected command edited later gets no new reply, and never counts as an answer.
- **Answers.** At `clarifying` or `planning`, a trusted comment that is not a command, posted after the round bound, is an answer to the current round, and gets a 👍. The bound is the latest transition marker's `seen` (section 5), or, if it has none, the ID of the App comment holding that transition. Comment IDs only increase, so a comment posted during a run belongs to the next round. Only transition markers move the bound: a reply, error, revision or dirty marker doesn't, so a rejection posted at `clarifying` or `planning` keeps that round's answers. A command or answer edited before the App uses it is read with its latest text.
- **Model and effort.** `/model` and `/effort` work like `/priority`: each adds one label, `model:*`, `effort:*`, `verifier-model:*` or `verifier-effort:*`, removes the others of that kind, then 👍s the comment, with no marker (5.2). `verifier` matches in any case.
  - `/model` takes a full name on `models.allowed` or an entry's label suffix (section 13), ignoring case, and sets the label with that entry's suffix. A name that matches more than one full name only when case is ignored must be given in its exact case.
  - `/effort` takes `low`, `medium`, `high`, `xhigh` or `max`, ignoring case.
  - A missing or extra argument, a model not on `models.allowed`, or an unknown level is rejected (see Rejected). For a model or level that isn't allowed, the reply lists the allowed label suffixes, or says the config allows no model, or lists the levels.
  - Each write is checked first, so a replay after a crash redoes only what's missing. If a reload dropped the model from `models.allowed` after the label was added, the replay still finishes rather than rejecting the command.
- **Commands edited into answers.** The App 👍s both applied commands, such as `/priority`, which writes no marker, and answers, so GitHub can't tell them apart. An applied command edited into plain text at `clarifying` or `planning`, in the current round, therefore becomes an answer, and the interviewer or planner reads the edited text. A command that a marker names, or that the App 👎'd, isn't.

PR reviews use GitHub's own review flow.

### 9.3 Human tasks

A task reaches `stage:needs-human` in one of three ways:

- **Blocked work.** A task needs an owner action: the implementer reports it, the retry cap is reached (8.3), or its PR was closed without merging, or merged into its story branch by someone untrusted (7.5). The daemon posts a hand-off comment using the template below. On `/done`, or a trusted 👍 on the latest hand-off comment, the task returns to `stage:ready`. A 👍 on an earlier hand-off comment, or on the issue itself, doesn't resume blocked work. Not built yet: hand-offs are phase 3's, and until then `/done` on a task that isn't a human task is rejected as not handled yet.
- **Planned work.** The planner emits a task marked `human`, such as creating an App or a ruleset (section 11.3). The daemon creates it after its plan's other children (5.2) and moves it to `stage:needs-human` by its first move (7.2). The owner signals done with a trusted `/done` or a trusted 👍 on the issue itself. When **Done when** has a check (11.3), the daemon runs it first (see Running the check): if it fails, the daemon replies once with what it found and leaves the issue open. Otherwise it closes the issue as completed (7.2).
- **A story branch's failure.** Not built yet (7.5). When a story branch's tip fails rule 2, the daemon files a human task under the story, with `human=1` on its `origin` marker, which names the failing tip (section 5), and moves it to `stage:needs-human` by its first move (7.2). Its body is this template. It's a human task, so a trusted `/done` or 👍 on the issue closes it, as for planned work, and never sends it to `ready`. Its **Done when** is the daemon's own check, not one of the planner's five kinds: the story branch's tip is no longer the failing tip its `origin` names. While it still is, a `/done` or 👍 is rejected with a reply saying so, as a failed check is (see Running the check), and the issue stays open, so the owner always has it to act on. Closing it doesn't release the story's tasks: only a passing tip does.

A `stage:needs-human` issue uses this template. The agent must fill every field; an empty field is a validation failure, and the agent asks a question instead.

```
**Goal:** one sentence
**Why it blocks:** #N cannot proceed until ...
**Steps:**
1. exact action, with exact values, commands or settings
2. ...
**Links:** direct links to the console page, file, or doc
**Done when:** observable result the owner can check
**Estimated time:** 5 min
```

A human task created from a plan gets this body from its plan item: the task's **Parent** line (11.2), then these fields, each filled, then the `cc` line (section 9), and last its `origin` marker with `human=1` (section 5). Its **Why it blocks** names the issues of the items that depend on it, or the parent when none does, in number order, then the planner's reason: `#12 and #13 can't proceed until <reason>` (#250's Q2a). Those issues exist by then, since human tasks are filed after the plan's other children, each after every human task that depends on it (5.2), so the body is written once, with real links. Its **Done when** is the planner's text, or for a check the daemon can run, the daemon's own sentence naming what it checks, each value as inline code, such as "The file `go.mod` on `main` contains `go 1.25`.", then "I check this when you reply `/done` or react 👍 to this issue." The planner's text isn't shown then: the sentence says exactly what the daemon checks. The check itself is on the `origin` marker (section 5).

**The checks.** The daemon runs a check itself, as `issuedog`, never in a stage run. It reads only data: the App's GitHub reads, with its installation token, or its JWT for `installation`, and one blob from its bare clone. It runs no command from the repo, and no agent text, since a check is one of the five kinds with values 11.3's validation accepted. So sections 3.1 and 3.2 hold. Each kind, with its read:

- `label`: `GET /repos/{owner}/{repo}/labels/{name}`, with Issues read. It passes when the repo has the label, matched ignoring case, as GitHub matches label names. A 404 fails.
- `issue-type`: `GET /orgs/{org}/issue-types` for the repo's owner, with the organization permission Issue Types read. It passes when the owner has an enabled issue type of that name, ignoring case. A disabled one fails. A 404 fails too, saying the owner is a personal account, which has no issue types (section 16).
- `file`: `main:<path>` in the daemon's bare clone (3.2, 3.4), as of the sync at the start of the pass (8.1), which costs no request and has no size limit. It passes when the path is a file and, with `contains` set, the file holds that text exactly, byte for byte. A missing path, or a directory, fails. The reply never quotes the file.
- `ruleset`: `GET /repos/{owner}/{repo}/rules/branches/main`, every page, with Metadata read. That lists only active rules, org rulesets included: a ruleset in evaluate mode or disabled isn't listed. It passes when a required-status-checks rule names a check whose context is exactly the name, from any source. A failure lists the checks the rules do require, or says none do. A 404 is no rules. Classic branch protection needs Administration read, which the App doesn't have (section 15), so it isn't read and doesn't count.
- `installation`: `GET /app/installations`, every page, with the App's JWT, as `GET /app` at startup is (3.5). An installation token is refused there, and it needs no permission. It passes when the App has an installation on an account with that login, ignoring case, that isn't suspended. A suspended one fails.

**Running the check.** Each trigger runs the check once, so nothing loops:

- **`/done`.** A trusted `/done` on a human task at `needs-human` runs it when step 1 handles the command (9.2). A pass closes the issue as completed, `needs-human → closed`, keyed `cmd=<comment id>` with `seen` the comment, and the App 👍s it (7.2). A failure gets the App's 👎 and the rejection reply (9.2), carrying `reply reason=rejected cmd=<comment id>`, which says what the check found. The issue stays open.
- **A 👍 on the issue.** The daemon reads the issue's own reactions, not a comment's, with a conditional request: `GET /repos/{owner}/{repo}/issues/{n}/reactions`. The newest 👍 by a trusted user (6.1), not a bot, that no marker names counts, so each such 👍 counts once, the newest first. A pass closes the issue as completed, keyed `cmd=r<reaction id>`, with `seen` the newest comment read. A failure gets one reply, quoting the 👍 and its user, saying what the check found and how to check again, and carrying `reply reason=rejected cmd=r<reaction id>`. The issue stays open, and the next pass checks no 👍 the marker names.
- **Plain text.** A **Done when** with no check has nothing to run, so `/done` or a 👍 closes the issue at once.
- **Unreadable.** A check whose fields on the `origin` marker couldn't be read (section 5) reads nothing and always fails, saying the check couldn't be read. So the issue never closes without its check.
- **Checking again.** Post `/done` again, or remove your 👍 from the issue and add it again, which makes a new reaction.
- **A failed read isn't a failed check.** A GitHub read, or the bare clone's, that fails gets no reply and writes nothing: the issue's visit fails, and the next pass tries again.
- **Who counts.** A `/done` or 👍 from an untrusted user, a bot or the App does nothing, though a write collaborator's `/done` comment still holds the issue (6.4). While the issue is held, `/done` and a 👍 wait (6.4): the 👍s are read only at `needs-human`, so one given during the hold counts once the hold ends there.
- **After the close.** The close judge sets `stage:completed` (6.4). A trusted reopen holds the task at `needs-human` (7.2).

### 9.4 Digest

One pinned issue per repo, `issuedog digest`. It uses one of the repo's three pin slots.

- The body is the current list: open questions, pending approvals, hand-offs and unblocked human tasks, PRs waiting for review, issues held for discussion (6.4), dropped children with an open PR (6.4), triage flags waiting on a code owner (6.2), stories whose children have all closed (7.3), and state errors (5.3). These are exactly the items the daemon assigns (9.6), but for a closed issue's `closer` state error, which isn't assigned (5.3). Each state error is also posted on its issue as a comment (5.3). Items are ordered by how much each one unblocks (see The order).
- Each item states what is being decided, the options, the recommendation, and links to where to answer.
- The daemon rewrites the body when the list changes. It posts a short comment that @mentions `notify` only when a new item appears: one comment per pass, listing every new item, so a burst is one notification (see Announcing new items).

**Finding it.**

- The digest is an issue the App authored (`<slug>[bot]`, 3.5) that meets one of these:
  - its body has `<!-- issuedog:digest -->`, its identity marker;
  - this daemon has already found it to be the digest;
  - its title is exactly `issuedog digest`, and it never had an `origin` marker, which every other issue the App creates has (5.2): see The title rule.
- The daemon finds it in the poll's issue list, which is `state=all` and listed in full on each start, with no search. A closed digest is still the digest.
- If more than one issue qualifies, open or closed, the lowest number is the digest. The others are logged and left alone.
- The identity marker is read even in an edited body (5.1). Once the daemon has found the digest, an edit that removes the marker, by anyone, changes nothing: the next pass writes the body again, marker and all. The title rule finds a digest whose marker was removed while no daemon ran.
- **The title rule.** An App task whose body lost its `origin` to an edit, or had it escaped by a dirty note (5.1), and that someone renamed `issuedog digest`, must not be taken for the digest, whether its `origin` was reposted or not (6.4). So an issue the App authored, titled `issuedog digest`, with no identity marker and no `origin` marker in its body as listed, is taken only once the poll's comments are in, and only if both hold:
  - no App comment on it carries an `origin` marker, edited or not, judged from the comments the poll lists anyway;
  - the App's first version of its body had none: its body as listed, if it was never edited, or else the original post in its edit history (5.1), which is read once per start for each issue the rule would otherwise take, all in one query. An original post whose text was deleted can't show it had none, so it counts as having had one.

  Such an issue that isn't taken stays as it is, in the pipeline if it was, and its body is never written.
- **A failed history read** is logged, and judges none of the issues it was for. Each stays held, unjudged: out of step 1 and stage work, with any items it had dropped from the digest, and no digest is created while one is held, since it may be the digest, and a new one would be a second (#305). Each later pass reads again, in one query, the histories of the issues still held, so the first pass whose read works takes back a digest whose marker was removed. A node the read finds gone, null with GitHub's `NOT_FOUND`, is an issue deleted since: it's let go, as when the error's post finds it gone (5.3), and the same query's other histories are judged. A poll that lists a held issue again judges it on that listing: renamed, or with its identity marker back, it's held no more. After `loop.max_attempts` failed reads on a start, the issue gets a `kind=digesthistory` state error (5.3), and from then on its history is read once every `loop.max_attempts` passes, so the hold ends on its own once reads work again (#437). It stays held, and no digest is created, until a read works or the owner acts: a restart reads it again at once, a rename lets the pipeline take it as any other issue, and its identity marker put back makes it the digest. So with no other digest, the repo has none until then, and the error says so.
- **Out of the pipeline.** The daemon never takes a snapshot of the digest, so step 1, the label rules, intake, stage runs and triage never see it. Its labels, comments and commands are ignored, with no reply.
- **Gone.** A request that finds the digest deleted or transferred drops it, and the next poll lists every issue again, to find it or create one. The items it announced are kept in memory until a restart, so a digest found again after a one-off 404 never announces them twice. GitHub never reuses an issue number, so this can't hide an announcement on a new digest.
- **A renamed repo** looks like a transfer to the digest's writes. Each write fails with a warning, and the daemon lists every issue again, which finds the same digest, so there's no second one. Every issue's read fails as a transfer too, so a rename needs `ISSUEDOG_REPO` (3.5) changed.

**Creating and pinning it.**

- On the first pass that finds no digest, the daemon creates one, titled `issuedog digest`, listing the current items. That happens in the loop, not at startup, so a failure doesn't stop the daemon (3.5). After a crash that follows the create, the next poll finds the issue, so there's no duplicate.
- A new digest's body starts with a pin note: "I couldn't pin this issue yet. If this line stays, pin it by hand." While the body starts with "I couldn't pin this issue", the first pass of each start that finds the digest open checks GraphQL `isPinned`. If it isn't pinned, the daemon pins it with GraphQL `pinIssue`. Then it writes the body without the note.
- If GitHub refuses the pin, or answers with no pin, the daemon logs an error, and the note becomes "I couldn't pin this issue: `<GitHub's message>`. Pin it by hand." The cause could be the undocumented permission (section 16), or three pinned issues already. The next start tries again.
  - A refusal is a GraphQL error, or an HTTP 401 or 403 answer to `pinIssue` that isn't a rate limit, as a missing permission may come either way (#226). For a 401 or 403, GitHub's message is the status and the message in its answer, such as `HTTP 403: Resource not accessible by integration`.
  - GitHub's message is cut to 200 characters, the last of them "…", so the note stays one short line, and escaped after the cut (5.1).
- Any other failure, including the `isPinned` check's, is logged, and the note becomes "I couldn't pin this issue yet: checking whether it's pinned failed (HTTP 502). I'll try again when the list changes, or pin it by hand.", or "pinning it failed" for the pin, naming the HTTP status when GitHub answered with one, but nothing else of the error, which the log has. It stops nothing: the pass announces new items and writes the body under that note as usual (#226). The check is tried again only on a later pass that writes the body anyway, as the list or the body changed, even by an edit that took the note out, or on the next start. So a check that fails once leaves the digest unpinned until the list or the body changes or the daemon restarts, and one that fails on every pass adds no request to an unchanged pass, and no body edit of its own to a changed one.
- A check or pin that finds the digest gone, deleted or transferred, writes nothing more to it, and drops it (see Gone). The check finds it gone by GraphQL's `NOT_FOUND` error for the issue, which GitHub answers, with an HTTP 200, for a deleted or transferred issue's number. An HTTP 404 or 410 from the GraphQL endpoint itself, to the check or the pin, says nothing of the digest, so it's any other failure (above) (#428). `pinIssue` takes the issue's node ID, which the daemon reads with a REST GET of the issue first, and node IDs are global, so it would pin a transferred digest in its new repo. A GET that GitHub answers from another repo, by following its 301, or whose issue names another repo, pins nothing, and the digest is gone (#413).
- A failure never stops the loop.
- Once a pin has worked, the daemon never pins again, so an unpin by the owner stands.
- Pinning doesn't change an issue's `updated_at` (checked live, #154).

**Closing it.**

- A close by a trusted user (6.1), not a bot, turns the digest off until a trusted user reopens it: no edits, no comments and no pin. No other digest is created meanwhile.
- Any other close or reopen is reverted, as 6.4 does for any issue. A reopen after a trusted close is closed again. The digest is never held by its own close or reopen, so the revert is silent: no notice is posted.
- Which close stands is read from the timeline, so it holds across restarts. A closer who later loses trust no longer counts, so the next read of the timeline reopens the digest.
- The timeline is read only for a digest that was ever closed, and only when its listing changed other than by the App's own write, except while a close or reopen is looked at again, below: during the wait for a reopen's event, and while a close is still the newest event after it, it's read on every pass.
- Each read of the timeline asks trust about the actor of each close or reopen event, with no cache: one permission request for each such event by someone CODEOWNERS names, or by anyone with no CODEOWNERS file (6.1). Their number grows with the digest's history, and while a close is the newest event they're made on every pass.
- A close or reopen whose event GitHub hasn't written yet is looked at again on the next pass, with nothing reverted.
  - A close's event must be from the digest's `closed_at` on. Until it shows, the digest, listed closed, is off.
  - A reopen clears `closed_at`, so the reopen that made the digest open is waited for when the newest close or reopen event is a close, or a `reopened` event older than the digest's `updated_at`. That may be an earlier reopen's, with a later close's and reopen's events still to come.
  - While it's waited for, the digest is off: nothing is written to it. The wait ends once GitHub's clock is 30 seconds, as long as an issue with unexplained labels is held back (5.1), past the earlier of `updated_at` and the time a pass first found the digest waiting with that newest event. The daemon keeps that time in memory, and forgets it once the wait is resolved or the newest event changes, so the next change waits again. Later changes, such as steady comments, can't stretch a wait. GitHub's clock is the `Date` of its answers, so the writes held back land on the first pass after the 30 seconds, up to one `idle_sleep` later.
  - So on a digest that was reopened before, any change by anyone other than the App, such as a comment, a label or an edit, makes the newest `reopened` event older than `updated_at`, and holds the digest's writes back for about one pass at the default 60-second `idle_sleep`, or for several passes with a shorter one, never more than 30 seconds. That re-wait is deliberate: it's how a trusted close and an untrusted reopen that both come between passes are caught.
  - After the wait, an older `reopened` event is taken as the newest. While a close is still the newest event, the digest is on again, as it was before the wait existed, and the timeline is read on each pass until the reopen's event shows. The daemon forgets its last resolution then, so its own writes, which would otherwise look like nothing changed, don't end the reads.
  - So on a digest that was reopened before, a trusted close and an untrusted reopen, both within GitHub's event lag, are found once their events are written: the reopen is reverted, and the close stands. An event more than 30 seconds late is still missed, until the digest changes again or the daemon restarts.

**Items, and their keys.** Each item has a key that names it across passes and restarts. `<n>` is the issue number.

- **State error.** Each open error (5.3), and each `closer` error on a closed issue whose close stays unjudged (5.3). Key: `err-<n>-<kind>-<key>`. The item gives the kind and key, copies the lines of the error comment, and says to 👍 it. An error whose only copy is in the issue body says it ends when its cause is gone. A closed issue's `closer` error says instead that a 👍 won't acknowledge it, and that it ends once GitHub says how the issue was closed.
- **Discussion hold.** The issue is held, and a discussion trigger on it is open (6.4). Key: `hold-<n>-<id>`, where `<id>` names the transition marker that moved the issue into `held`, whatever hold it was, by its key (5.2): its `event=` as it is, such as a discussion hold's trigger key or a hand-set hold's label event, or else `cmd` and its `cmd=`, such as `cmd502` for a `/hold`, or else `run` and its `run=`. The first hold wins, and a discussion hold on an issue that's already held writes no marker, so the key stays the same while the hold stands, however triggers come and go, and a later hold has a new one. Only a marker with none of these keys, which the App doesn't write, falls back to the oldest open trigger's key. If the first hold's marker is later edited or deleted, so it is no longer read (5.1), the key moves once, to the marker that then begins the hold: a hand-set `held → held` marker, or the hold that 6.4 writes when an edit or deletion hides a hold's marker. Strictly, that later marker is then "the transition marker that moved the issue into `held`". The item lists each open trigger, oldest first, with who did what, a link and how a code owner resolves it:
  - a comment: a 👍 on it approves it, and a later comment of theirs counters it, other than `/hold` or `/resume`, which counter nothing. A comment known from its record alone is gone, so it says so and links the App comment that recorded it;
  - any other trigger: a 👍 on its notice, which it links, a close's included;
  - an edit or deletion of what may have been the App's content, which may have hidden a record (5.1), or a deletion while the issue was held, which may have hidden a code owner's `/hold` that wrote no marker: only `/resume`, as a 👍 on its notice could release a trigger whose record is gone, or a hold;
  - one with no clean notice, deleted, edited or never posted because an App comment was deleted or edited after the trigger: only `/resume`.

  It names an owner hold on the issue that stays once its triggers are resolved: one a marker records, or a `/hold` on the issue that writes none because the issue was held already, but not one that a `/resume` the App applied ended while the issue stayed held for another reason, as an `ended reason=owner` record says (6.4). A `/hold` on an issue above it that writes no marker on it is named once the App's record of the discussion's end names it, and so is a comment deleted above it during the hold that may have been one (6.4). It ends with `/resume`, which accepts every trigger. Logins are code and defused, and a rename's title is escaped as a heading's title is (below). A trigger known from its record alone says it was "recorded earlier".
- **Pending approval.** The issue is at `spec-review`. Key: `rev-<n>-<rev>`, the latest revision, or `rev-<n>-0` with none yet. If the revision can't be approved yet, the item says why: a dirty body, a dirty App comment after the revision that may hide a newer one, a body that no longer matches its hash, a type error that holds the approval back (5.3), a type that doesn't say what kind of issue it is, or a type that doesn't go on to `planning`.
- **Plan approval.** The issue is at `plan-review`. Key: `plan-<n>-<rev>`, the latest plan revision, or `plan-<n>-0` with no clean one, so it never clashes with a spec's `rev-<n>-<rev>`. The item names the revision and its hash, links the plan comment, or with no clean one the comment of the move to `plan-review`, which after a dirty plan comment is the App's record of it (5.1), says to 👍 the plan comment or post `/approve`, and says that `/revise <notes>` or any other comment sends it back. If the plan can't be approved yet, it says why instead of how to approve it, in this order: there's no clean plan revision, as none was posted, or it was edited without approval or deleted; an App comment after it was edited without approval or deleted, so it may hide a newer one; the plan comment changed after it was posted, so it no longer matches its hash; the body has an edit that wasn't approved; then the type's reasons, as for a spec, with `planned` in place of `planning`. After any of the first three only a new plan can be approved, so its last line says that sending it back gets a new plan (7.4).
- **Open question.** The issue is at `clarifying`, its latest transition is an interviewer round with `round` and `questions` of 1 or more (9.1), and no trusted answer has come since. Or it's at `planning`, and its latest transition is a planner round in the same way. Either looks through a hold the issue went back from by `/resume`. Key: `q-<n>-<round>`, and a planner round ranks as an interviewer round does: the rounds share one numbering, so the keys never clash. A typed bug or task's move carries neither field, so it gives no item while it waits for phase 3.
- **Triage flag.** The issue is at intake with no stage label, and its latest triage marker that counts is a flag, `verdict=ask` (6.2). Key: `flag-<n>-<comment id>`.
- **Human task.** The issue is a human task at `needs-human` (9.3), and every issue blocking it is closed, as its blocked-by links show: `GET /repos/{owner}/{repo}/issues/{n}/dependencies/blocked_by`, every page, read with a conditional request only for such a task, so an unchanged pass costs a 304. A blocker in another repo counts by its own state, and so does one someone else linked. Key: `human-<n>`. The item says a human task waits, copies its **Goal** and **Done when** from the App's clean body, without the sentence on when the check runs, says to reply `/done` or react 👍 to the issue, and links the issue. When the body isn't the App's clean one (5.1), or either field isn't found, it says to see the issue instead.
  - **Judged on each pass.** A blocker's close changes nothing on the task, so an issue at `needs-human` is visited on every pass (8.1), and the item appears on the first pass after its last blocker closes. A new open blocker takes it away on the pass that reads it. A failed read keeps the issue's last items, as a failed step 1 does (see Keeping the list). Closing the task ends the item.
- **Finished story.** The issue is a story at `planned`, or an epic at `planned` whose approved plan is a plan of tasks, which acts as its own story (section 4). Its `created` record (5.2) stands, every child the record names is closed, its close judged and accepted, with no close of one still to judge (6.4), and no open issue is left below it. Key: `done-<n>`. The item says the story waits for story verification (7.3), which runs by hand until phase 4, and to close the story once that passes. It lists the children the record names, or for a revision's `children=none`, says its plan's latest revision left it no children, and links the issue. Closing the story ends the item.
  - **Judged on each pass.** A child's close changes nothing on the story, so the item is found on the story's last visit and judged again on every pass, from what the poll listed and the snapshots held, with no request: every child the record names was last listed closed, and no open issue the daemon holds names the story as its parent. So a child created in this pass, which no poll has listed yet, can't make a story look finished. A child reopened, or an open issue added below the story, takes the item away until it closes again.
- A round's or a flag's questions and options are copied from the App's own clean comment, whose `**N. …** Blocks:` and `a. … (recommended):` lines have a fixed format. If they can't be read back, the item says to see the comment.
- Each item links to where to answer: `https://github.com/<owner>/<repo>/issues/<n>#issuecomment-<id>`, or the issue itself for an error in the body.
- Not built yet: hand-offs (9.3, phase 3), PRs (phase 3), and dropped children with an open PR (6.4, phase 3, #234). Each adds its own kind to the same list.
  - **Closed story PR**, with PRs: a story at `pr-open` whose PR closed without merging (7.5). Key: `story-pr-<n>-<PR number>`. The item links the PR, and says to reopen it or close the story. Reopening the PR or closing the story ends the item.
- **Keeping the list.** The items are cached per issue, and updated each time step 1 succeeds on it (8.1). An issue whose read or step 1 fails keeps its last items. One that closes or is dropped loses them.
  - A command, or a plan's children writes (5.2), on one issue may write to another before the other's visit, as a parent's `/resume` writes its `ended` record to a child (6.4). The other's snapshot is then out of date, so it skips step 1 that pass, keeps its last items, and is read again on the next. But one the digest may list items for that aren't cached is read again at its turn and visited instead, for its items: one the start's first poll listed, as the last daemon's body may list it, or one a poll listed closed with items, as a close reverted before the visits, each until step 1 succeeds on it. So a restart's first pass doesn't drop its items, writing the body without them, only to list them again on the next pass (#216). Read again, it still gets no stage work or assignment that pass, and is read again on the next, as any issue a command wrote to. A visit that fails, or waits for its next pass, after its command wrote to the issue may have left the command half done, so then the issue isn't read again: it waits for the next pass, where that command finishes before the issue's own. An issue first listed after the start, such as a child a plan just filed, was never in the digest, so it skips the pass as before. Each time, that's one more read of the issue in the pass, mostly on a restart's first. But it counts as not cached until a visit succeeds, so after its own visit failed, a later pass that writes to it before its turn reads it again too. The poll that lists every issue again once the digest was found gone isn't a start's first: the items stay cached, so it makes no issue count as not cached, and it judges the closes it lists as any later poll does (8.1). A pass that writes to no such issue reads nothing more. An issue whose own visit fails on a restart's first pass still has no items to keep, so it drops out of the digest until a visit succeeds (#360).

**The order.**

- Each item scores 1 plus the open issues below its issue, counted from the parents in the daemon's snapshots. Those hold only open issues, so an open issue below a closed one doesn't count toward the closed one's ancestors. Phase 2 adds the issues it blocks once dependencies exist.
- The highest score comes first. Ties go by kind: state errors, then discussion holds, then approvals, a plan's as a spec's, then questions, then human tasks, then flags, then finished stories, as story verification unblocks no other issue. Then by priority, p0 first (default p2), then the oldest issue, then by issue number, comment and key, so the same items always come out in the same order.
- **Plan order.** The plan approvals of issues one plan filed are listed together, in that plan's item order, `S1`, `S2` and so on, whatever their priorities (#248's assumption 8). The group sits where its best member would rank on its own by the rules above, and within it, items go by item number, then by those rules. An issue's plan and item come from its origin, from its body or a clean App comment, such as a reposted one (section 5, 6.4), so one with none, such as an epic or a story the owner filed, ranks on its own. Every other item keeps its place.

**The body.**

- The body is rendered the same way from the same items: it holds no times, relative or not. The pin note comes first, if there is one. Then a line says how many items wait, and each item follows: a heading `### <rank>. #<n>: <title>`, its kind, priority and score, its lines, and its link. With nothing waiting it says "Nothing is waiting on you." The identity marker is the last line.
- It's written only when it differs from the body last listed or written, ignoring CRLF line endings and the space around it.
- It has no `rewrite` marker (5.1).
- It must fit GitHub's 65,536-character limit, with 1,024 to spare: 64,512, counted as UTF-8 bytes plus one for each newline, which is never less than GitHub's count. Over that, the lowest-ranked items are cut, and a line after them says "…and N more, cut to fit GitHub's limit on an issue body."
- The body mentions nobody. Titles are escaped like any text the App didn't write (5.1, section 9): one line, tags escaped, mentions defused and markers escaped. `[`, `]`, `!` and `\` are backslash-escaped too, so a title makes no link, image or footnote. GitHub still autolinks a bare `https://…` or `www.…` in a title, and `owner/repo#1` still makes a cross-reference (section 16). Such a link shows its whole target and loads nothing.
- Lines copied from the App's own comments are defused and escaped again, and can't start a block such as a heading or a quote.

**Announcing new items.**

- An item is new when its key isn't in any `digest-new` comment of the App's on the digest that was never edited. An item that goes away and comes back with the same key isn't new.
- A new item gets the digest's mention only if its own comment doesn't mention `notify` already. Question rounds, specs, plans and flags end in a `cc` line, and so does a human task's body (9.3), so only state errors get it, finished stories, since no comment says a story's children have all closed, and discussion holds that no App comment mentioned.
- A discussion hold is announced by its triggers, not by its own key. A trigger is mentioned already when a clean App comment with a `cc` line records its key: the hold's own transition marker, or a notice (6.4). A comment trigger on an issue that was already held has neither. Nor has a trigger whose notice wasn't posted, unless the hold's own transition marker records it as `event=`, nor one whose record was edited or deleted since. Each trigger that isn't mentioned has the key `hold-<n>-<trigger key>`, and the hold is new while one of those keys isn't in a `digest-new` comment. Its announcement writes them all into the marker. So each such trigger is announced once, whatever order they're found in, and resolving one doesn't make the hold new again. A hold whose triggers are all mentioned is never new.
- A new item with no mention is listed in the body only, and its key is never written into a `digest-new` comment.
- Each pass with new items to mention posts one comment. It lists them in rank order, each with its issue, title, kind and link, then the `cc` line (section 9), then `<!-- issuedog:digest-new items=<key>,<key> -->`.
- In the marker, a key's spaces, control and non-ASCII bytes, `%`, `,`, `<` and `>` are percent-encoded as `%XX`. That changes no key phase 1 makes.
- Over the size limit, the lowest-ranked items are left out of the list and the marker, and a line says "…and N more, which I'll announce in the next comment." They're new on the next pass.
- With `notify` empty, no comment is posted. So turning `notify` on, from empty, announces every open state error in one comment, as none was announced while it was empty. Over the size limit, the rest follow in the next passes' comments.
- The comment is posted before the body is written, so a replay finds it and doesn't post it again. A failed comment still lets the body be written, and the next pass announces the items. The exception is the pin: on the pass that creates the digest, on a start's first pass while the pin note is there, and on a later pass that tries a failed check again, the create and the pin's body edit come before the comment. A check or pin that fails again makes no edit of its own: the body is written after the comment, under the failure's note. The pass's comment hasn't been posted yet then, so a replay still announces the items once.
- An edited comment counts for nothing, so an untrusted write collaborator can't silence future mentions by adding keys. At worst the owner gets one repeated mention. A reaction doesn't change a comment's `updated_at` (checked on real GitHub, #160), so a 👍 on an announcement doesn't count as an edit.
- A deleted comment still counts until a restart, since the comment poll lists no deletions. Even if the deletion moves the digest's `updated_at` (section 16), the daemon never takes a snapshot of the digest, so it doesn't read the digest's comments again.

**Cost.** On a pass where nothing changed, the digest makes no request beyond the poll. When something changes, it adds at most one comment and one body edit per pass, a timeline read and any revert when the digest was closed or reopened, and one `isPinned` check per start while the pin note is there, with one more, and a pin, on each pass that writes the body while the check or the pin keeps failing. The title rule reads an issue's edit history once per start, and only for an issue it would otherwise take. While the read fails, each pass reads again, in one GraphQL request for every issue still held, up to `loop.max_attempts` times per start, and the last of those failures posts one comment per issue; after it, the read is made on one pass in `loop.max_attempts`. So an outage of P passes at a start costs about `loop.max_attempts` + P / `loop.max_attempts` requests: 22 for an hour at the defaults, one pass a minute. Step 1's reaction reads on open errors, and a human task's reads of its reactions and blockers, are conditional (8.1).

### 9.5 Escalation

Deterministic rules decide what needs the owner. An LLM may add items to the escalation list. It never removes one.

Escalation triggers come from config (`escalate` in section 13), for example changes to dependency manifests, migrations, deployment files or payment code. A triggered PR gets the `review:high-risk` label and a "Look at these first" section listing the matched files and rules. Only a PR to `main` is reviewed, so a story's PR is triggered by any change on its branch that matches, and a task's PR into a story branch is merged by the App as usual (7.5).

### 9.6 Assignment

The owner finds everything waiting on them in GitHub's own "assigned to me" view. The daemon assigns every user in `notify` to an issue or PR while it waits on them, and unassigns them as soon as it doesn't:

| Item | Assigned while |
|---|---|
| Question round | The issue is at `clarifying` or `planning` with an unanswered round (9.1) |
| Spec or plan | The issue is at `spec-review` or `plan-review` |
| Hand-off | The task is at `needs-human` after a hand-off comment (9.3) |
| Human task | The human task is at `needs-human` and every issue blocking it is closed (9.4). The first pass after the last blocker closes assigns `notify`, and one that reads a new open blocker unassigns them. Closing the task ends the item, but `notify` stays assigned to the closed issue (see Pipeline issues) |
| Pull request | The PR targets `main`, is open, and its task or story is at `pr-open`. It is unassigned when the PR merges or closes, or when the issue leaves `pr-open`. A task's PR into its story branch waits on the App, not the owner (7.5) |
| State error | From the daemon's state-error comment until a trusted user reacts 👍 to it, or its cause is gone (5.3) |
| Discussion hold | The issue is held for discussion and a trigger is unresolved (6.4) |
| Dropped with an open PR | The issue is held with `reason=dropped` (6.4), until its PR merges or closes |
| Triage flag | The issue's latest triage marker is a flag (6.2), until a code owner answers it |
| Finished story | The story, or an epic planned into tasks, is at `planned`, every child its `created` record names is closed, and no open issue is below it (9.4). Closing the story ends the item, but `notify` stays assigned to the closed issue (see Pipeline issues) |
| Closed story PR | The story is at `pr-open` and its PR closed without merging (7.5), until the PR reopens or the story closes. Not built yet (phase 3) |

- These are the same items the digest lists (9.4), but for a closed issue's `closer` state error (5.3), as a closed issue is never assigned (see Pipeline issues). Assignment is built for the items that list has today, on issues (#191, #192): a question round, a spec at `spec-review`, a plan at `plan-review`, a state error, a triage flag, a discussion hold, a finished story and a human task. It takes its items from the same list the digest builds, which is filled whether or not the digest is on, so the two never disagree, and each story that adds a kind of item adds it to that list. The hand-off row waits for phase 3 (9.3), the pull request and closed story PR rows for phase 3, and the dropped row for phase 3 too, as it needs PRs (#234).
- **Pipeline issues.** Assignment covers an open issue the daemon holds a snapshot of, never the digest, that has a stage label, a transition marker of the App's, or an item on the list. The last takes in a triage flag, which waits at intake with no stage label, and a state error on an issue outside the stages. A stage label left out (5.1) doesn't count here, although 6.2 counts it: such an issue is held back from the pass for up to 30 seconds, and after that the pass goes on without the label, until it is explained or removed (5.1). An issue with none of these, such as one triage left to people or one not triaged yet, is left alone, and so is a closed issue.
- **What it writes.** A pipeline issue's assignees should be exactly the `notify` users while it has an item, and nobody while it hasn't. Only the difference is written, removals first, so an add doesn't meet GitHub's cap of ten assignees with ones that are going. Logins compare in any case. Each pass looks only at the issues step 1 succeeded on (8.1), so an issue whose read or step 1 failed keeps its assignees that pass. A finished story's item is judged again on every pass from what the poll listed (9.4), so a child's close assigns `notify` to the story, and a child reopened unassigns them, with no visit to the story. Assignees come from the issue GET the snapshot makes anyway, so an unchanged pass makes no request.
- **Stage work in the same pass.** Assignees are written before the pass's stage work (8.1), but for an unassign of `notify` users from an issue at `clarifying` or `planning`, which waits until after it. A run there that leaves the issue at `spec-review` or `plan-review`, as the next revision a send-back gets in the same pass does (7.4), calls the unassign off, as the issue waits on the owner again, so `notify` stays with no write. So does a run whose result fails to apply, and is tried again on the next pass (8.2), which judges the assignees then, so a crash during the apply leaves them as a pass with no crash does. Anything else, such as a run that fails or a run on another issue, leaves the unassign to be made after the stage work.
- **A login GitHub won't assign.** GitHub leaves out a login it can't assign, such as a `notify` user with no access to the repo. The daemon remembers such a login, logs it once, and doesn't add it again, so it can't cause a write on every pass. A change to `notify`, or a restart, forgets it, and the first issue that wants it then tries once more. A remembered login that is assigned all the same, as by hand once it has access, stays where an item wants it.
- **A failed write.** A write that fails is logged as the pass's error, and the rest of the pass carries on, the issue's stage work included, since the failure says nothing of the issue as step 1 read it. A failed removal ends the issue's writes for that pass, so an add it would make waits for the next. The next pass reads the issue again, and writes again if it still differs. So a write that fails on every pass, such as with a 422 for a login GitHub can't assign (section 16), costs that read, which its ETag may save, and the write on each pass, and never holds back the issue's stage work. A write that finds the issue gone, deleted or transferred (section 16), is no error: the issue gets no stage work that pass, if the write came before it, and the next pass reads it again, which drops it if it's still gone. A gone issue whose write got any other answer is found gone by its next read instead, the read before a run or on applying a run's result (8.2), or else the next pass's, and the read after that drops it.
- **Leaving the pipeline.** An issue that leaves the pipeline while it's open, as a flag that `/ignore` answers does, loses the `notify` users it was assigned, once. Its other assignees, and any later change to them, are left alone. That memory is lost on a restart, so an issue that left while no daemon ran keeps them.
- Each PR carries the `priority:*` label of the task it closes, or a story's PR the story's (7.5). The issue's label is the priority: the daemon copies it to the PR and reverts any other change to the PR's label. Not built yet: PRs are phase 3's (#234).
- The owner sees what's waiting with `is:open assignee:@me sort:created-asc`, and the most urgent items by adding `label:priority:p0` or `label:priority:p1`. The digest orders the same items by how much each one unblocks (9.4).
- Only the App changes assignees on pipeline issues and PRs. Assignees are never read as state (section 5): a manual change is reverted on the next poll and changes nothing else.

## 10. Verification

Verification is the gate between implementation and a PR.

### 10.1 Deterministic checks (run first)

The daemon decides these itself, outside Claude, from exit codes and its own git inspection of the bare repo.

1. Every command in `verify.commands` (tests, lint, vet, build) passes.
   - The commands run as `agent` in a fresh checkout of the head SHA.
   - They get no GitHub credentials, the `network.allow` egress list and `verify.command_timeout`.
2. The diff touches no protected path (section 6.3). Every protected path must also be as it is at the baseline, one `main` commit. On a story branch, and for a task in a story, that's the story's baseline: the merge base of `main` and the story branch's tip, the tip the task is named against (3.4). `main` is linear, as section 15 allows only squash merges, so that's the newest `main` commit in the tip's history; if git finds more than one merge base, the rule fails. For a task with no parent, it's `main` as it is now. For a conflict bug, it's the `main` commit the bug names, which is also the merge base of its head and `main` (7.5). A task's own history never chooses its baseline. A story's history does, and nothing pushed to the branch can make that an older commit: only an admin or the App can create a story branch or force-push one, and the App creates it from `main` as it is then, so its baseline is never older than the `main` commit it was cut from (7.5, section 15). So no older version on `main` counts, and nothing pushed to a branch can bring in agent config (3.4). A story's head that's only behind `main` still passes, since its baseline moves only when `main` is merged into the branch.
3. No file matching `verify.test_globs` is deleted, and no new `verify.skip_markers` are added.
   - Markers are checked only on added lines, and only in files matching `verify.test_globs`.
   - Markers are plain strings. A marker that starts with a letter matches only where it is not preceded by a letter, digit or `_`. So `xit(` matches `xit("works", …)` but not `os.Exit(`, and `.skip(` still matches `describe.skip(`.
4. Files in `verify.config_paths` are unchanged, unless the task's scope is `verify.tooling_scope`.
5. When the diff modifies files matching `verify.source_globs` that are not tests, it also adds or modifies files matching `verify.test_globs`. Changes to other files, such as docs, are exempt.
6. The diff is at most `verify.max_diff_lines`, counted by the daemon. Binary files are allowed only if they match `verify.binary_allow`.
7. The branch is based on its target branch and merges cleanly: its story branch for a task in a story, else `main` (7.5).

Rule 2 is checked before rule 1, so no command ever runs on a diff that changes agent config.

Any failure is a verify failure, with the output attached as findings. A diff over the size limit gets the finding "task too large, split it". The LLM verifier cannot override a deterministic failure.

### 10.2 LLM verifier (task level)

It runs only after the deterministic checks pass. It runs in a fresh process and a fresh checkout of the head SHA (section 3.4), with:

- the task's acceptance criteria and definition of done
- the full diff against the base, which the daemon writes to the context directory (rule 6 guarantees it fits)
- the deterministic check output

It returns `pass`, `request_changes` with findings tied to acceptance criteria, or `question` when a criterion is ambiguous.

The run fails closed: an unparseable or missing verdict counts as `request_changes`.

### 10.3 Story verification

- **When it runs.** The trigger is in section 7.3.
- **What it runs.** The daemon runs `verify.story_commands` (e2e suites) on the story branch's tip, under the same rules as 10.1 rule 1, and only on a tip whose checks pass (7.5). A story with no story branch is verified on `main`.
- **What the LLM checks.** The LLM verifier checks the story's acceptance criteria against the e2e results.
- **On failure.** Failures become `bug` sub-issues with an `origin` marker, worked on the story branch (7.5).
- **On a pass.** The App opens or updates the story's PR to `main` (7.3), or closes a story with nothing to merge.

### 10.4 The `issuedog/verify` check

- **On pass.** The daemon posts a check run named `issuedog/verify` with conclusion `success` for the head SHA. It includes a short summary and a link to the verifier comment.
- **Where.** It's posted on task PRs, whatever their target, and on a story's PR (7.5). On a story branch's tip, its `external_id` names the branch, which is how the daemon marks the tip as checked (7.5). The check run is the only record of it. So the story's PR, whose head is that tip, carries it. It's the tip's check, so it doesn't show whether story verification passed on that tip (7.5).
- **Ruleset.** The `main` ruleset requires this check, with the issuedog App pinned as its source. Nobody else, including anyone with write access, can satisfy it. The `issuedog branches` ruleset on story and task branches requires no check (section 15): the App merges task PRs into a story branch only on a passing check, and a push it didn't make is checked again (7.5).
- **When `main` moves.** For a PR to `main` from a task with no parent, the daemon re-runs section 10.1 on the merge result of `main` and the PR head. If that fails, it updates the check to `failure`. The ruleset does not require branches to be up to date, so a merge to `main` doesn't force every open PR to update and be re-approved. The daemon's merge-result check stands in for that. A story branch instead gets `main` merged in with a real merge commit, and its new tip is checked (7.5).

## 11. Templates

Adapted from CCPM (MIT, Copyright (c) 2025 Ran Aroussi). Attribution goes in `NOTICE`.

Acceptance criteria and the definition of done are plain `-` bullets, not `- [ ]` checkboxes. Nothing reads or ticks them: the verifier's comment and the checks record what's done, and a tick would be a body edit that changes the hash (7.4).

### 11.1 Spec (issue body after spec-review)

```
## Problem
## Goals
## Out of scope
## Users and flows
## Constraints
## Acceptance criteria
- observable, testable statements
## Decisions
- Q2.1 → c: summary of the answer (owner, round 2)
```

The interviewer's `spec` output fills these sections, and the daemon renders them:

- **Writing it.** The spec replaces the whole body. The title stays, and the original text stays in GitHub's edit history.
  - Agent text is escaped (5.1). A `#` or `##` heading in it is demoted to `###`, so it can't add a section.
  - Acceptance criteria are plain `- ` bullets, with any `[ ]` the agent wrote stripped. An empty section reads "None.".
  - The body's first line is `<!-- issuedog:rewrite run=<run id> -->`, which makes the write the App's full rewrite (5.1). It has no dirty note. On a dirty body, the marker also carries `replaced=<login>`, the body is clean from then on, and the revision comment starts with a line naming whose edit the spec replaced, with the login defused (7.4).
- **Write order.** The type label, if the spec sets a type, then the body edit, skipped if the body already matches as the App's last edit. When the run's own rewrite marker is on it, as after a crash just after the edit, its `replaced` keeps the revision comment's first line the same. Then the revision is posted with the move to `spec-review` (7.4), and its hash is taken from the body GitHub returns. Once the move is written, a replay doesn't edit the body or the type again.
- **The revision comment.** It starts with the line naming whose edit the spec replaced, if the body was dirty, then the type line when the spec sets a type (9.1). Then come the agent's `message`, which answers revision notes or says what changed, and a list of the decisions "Added, not asked". Then the revision and how to approve it (7.4), and last the `cc` line (section 9).
- **Decisions.** Every question asked appears at least once, in one of these forms:
  - answered: `- Q2.1 → c: <summary> (mertenvg, round 2)`, or `- Q2.1 → free text: <summary> (mertenvg, round 2)`
  - superseded: `- Q1.3 → superseded by Q2.1`, by a question asked in a later round
  - dropped: `- Q1.3 → dropped: <why>`

  A decision the interviewer made without asking reads `- Added, not asked: <summary>`. An answer names a login with a clean, trusted comment on the issue, and the round it was answered in, which is no earlier than the question's. Only questions on clean round markers count as asked (9.1). An answer's letter names one of its question's options, as the round's clean comment reads back in the 9.1 format, the way the digest copies them (9.4). A round whose comment doesn't read back allows `a` to `d`.

A task that writes comments or issue bodies adds `- Text the daemon didn't write is escaped (5.1)` to its definition of done.

### 11.3 Planning rules

- An epic plan contains either stories, with acceptance criteria and no tasks, or tasks, when the epic has a single user-facing outcome. A story plan contains tasks.
- At most `plan.max_tasks` (default 10) tasks per plan. This is a hard limit (#247's Q2a): larger work becomes more stories, or the planner asks. Raising `plan.max_tasks` allows more.
- Each task maps to one scope label from the allowed list, and each task other than a human task maps to one PR.
- Each task should fit within `verify.max_diff_lines`.
- Prefer extending existing code over adding new modules. Each task's body names the existing files it touches. The plan comment names none (11.4).
- A scope outside the allowed list becomes a question to the owner.
- Work only the owner can do is a task marked `human`, written in the template from section 9.3 rather than 11.2.
- "Depends on" names items of the same plan, by ID. Links to issues outside the plan, and `depends-on` links to other repos (section 14), wait for later work. So the link limits below count within the plan.
- Each item may set a priority, `p0` to `p3`, and a model and an effort from `models.allowed` and the effort levels (section 13). An item with no priority shows the issue's. The plan's validation checks the model and effort (below). When the daemon creates the item's child, it sets the child's `model:*` label, by its entry's label suffix, and its `effort:*` label from them, which set the runs on it, a story's planner runs included (3.3). The model is resolved against `models.allowed` again then, so one a reload has since dropped is left off and logged, and the child is still created. An item with neither gets no such label. Issues also get these labels from `/model` and `/effort` (9.2) or by hand.
- **A revised plan.** A plan for an epic or story that was `planned` before is a revision of its approved plan (9.1, 6.4). It marks every item `kept`, `changed`, `new` or `dropped`, and a first plan marks none. Every child of the approved plan, the issues matched to its items by their `origin` (5.2), appears exactly once, by its item ID, kept, changed or dropped. A child whose issue is closed can only be kept: changing its work means a new item with a new ID. A kept or dropped item has its ID, title and status alone, and a kept one keeps its dependencies from the approved revision. A changed item is written in full, as a new one is, and keeps its ID. A new item's ID is no child's, and no item's of the approved revision. Other sub-issues are context only, never items. A revision always waits for review, whatever `plan.review` says (7.2, #195's Q2a).

**Items.** Every item has an ID, a title, an outcome, acceptance criteria and its dependencies, and may have a priority, a model and an effort. A task also has a scope, and one of two bodies, which becomes its issue body: an 11.2 body (context, change, definition of done and test plan), or for a human task, the 9.3 fields. A story has neither. A revision's item also has its `status`, and a kept or dropped one has nothing but its ID, title and status.

**A human task's check.** Its **Done when** is text, and may add a check the daemon runs first (9.3). A check is one of five kinds, with exactly that kind's fields:

- `label`: a label exists. `label` is a name of at most 50 characters, on one line, and not `.` or `..`.
- `issue-type`: an issue type exists. `issue_type` is a name on one line.
- `file`: a file is on `main`. `path` is a path from the repo root, on one line, with no leading `/` or space, no backslash, and no empty, `.` or `..` segment. `contains`, if set, is text the file must contain, one line of at most 256 bytes.
- `ruleset`: a ruleset on `main` requires a check. `check` is the check's name, on one line.
- `installation`: the App is installed on an owner. `owner` is a user's or organization's login.

The daemon runs a check as 9.3 says, and records it on the task's `origin` marker (section 5) only once this validation has accepted it, so the two can't differ.

**Validation.** The daemon checks the planner's output after its schema, which it doesn't trust, so every bound the schema has is checked again. It fails closed: a broken rule is a failed attempt (8.3), with nothing written. The failure names every rule broken, each as `rule <name>: <detail>` with the item and field, and the attempt cap's error quotes the last one (5.3). The rules:

- `outcome`: a plan has a plan and no questions, and a question round has questions and no plan.
- A question round follows the interviewer's question rules (9.1): `question-count`, at most `loop.max_questions_per_round`; `blocks`; `options`, 2 to 4, no two the same; and `one-line`. Its comment fits `length`.
- `structure`: the plan is `stories` or `tasks`, and a story's is `tasks`. It has at least one item and a summary, and each item has criteria. A story has no scope, `human` or body. A task has exactly one body, the human task's when it's marked `human`. A task body has its context, change, definition of done and test plan.
- `item-id`: `S1`, `S2` and so on in a plan of stories, `T1`, `T2` and so on in a plan of tasks, with no leading zero, each used once.
- `status`: a revision's every item is `kept`, `changed`, `new` or `dropped`, and a kept or dropped one has no field but its ID, title and status. A first plan's items have no status.
- `children`: in a revision, every child of the approved plan appears exactly once, never as `new`, and an item marked kept, changed or dropped is a child's.
- `closed-child`: a closed child is only ever kept.
- `new-id`: a new item's ID is no child's, and no item's of the approved revision.
- `scope`: each task has a scope from the list.
- `max-tasks`: at most `plan.max_tasks` tasks. In a revision, the tasks that aren't dropped.
- `depends-on`: each dependency is another item of this plan, named once, and in a revision, not a dropped one.
- `cycle`: no dependency cycles. Each one is named, such as `T1 → T2 → T1`. In a revision, a kept item's dependencies from the approved revision count, less any on an item the revision drops or doesn't list, and a dropped item has none.
- `sub-issues`: the issue's existing sub-issues and the plan's items come to at most 100. In a revision, only its new items are added.
- `links`: no item is blocked by, or blocks, more than 50 items, a revision's links counted as for `cycle`.
- `model`: a full name on `models.allowed`, or an entry's label suffix.
- `effort`: one of the five effort levels.
- `priority`: `p0` to `p3`.
- `human-task`: a human task fills every 9.3 field: a goal, why it blocks, at least one step and one link, the **Done when** text and the estimated time.
- `done-when`: a human task's check is valid, as above.
- `file-paths`: the plan comment's visible text names no file path (#247's assumption 8). A file path is a word with a directory and a file extension, such as `dir/file.ext`, outside a link. A bare file name is allowed. So that prose with a slash passes, the extension is a lowercase letter followed by lowercase letters and digits and isn't a Go module's version such as `.v3`, the directory has a letter and isn't only versions such as `2.x`, and the word isn't capitalized names whose last is one of the framework names Express.js, Next.js, Node.js, Nuxt.js, React.js, Socket.io and Vue.js: "TLS 1.2/1.3", "HTTP/1.1", "Python 2.x/3.x", "Express/Node.js", "Express/Socket.io", `gopkg.in/yaml.v3`, `net/http.Handler` and `internal/daemon.checkPlan` are no file paths, while `Assets/Scripts/Player.cs`, `Components/Button.js`, `scripts/install.ps1` and `v2/main.go` are. The visible fields are the why, the summary, the message, the assumptions and the order, each item's title, outcome and criteria, and a human task's **Done when** text.
- `one-line`: the why, the order, each assumption, each item's title, outcome and criteria, each definition-of-done entry, and a human task's goal, why it blocks, steps, links, **Done when** text and estimated time.
- `length`: the plan comment as it's posted, markers and plan data included, fits GitHub's 65,536-character limit with 1,024 to spare.

The check also fails a result on an issue the planner no longer runs on, read again: one that isn't an epic or a story, such as one the owner retyped during the run, or one `planned` before whose approved plan revision doesn't read back (9.1). For a revision, the check reads the approved plan's children as creation finds them (5.2), each with its state. A sub-issue or child read that fails during the check is a failure to apply (8.2).

A plan contains either stories or tasks (11.3); the template shows both forms. Item IDs (`S1`, `T1`) are the stable IDs used in `origin` markers (section 5.2).

- **Levels of detail.** The comment shows each item's fields above and no more. Of a task's body it shows only a human task's **Done when** text, and its check by kind, never its path or other values. So the comment names no file paths (11.3), and a task's files are only in its body, which the `plan-data` marker keeps.
- **The parts.** Priority is the item's, or else the issue's, `p2` when it has none, so every item shows one. `human`, model and effort show only when set. A message on what changed goes after the summary, headed "Changes since rev <previous>" from rev 2 on. Assumptions show only when there are any.
- **Agent text** is escaped as a spec's is (11.1): headings demoted, `[ ]` boxes stripped, mentions defused, and tags and markers escaped. Criteria are plain `-` bullets.
- **The validation line** is the daemon's own, from its counts: the items and what they are, the sub-issues the issue will have, and the most dependency links of one type an item will have. An epic's plan of stories reads "N stories, with no tasks".
- **Skipping review.** A plan that skips review (7.2) heads its assumptions "Assumptions:", and has no `cc` line or approval line. Its last line says the plan skips review, as `plan.review` is false, and the issue moves straight to `planned`.
- **The markers.** After the text come the move's transition marker, with `rev` but no `body`, the `plan-data` marker, and the plan revision marker as the last line (section 5, 7.4). Once anyone but the App edits the comment, none of them counts, and the daemon records the move again in a comment of its own (5.1).
- **A revision** (11.3) shows each item's status after its title, as in `**T2. Title** · changed · scope:booking · p1`. A kept or dropped item is that one line, `**T1. Title** · kept`, and a changed or new one shows its fields as any item does. Its validation line counts the items that aren't dropped, adds only the new items to the sub-issues, counts a kept item's links from the approved revision, and adds "every child listed once, kept, changed or dropped, and each closed one kept". A revision never skips review, so it always has the `cc` and approval lines.

### 11.5 Pull request

The title is `<type>: <short sentence>`, where `<type>` is one of `pr.title_types` (section 13; default `feat`, `fix`, `chore`). The implementer names the type in its structured output, and output naming a type outside the list fails validation (3.3). With squash merging (section 15) the title becomes the commit subject on `main`.

```
Closes #N

## What changed
## Why
## Tests
- added: ...
- updated: ...
## Results
| Check | Result |
|---|---|
| go test ./... | pass (412 tests, 38s) |
## Verifier notes
## Look at these first   (only when escalated)
```

Story branches change the first line (7.5):

- **A task's PR into its story branch** starts with `Task #N, in story #S` instead of `Closes #N`. GitHub's closing keywords act only on a merge into the default branch, so the App closes the task itself once it has merged the PR.
- **A story's PR** to `main` starts with `Closes #S`, and lists the story's closed children under "What changed". The story verifier names its title's type, from the same list. Its squash-merge makes it the one commit the story adds to `main`.

### 11.6 Created children

The daemon writes each child of an approved plan from its plan item (5.2):

- **Titles.** A story's starts with its item ID, `S2. Title`, never twice. A task's is as planned.
- **A story's body.**

  ```
  **Parent:** #N   **Priority:** p2
  ## Outcome
  One sentence.
  ## Acceptance criteria
  - ...
  Depends on: S1, or nothing.
  <!-- issuedog:origin plan=#N rev=1 item=S2 -->
  ```

- **A task's body** follows 11.2, and a human task's 9.3. Each body's last line is its `origin` marker, with `human=1` for a human task (section 5).
- **Agent text** is escaped as a spec's is (11.1): headings demoted, `[ ]` boxes stripped, mentions defused, and tags and markers escaped, so the `origin` marker is the body's only one. An empty section reads "None.".
- **Labels.** The type, as the `type:story` or `type:task` label, or on a `types: issue-types` repo as the `Story` or `Task` issue type; `scope:*` for a task; `priority:*`, the item's, else the parent's, else `p2`; the label of its first stage, `planning`, `ready` or `needs-human` (7.2); and `model:*` and `effort:*` when the item sets them (11.3).
- **Size.** Every body is checked before anything is written. One over GitHub's 65,536-character limit, with 1,024 to spare, is an error naming the item, and none of the plan's children is created. A human task's is checked with the widest issue number for each issue its **Why it blocks** names.

## 12. Agents and skills

- **Stage prompts.** These live in `.issuedog/prompts/{triage,interviewer,planner,implementer,verifier}.md`. issuedog ships defaults, and a file on `main` overrides the default (section 3.4).
  - The defaults and the schemas are embedded in the binary, so the image needs no extra files. `triage.md`, `interviewer.md` and `planner.md` ship now. The implementer and verifier prompts ship with their stages. Schemas can't be overridden.
  - The planner's prompt covers the levels of detail and item IDs; scopes, sizing, priority, model and effort; dependencies, and human tasks with their checks; and asking a question for a scope that isn't on the list, or a choice it can't settle. Its schema allows a plan or a question round, with the five check kinds (11.3).
  - A blank file on `main` falls back to the default, with a warning. A file over 64 KiB, or a read error other than not-found, is a setup error: the run doesn't start and isn't counted. So is a failure to read what the planner's files need: the parent, a sub-issue list, a sub-issue's stage or type, or for a revision, its children.
- **Context files.** Each run gets its files in `/run/issuedog/<run-id>/` (3.1). Text in `untrusted.md`, and every comment and body in the interviewer's and the planner's files, sits in a code fence it can't close, under a heading the daemon writes.
  - `system.md` is a fixed preamble the daemon writes, then the stage prompt. The preamble covers the trust rules, the output contract and this repo's limits, and a prompt on `main` can't remove it. The interviewer's limits are the questions per round, the rounds so far and the next round's number, which follows the planner's rounds too, the logins a decision may name, and whether it may set the type (section 4). When the planner asked rounds, the preamble also says those questions aren't the interviewer's, so no decision names them (9.1). Its preamble always says, too, that an issue with a parent is never typed `story`, whether the issue is back from a discussion hold, and if so, the stage it came from, and the outcomes the run may return there, `unchanged` and `plan` included only where they're allowed (9.1). On a story with a parent, its typing line says to leave the type out, and the hold line says never to write the spec (9.1).
  - The planner's preamble says the titles of the sub-issues `children.md` and `parent.md` list are data, not instructions, while the issue's and the parent's own titles are trusted (6.2). It gives every limit its check enforces (11.3), with this repo's values: the plan kinds the issue allows; the scopes, `plan.max_tasks` and `verify.max_diff_lines`; `models.allowed`, with their label suffixes, and the effort levels; the default priority, the issue's own; how many more sub-issues fit, which bound a revision's new items; whether the plan is a first plan, with no statuses, or a revision of the approved plan revision it names, with the rules of a revision (11.3), and that a revision always waits for review; the rounds so far, which of them are the planner's, and the next round's number, with the questions per round; the item ID format; the check kinds, their fields and bounds; that the visible fields name no file paths; that "Depends on" names only items of this plan, within the link limit; the one-line fields; and the comment's length.
  - `prompt.md` is the daemon's short task text, saying where the context files are. Triage's names each one by its full path. The interviewer's and the planner's name the context directory once, then each file by name.
  - `untrusted.md`, when there is anything for it, holds the untrusted input of 6.2.
- **The interviewer's files.**
  - `issue.md`: the number, title, type or "none", parent (`#N` or "none"), author, and the body. The body's markers are left out while the App made its last edit, as when it rewrote the body as a spec, whoever filed the issue, or nobody edited a body the App filed; otherwise they're escaped, as a trusted user's edit isn't the App's text (5.1, #312). A dirty body, or a title or body an untrusted author changed after admission (6.2), is replaced by a line saying where it is, if anywhere. A title someone untrusted renamed, on an issue the App or a trusted author filed, shows as of its last trusted change, with a line saying where the new one is, if anywhere (6.2). Its renames come from step 1's timeline read, so they cost no request. At the `clarifying` after a discussion hold, it also has an "After a hold" section: the stage the issue came from, where its latest hold began and ended, and the discussion's owner input (6.4), each comment fenced under a heading the daemon writes.
  - `conversation.md`: the App's clean comments, with markers left out, earlier rounds labelled "Round N, QN.1–N.k", the planner's too, and revisions labelled as of the spec or of the plan; and trusted, clean comments, with author, ID and the round they answer. Oldest first.
  - `input.md`: this run's input (9.2): each input labelled as an answer to the latest round, as the revision notes that sent the spec back, or as new since the issue came to `clarifying`, as after an override. At the `clarifying` after a hold from `spec-review` or `plan-review`, a `/revise` that waited through the hold is there as revision notes (6.4). With no input, it says "none: first run".
  - A login in these files' headings, in `issue.md`'s Author line, and in the notes that stand in for the title or body, is named only when it is a valid GitHub login: letters, digits and single hyphens, with an optional Enterprise Managed User `_shortcode` suffix, 39 characters at most, or an App's `[bot]` login. Anything else shows as "someone unnamed".
- **The planner's files.** It runs in a fresh checkout of `main` (3.4). Its files are read when a run starts, so a pass where nothing changed makes no request for them.
  - `issue.md`: as the interviewer's, with the issue's priority, `p2` with none. It has no "After a hold" section.
  - `parent.md`, for a story with a parent: the parent's number, title, type and body, its latest plan revision, and its other sub-issues, each as `children.md` lists them. The body's markers are left out as `issue.md`'s are. The plan revision is the comment's text with markers left out, and only while it's clean, not hidden and still matches its hash (7.4); else a line says why it's left out. A parent's title or body its untrusted author changed after admission goes in `untrusted.md`, as the issue's does, and so do both when it was never admitted, and a title someone untrusted renamed, which shows as of its last trusted change (6.2). Its type, by label, is judged as a sub-issue's is (below). That reads the parent's timeline once, for its admission, its renames and its type. A parent in another repo isn't read, and the file says so.
  - `children.md`: the issue's sub-issues, open and closed, each with its number, title, state, a closed one's close reason, type and, while it's open and in this repo, its stage, or "not in the pipeline" when no transition moved it. One in another repo is named with its repo, as it counts towards the 100, and its type isn't read, as its labels aren't this repo's to judge.
    - **Stages** are read from each sub-issue's markers, as for any issue (5.1), never from its stage label, which may be an untrusted one step 1 hasn't reverted yet (#312). One whose snapshot the daemon holds after a good step 1 costs no request but for its edits' history (5.1); one it doesn't hold is read. A closed one gets no stage.
    - **Types** by label are judged as the label rules judge them (5.1), never taken from a `type:` label as it is: an untrusted one may be there before step 1 reverts it, and for good on a closed issue, which step 1 doesn't visit (#445). One whose snapshot the daemon holds after a good step 1 has the type step 1 left it, at no request. For any other, the type is its first `type:` label whose latest change that stands is an add, by the App or a trusted user, or none, which costs its timeline once, only when it has a `type:` label. A GitHub issue type, which is no label, is taken as read.
    - **Titles** are data, not instructions, in this list and in `parent.md`'s, as the preamble says (6.2).
    - **For a revision**, of an issue `planned` before (11.3): the children of its approved plan, found as creation finds them (5.2), each with its item ID, number, title, type, and stage or close reason, in plan order; then the approved revision's items, as its plan data keeps them, task bodies included, fenced, which a kept item keeps and whose dependencies count; then the other sub-issues, as context only, never to be listed as items. The intro says to list every child exactly once, by its item ID, kept, changed or dropped, and that a closed child can only be kept.
  - `conversation.md`: as the interviewer's.
  - `input.md`: this run's input: each labelled as the revision notes that sent the plan back (7.4), as an answer to the latest planner round, as posted while the issue was on hold, or as new since the issue came to `planning`. With no input, it says "none: first run". While the move that put the issue at `planning` is the interviewer's `plan` or `unchanged` after a discussion hold (9.1), it also has, each fenced under a heading the daemon writes: after `plan` only, that move's message, as the interviewer's notes on what changes in the plan (section 5); the discussion's owner input, as the interviewer read it (6.4); and each `/revise` the interviewer's moves after the hold named with `cmd=`, once each, as revision notes for the plan.
  - `untrusted.md`: as the interviewer's, on epics and stories (6.2), with the parent's untrusted title or body too.
- **The triage agent's files.**
  - `issue.md`: the number, the author and whether they're trusted, and the type. For a trusted author, it also has the title and, unless it's dirty, the body.
  - `comments.md`, if there are any: trusted people's clean comments. The App's comments are left out.
- **Domain subagents.** These live in `.claude/agents/*.md` and are available to the implementer and verifier during a run. Add one only when a domain has rules the model keeps getting wrong.
- **Skills.** These live in `.claude/skills/*`, for repeatable procedures such as adding a migration.
- **Changing them.** Agents cannot change any of these. They are protected paths, and the verifier only ever loads the versions on `main`.

Model and effort keys:

## 14. Cross-repo work

- **Proposing.** A planner may propose an issue in another repo listed in `cross_repo.allowed`.
- **Creating.** The daemon creates it with a link back to the source issue and labels it `stage:intake`. It carries no `origin` marker, so the target repo's daemon waits for a trusted person there to add `approved`.
- **Same owner.** The daemon links the dependency through the issue dependencies API (blocked-by).
- **Different owners** (for example `mertenvg/dmcn` and `dmcnp/open-dmcn`). Sub-issues are not allowed across owners, and native dependencies across owners are unconfirmed (section 16). The daemon instead adds a `<!-- issuedog:depends-on url=... -->` marker to the blocked issue and treats the issue as blocked until the target is closed.
- **Access.** The issuedog App must be installed on every owner in the allowed list.

## 15. GitHub setup per repo

1. **GitHub App.**
   - Repository permissions: Contents read/write, Issues read/write, Pull requests read/write, Checks read/write, Commit statuses read/write, Metadata read.
   - Organization permissions: Members read (for CODEOWNERS teams) and Issue Types read (for a human task's `issue-type` check, and the current name of a type a revert restores, 5.1). Without it, a revert restores the type by the timeline's name, which GitHub refuses for a type the org renamed (5.1).
   - Install it on each owner: the personal account and each org. Each installation has its own hourly token, and the daemon refreshes them.
   - No admin permissions.
   - Import its private key into the state volume once: `docker run --rm -i --cap-add NET_ADMIN -v issuedog-state:/state issuedog key import < app-key.pem`. Then delete the downloaded file. To rotate the key, generate a new one on GitHub and import it the same way.
2. **Plan.** Rulesets work on public repos on GitHub Free, and on private repos only with Pro, Team or Enterprise. Code owners on private repos also need Pro.
3. **Ruleset on `main`.** It targets `main` only. Story and task branches have their own (step 4). The ruleset:
   - require a pull request
   - require code-owner review, and dismiss stale approvals on new commits
   - require the `issuedog/verify` check with the issuedog App as the pinned source; leave "require branches to be up to date" off (section 10.4)
   - block force pushes
   - allow squash merges only
   - bypass list: Repository admin, "for pull requests only", so the owner can merge their own protected-path PRs; never the write role and never the App

   In the repo's general settings, allow only squash merging and set its default commit message to "Pull request title and description", so the PR title becomes the commit subject and the description its body (11.5).

   **Interim.** While the pipeline is run by hand with the owner's token, the owner authors every PR and cannot approve it. Until the App runs, the ruleset requires only a pull request with squash merging and blocks force pushes; code-owner review and the check are added then.

4. **Ruleset on `issuedog/*`**, named `issuedog branches`. Its target is the branch pattern `issuedog/*`, so it covers story and task branches alike, since they share `issuedog/<n>-<slug>` (3.2, 7.5). The ruleset:
   - enforcement status: Active
   - restrict creations
   - restrict deletions
   - block force pushes
   - nothing else: no pull request and no required checks, so anyone with write access can push commits to a story branch, or merge into one (7.5)
   - bypass list: Repository admin, "Always allow", and the issuedog App, "Always allow"

   So a write collaborator who isn't an admin can push to an existing `issuedog/*` branch but can't create, delete or force-push one, task branches included, and names branches of their own outside `issuedog/`. Creation is restricted so that only the App or an admin can create `issuedog/*` branches. An admin can at any time, as the dispatcher does while the pipeline runs by hand, and is trusted with where a branch starts, since an admin can change the rulesets anyway. The App cuts a story branch from `main` as it is then, so no one else can start the branch from an old `main` commit, whose agent config the owner may since have changed, and its history then only moves forward, which is what lets rule 2 take a story's baseline from git (10.1, 7.5).

   Unlike the `main` ruleset's, this bypass list includes the App. The App is trusted to move these branches: it merges task PRs and `main` into story branches, as anyone with write access can, and beyond that creates story and task branches, pushes a new run's result over a task head it dropped and deletes a branch once its PR has merged, which need the bypass (3.4, 7.5). `main` still needs the owner's review, which a bypass there would let the App skip. The App's token stays with the daemon, never with an agent (3.1), so no agent can use the bypass. An admin can change the rulesets anyway, so their bypass gives them nothing new.

   **Interim.** While the pipeline is run by hand with the owner's token, the admin bypass covers the dispatcher's creation of story and task branches, and its resets and deletes of task branches, so the ruleset can go in at once.

5. **CODEOWNERS** including `/.github/CODEOWNERS`. The App is never a code owner.
6. **Labels.** `stage:*`, the closed stages `stage:completed` and `stage:discarded` (6.4) included, `priority:*`, `scope:*`, `approved`, `review:high-risk`, and `type:*` for personal-account repos. `model:<suffix>` and `verifier-model:<suffix>` for each entry in `models.allowed`, and `effort:<level>` and `verifier-effort:<level>` for each effort level (section 13). The daemon creates any that are missing on startup, and a new model's after a reload (8.1). It never edits or deletes a label, so a model dropped from the list keeps its labels.

   `triage:ask` and `triage:left` (6.2) aren't created on startup: GitHub creates each the first time the App adds it.
7. **Org repos.** An org owner creates the `Epic` and `Story` issue types.

  - that one PATCH sets an issue's title and body together, and its `userContentEdits` entry names the App, so a changed child's rewrite (6.4) reads as the App's full rewrite (5.1).
- **Renamed and deleted issue types.** A revert restores a type by the name the org gives it now (5.1), as the fakes model GitHub. Confirm on real GitHub:
  - that a renamed type keeps its ID on the issues, on the timeline's issue-type events and in `GET /orgs/{org}/issue-types`, while the events keep the old name;
  - that setting a type by a name the org renamed away is refused with a 422;
  - what deleting a type leaves: whether the issues lose it, and whether its events still give its name and ID. A revert to a type the org no longer lists is reported once as a `typegone` state error, and the issue goes on with the type that stands until a trusted user changes the type (#409);
  - that `GET /orgs/{org}/issue-types` answers 403 without Issue Types read, as the fakes model it, and not 404. Either is taken as a refused read, which keeps the timeline's name (5.1).
- **A removal's issue type.** GitHub's REST description gives the timeline's `issue_type_removed` event only `prev_issue_type`, and the fakes give it the same (5.1). Confirm on real GitHub whether it also carries an `issue_type`, and if so, which type it names. Either way, a removal counts as leaving no type (#246). The webhook's payload is another shape, and isn't the timeline.
- **Cross-owner dependencies.** Do native blocked-by links work across owners? One report says GitHub returns 422. If they do work, they could replace the `depends-on` marker.
- **Pinning the check source.** The ruleset can only pin the App as the source of `issuedog/verify` once the App "has recently submitted a check run". Setup must post one bootstrap check run before adding the rule.
- **Pinning the digest.** The daemon pins the digest with GraphQL `pinIssue` (9.4), but the permission `pinIssue` needs from an App is not documented. Test it with Issues write on a real run. A refusal there is logged and named in the digest's pin note, and becomes a `type:bug` issue. Checked live (#154): pinning doesn't change an issue's `updated_at`.
- **Finding the digest across a restart.** Changes made while no daemon runs can lead to a second digest (9.4):
  - The marker removed and the title changed. The old digest isn't found, so a new one is created, and the old one is an issue like any other, which triage runs on.
  - The `digest` marker swapped for an `origin` marker. The old issue isn't found, so a new one is created. Then step 1's dirty note escapes the `origin` marker. The App's versions of the old digest's body have no `origin`, so nothing is reposted (6.4), and its original post had none, so the title rule takes it as the digest again, and there are two pinned digests, with the newer one left alone for good. Reading the original post, which the title rule now does (#292), doesn't close this gap.
  - The marker removed, then a start whose edit-history read fails. Settled by #305: the old digest is held, out of the pipeline, with no digest created, until a read works, so there's never a second one. A read that fails on `loop.max_attempts` passes leaves the repo with no digest until a later read works, made once every `loop.max_attempts` passes (#437), or the owner restarts the daemon, renames the issue or puts its identity marker back, as its `digesthistory` state error says (9.4, 5.3).
  - All are visible to the owner.
- **The digest's pin note.** An untrusted write collaborator who puts "I couldn't pin this issue…" at the top of the digest's body just before a restart makes that start pin it again, overriding the owner's unpin. Otherwise the next pass writes the body again without it.
- **The digest's closes and reopens.** A trusted close followed by an untrusted reopen, both between the poll and the App's next write to the digest, or in the same second as that write, look like the write's own change (9.4). They're missed until the next change to the digest by someone other than the App, or a restart.
- **The digest as a sub-issue.** Someone may make the digest a sub-issue. If the owner then holds its parent, `/hold` gives the digest `stage:held` and a transition comment. It still stays out of the pipeline.
- **Links in titles.** The digest escapes `[`, `]`, `!` and `\` in titles (9.4), but GitHub still autolinks a bare `https://…` or `www.…`, which shows its whole target and loads nothing, and `owner/repo#1` still makes a cross-reference. Decide whether to escape those too.
- **Hiding an announcement.** Whether hiding a comment changes its `updated_at` isn't known. If it does, a hidden `digest-new` comment counts as edited, and its items are announced once more.
- **Unions in the planner's schema.** The planner's schema nests `oneOf`, for a check's kinds, and `if/then/else`, for a plan's kind and a task's `human`. Claude Code sends `--json-schema` as a non-strict `StructuredOutput` tool, and the API is reported to refuse unions only at the top level. Confirm this on the first live planner run. If it answers 400, flatten the schema and leave those rules to the daemon's check (11.3), which enforces them already.
- **`--json-schema` in long runs.** It must work together with `--dangerously-skip-permissions` and long tool loops. Also confirm how many structured-output retries are allowed.
- **Where a reposted `origin` lives.** Settled by #195 (#290, #291): in an App comment with no `cc` line, posted once the body's markers aren't read (6.4). The issue's origin is read from the body while its markers are read, and else from the newest clean App comment that carries one (section 5), so the class, the digest's plan order and matching a plan's children (5.2) all read it there, and the digest's title rule never takes an issue with one (9.4).
- **Where a plan's hash lives.** Settled by #247's Q1a: the plan comment's last line is the plan revision marker, `revision kind=plan`, whose hash covers everything above that line, the `plan-data` marker included. The move's transition marker, inside that text, carries `rev` but not `body` (section 5, 7.4).
- **Running a Done-when check.** Settled by #250: the daemon runs a check itself, as `issuedog`, with the App's installation token, or its JWT for `installation`, and reads a file check's file from its bare clone. A check is one of five kinds with validated values, so no agent text runs, and sections 3.1 and 3.2 hold (9.3).
- **Human tasks' reads.** Running a check and finding a human task's item (9.3, 9.4) rely on GitHub behaviour the fakes only model. Confirm on real GitHub:
  - that `GET /repos/{owner}/{repo}/rules/branches/{branch}` answers the App's installation token with Metadata read, org rulesets included;
  - that `GET /orgs/{org}/issue-types` answers 404 for a personal account. An org the App can't see may answer 404 too, and its check then fails as a personal account's;
  - that the reads of an issue's own reactions and of its `blocked_by` links give ETags, so an unchanged pass costs a 304 for each;
  - that `blocked_by` reports each blocker's `state`, so a blocker's close shows in it;
  - whether a reaction on an issue itself, not on a comment, moves the issue's `updated_at`. GitHub doesn't document it, and the live check that a reaction doesn't change a comment's `updated_at` (#160, 9.4) covers comment reactions only. Nothing waits on it, since an issue at `needs-human` is visited on every pass (8.1).
- **Free conditional reads.** Unconfirmed. "An unchanged pass costs no rate limit" (8.1) rests on GitHub's docs that a conditional request answered 304 doesn't count against the primary rate limit when it's authorized. Confirm live that a GET with the App's installation token and `If-None-Match` set to an earlier answer's ETag, as the daemon's ETag cache sends it, answers 304 for an unchanged resource, and that `X-RateLimit-Remaining` doesn't drop across it. Check it for the poll's issue list with `since=`, the 10-minute listing of every open issue and its `page=N` pages, an issue's comments, timeline and reactions, and a sub-issue list. If a 304 does count, each pass costs a request for every conditional read, and 8.1's polling cost is wrong. The specific ETag checks above, in Re-planning and Human tasks' reads, rest on this one.
- **Transferred issues in listings** (8.1). The daemon finds a transferred issue it holds only by its absence from the listing of every open issue. GitHub's REST docs for getting an issue say a transferred issue's old path answers a 301, or a 404 if the caller can't read the new repo, and a deleted one's a 410 or a 404, but not what the old repo's listings show of a transfer. The fake (#199, #239) drops a transferred issue from every listing of the old repo, `since=` or not, with no close and no event left there. Confirm live, with the App's token: that a transferred issue drops out of `GET /repos/{owner}/{repo}/issues`, with `state=open` and with `state=all` and `since=`, and isn't listed closed there; that the transfer moves nothing the old repo's `since=` listings show, so only the 10-minute listing finds it; and what the old path answers for an issue converted to a discussion, which also drops out of the listing.
- **Classic branch protection.** A `ruleset` check reads only rulesets, since classic branch protection needs Administration read, which the App doesn't have (section 15). So a check that only classic protection requires fails it. Decide whether that's wanted.
- **Approving PR reviews with comments.** Section 7.2 covers reviews with comments and approving reviews with none. An approving review that has comments is not yet covered.
- **Usage-limit text.** The text `-p` prints when a subscription limit is hit is undocumented, so `usage_limit.pattern` must be checked against a real occurrence.
- **`--bare` becoming the default.** Anthropic plans to make `--bare` the default for `-p`. `--bare` ignores `CLAUDE_CODE_OAUTH_TOKEN` and skips project agents and skills. Pin the Claude Code version, and re-test before upgrading.
- **Egress firewall on macOS.** The owner-matched firewall rule (section 3.1) needs `--cap-add NET_ADMIN` and the daemon's file capabilities. Confirm both work on Docker Desktop for Mac.
- **Rumi Black's plan.** Confirm its visibility and plan meet the ruleset requirement in section 15.
- **Public release.**
  - Anthropic does not allow third-party tools to offer claude.ai login or route requests through users' subscriptions without prior approval. The README should therefore require users to bring their own `ANTHROPIC_API_KEY`.
  - Ask Anthropic before supporting subscription tokens in a distributed build.
  - The product name must not include "Claude Code". Plain-text "runs Claude Code" is fine.
- **Max plan limits.** Limits for sustained unattended use on the owner's own Max plan are undocumented. Anthropic's usage policy assumes "ordinary, individual usage".
